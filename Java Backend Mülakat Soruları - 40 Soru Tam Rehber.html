ConcurrentHashMap İçinde Thread Safety'i Nasıl Sağlar?

ConcurrentHashMap, tüm haritayı kilitlemek yerine bucket-level synchronization (segmentasyon) kullanır.

Temel İlkeler:

1. Bucket Bölümleme: Harita 16 (veya daha fazla) segment'e bölünür. Her segment bağımsız olarak kilitlenir.

// ConcurrentHashMap sadece ihtiyaç duyduğu segment'i kilitler // Thread 1: Bucket 0'ı kilitler // Thread 2: Bucket 5'i kilitler (aynı anda yapabilir!)

2. CAS (Compare-and-Swap) Operasyonları: Java 8+ versiyonlarda atomik işlemler için kullanılır.

3. Null Değer Kısıtlaması: HashMap'ten farklı olarak ne key ne de value null olamaz.

Uygulamada Kullanımı:

ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>(); // Thread-safe operasyonlar map.putIfAbsent("count", 0); // Atomik map.computeIfPresent("count", (k, v) -> v + 1); // Atomik // HashMap ile bunu yaparsanız race condition oluşur!
HashMap'i multi-threaded ortamda senkronize etmek için Collections.synchronizedMap() kullanabilirsiniz, fakat ConcurrentHashMap daha performanslıdır.
ConcurrentHashMap'te iteration sırasında kilitlenme olmadığından, döngü sırasında eklenen yeni elemanlar görülmeyebilir (bu istenen davranıştır).

wait(), sleep() ve join() Arasındaki Farklar Nelerdir?
Metod Monitor Lock'u Serbest Bırakır Kullanım Amacı Uyandırılma Koşulu
wait() ✓ Evet Thread'i başka thread'in notification'ını beklemesi için uyutma notify() veya notifyAll() çağrılmasında
sleep() ✗ Hayır Thread'i belirli bir süre için uyutma Zaman dolduğunda otomatik
join() ✗ Hayır Bir thread'in diğer thread'in bitmesini beklemesi Hedef thread sonlandığında

Detaylı Örnekler:

wait() - Prodüktör/Tüketici Deseni:

synchronized void consume() { while (buffer.isEmpty()) { wait(); // Lock'u serbest bırakır, diğer thread'ler çalışabilir } buffer.remove(); } synchronized void produce() { buffer.add(item); notifyAll(); // Bekleyen thread'leri uyandır }

sleep() - Basit Gecikmeler:

for (int i = 0; i < 5; i++) { System.out.println("Countdown: " + (5 - i)); Thread.sleep(1000); // Lock'u tutmaya devam eder }

join() - Thread Sıralaması:

Thread thread1 = new Thread(() -> { System.out.println("Thread 1 çalışıyor"); }); thread1.start(); thread1.join(); // Main thread'i Thread 1'in bitmesini bekle System.out.println("Thread 1 bitti, artık main devam edebilir");

Hafızda Kalması Gereken Noktalar:

  • wait() ve notify() mutlaka synchronized blok içinde olmalı
  • sleep() thread'i kesmez, interrupt edilebilir
  • join() timeout ile kullanılabilir: thread.join(5000)

Java Class Loading Mekanizmasını Açıklayınız

Class loading, bir .class dosyasını JVM'ye yükleme ve kullanıma hazır hale getirme işlemidir. Üç aşamadan oluşur:

1. Loading (Yükleme) - Üç Class Loader Türü:

Class Loader Hiyerarşisi:

  • Bootstrap ClassLoader: Java standart kütüphaneleri (java.lang, java.util vs) yükler. JVM'nin parçasıdır.
  • Platform ClassLoader: (Java 9+) Extension ClassLoader yerine kullanılır. JDK'nın platform modülleri yükler.
  • Application ClassLoader: Uygulamanızın class'larını yükler. CLASSPATH'den bulur.

Parent Delegation: Çocuk ClassLoader'ı, kendi yüklü bulunmayan bir class için önce parent'ına sorar.

// Hangi ClassLoader bir class'ı yükledi? ClassLoader loader = String.class.getClassLoader(); System.out.println(loader); // null (Bootstrap ClassLoader gösterilmez) ClassLoader loader2 = MyClass.class.getClassLoader(); System.out.println(loader2); // sun.misc.Launcher$AppClassLoader

2. Linking (Bağlantı):

Verification: .class dosyasının formatı kontrol edilir

Preparation: Static değişkenler için bellek ayrılır

Resolution: Symbolic referanslar gerçek memory adreslerine dönüştürülür

3. Initialization (Başlatma):

Static bloklar ve static değişkenler ilk değerlendirilir.

public class MyClass { static { System.out.println("Initialization çalıştı!"); // Class ilk kez yüklenince çalışır } static int count = 10; }
Custom ClassLoader'ları plugin sistemleri ve dinamik sınıf yüklemesi için kullanabilirsiniz.

equals() ve == Arasındaki Fark Nedir?
Operatör Kıyaslama Türü Kullanım
== Referans karşılaştırması Primitive'ler ve object referansı
equals() Mantıksal eşitlik Obje içeriğinin karşılaştırılması

Pratik Örnek:

String s1 = new String("Java"); String s2 = new String("Java"); System.out.println(s1 == s2); // false (farklı obje referansları) System.out.println(s1.equals(s2)); // true (aynı içerik) // Primitive'ler için: int a = 10; int b = 10; System.out.println(a == b); // true (değerler aynı)

equals() Kendi Sınıfımızda Implement Etme:

public class User { String email; int age; @Override public boolean equals(Object obj) { if (this == obj) return true; if (obj == null) return false; if (!(obj instanceof User)) return false; User other = (User) obj; return this.email.equals(other.email) && this.age == other.age; } @Override public int hashCode() { // hashCode'u da override etmemiz GEREKLI! return Objects.hash(email, age); } }
equals() override ettiğinizde mutlaka hashCode() da override edin! Aksi takdirde HashMap/HashSet'te sorun yaşarsınız.

hashCode() - equals() Kuralı:

  • Eğer equals() true dönerse, hashCode() aynı değeri döndürmelidir
  • Eğer equals() false dönerse, hashCode() farklı değer döndürebilir (ama aynı da dönebilir)
Soru 5:
JVM'de Garbage Collection Nasıl Çalışır?

Temel Kavram:

Garbage Collection, artık kullanılmayan nesneleri otomatik olarak belleğinden silen JVM özelliğidir. Reachability (ulaşılabilirlik) üzerine kuruludur.

Heap Yapısı - Generational GC:

Nesiller (Generations):

  • Young Generation: Yeni yaratılan nesnelerin bulunduğu alan. Hızlı ölür.
  • Old Generation: Young generation'dan "yaşa çıkan" nesneler buraya taşınır.
  • Permanent Generation / Metaspace: Class metadata ve String pool

GC İşlem Adımları:

1. Mark Phase: Hangi nesnelerin ulaşılabilir olduğunu işaretler 2. Sweep Phase: İşaretlenmeyen nesneleri siler 3. Compact Phase: Belleği organize eder (bazı collector'larda)

GC Türleri:

Minor GC: Young generation'ı temizler (hızlı, sık)

Major GC: Old generation'ı temizler (yavaş, nadir)

Full GC: Tüm heap'ı temizler (çok yavaş, ender)

Modern Collector: G1 GC

G1 GC heap'ı bölgelere (region) ayırır ve region-by-region işlem yapar, daha düşük pause time sağlar.

// GC log'larını görmek için (production'da kullanmayın): // java -Xlog:gc -Xmx1G MyApp // GC pause'ları azaltmak için: // java -XX:+UseG1GC -XX:MaxGCPauseMillis=200 MyApp
Memory leak: Hala referanslı olan ama artık kullanılmayan nesneler GC'den kurtulmazlar. Statik koleksiyonlara sınırsız ekleme yaparsanız memory leak oluşur.

volatile Nedir?

Volatile bir değişkenin her okuma/yazması ana belleğe gider, CPU cache'ine değil. Böylece diğer thread'ler en güncel değeri görür.

private volatile boolean flag = false; // Visibility garantili // Thread 1 flag = true; // Thread 2 (hemen görür) while (!flag) { // bekleme }

volatile'in Sınırlaması:

private volatile int count = 0; // BU PROBLEM: count++ atomik değildir! // 1. Mevcut değeri oku (10) // 2. Bir ekle (11) // 3. Yaz (11) // İkinci thread araya girerse: her iki thread'in increment'i kaybolabilir // Çözüm: private volatile int count = 0; synchronized void increment() { count++; // Artık atomik }

synchronized Ne Yapar?

public synchronized void transfer(Account from, Account to, int amount) { if (from.balance >= amount) { from.balance -= amount; // Critical section başlangıcı to.balance += amount; // Critical section sonu // Başka thread'ler bu süre boyunca bu metodu çağıramaz } }
Baskı düşük ise volatile, baskı yüksek ise AtomicInteger veya ReadWriteLock kullanın.
Soru 7:
Shallow Copy vs Deep Copy - Fark Nedir?

Shallow Copy (Yüzeysel Kopya):

Sadece referansları kopyalanır, nested obje'ler paylaşılır.

public class Person { String name; Address address; // Nested obje } Person original = new Person(); original.name = "Ali"; original.address = new Address(); original.address.city = "İstanbul"; // Shallow copy Person copy = original; // YANLIŞ: Aynı obje referansı copy.address.city = "Ankara"; System.out.println(original.address.city); // "Ankara" - Original da değişti!

Deep Copy (Derin Kopya):

Nested obje'ler de kopyalanır, tamamen bağımsız nesneler oluşur.

public class Person implements Cloneable { String name; Address address; @Override public Person clone() throws CloneNotSupportedException { Person copy = (Person) super.clone(); // Nested objeyi de kopyala copy.address = new Address(); copy.address.city = address.city; return copy; } } Person original = new Person(); Person deepCopy = original.clone(); deepCopy.address.city = "Ankara"; System.out.println(original.address.city); // "İstanbul" - Original değişmedi

Ne Zaman Kullanmalı?

  • Shallow Copy: Immutable nested obje'ler varsa (String, Integer)
  • Deep Copy: Mutable nested obje'ler varsa (List, Map, custom obje'ler)
En kolay yol: Jackson kütüphanesini kullanarak JSON'a çevir, geri dönüştür (deep copy garantili).

Checked vs Unchecked Exceptions - Fark Nedir?
Tür Parent Class Compile-Time Check Örnek
Checked Exception Exception ✓ Evet (zorunlu handle etme) IOException, SQLException
Unchecked Exception RuntimeException ✗ Hayır (opsiyonel) NullPointerException, ArrayIndexOutOfBoundsException

Checked Exception Örneği:

public void readFile(String filename) throws IOException { // IOException checked exception'dır // Ya try-catch ya da throws kullanmalısınız FileReader file = new FileReader(filename); } // Çağrıldığında try { readFile("data.txt"); } catch (IOException e) { e.printStackTrace(); }

Unchecked Exception Örneği:

public void divide(int a, int b) { // ArithmeticException unchecked // Compile error yoktur, ama runtime'da çıkabilir return a / b; // b == 0 ise çöker }

Uygulamada Seçim:

// Checked Exception: Beklenen dış hatalar public User getUserFromDatabase(int id) throws SQLException { // Veritabanı bağlantısı başarısız olabilir } // Unchecked Exception: Programcı hatası (invalid parameter) public void setAge(int age) { if (age < 0) { throw new IllegalArgumentException("Yaş negatif olamaz"); } this.age = age; }
Modern API'ler daha çok unchecked exception'lar tercih eder (try-catch'ten kurtulmak için). Checked exception'lar sadece gerçekten recover edilebilir durumlarda kullanın.

ThreadLocal Nedir?

Her thread'in kendi değişken kopysını tutmasını sağlayan bir veri yapısıdır. Bir thread başka thread'in değerini göremez.

Yüksek Volume Ödeme Sisteminde Thread-Safe Hesap Bakiyesi Güncellemesi

Problem:

İki thread aynı anda son 100 TL'yi çekmeye çalışıyor. İkisinin de başarılı olması engellenmeli.

Çözüm 1: Pessimistic Locking (Kilitleyici Yöntem)

@Transactional public boolean withdraw(Long accountId, BigDecimal amount) { // SELECT ... FOR UPDATE - veritabanı satırı kilitler Account account = accountRepo.findByIdWithLock(accountId); if (account.getBalance().compareTo(amount) >= 0) { account.setBalance(account.getBalance().subtract(amount)); accountRepo.save(account); return true; } return false; }

Çözüm 2: Optimistic Locking (Versiyon Kontrolü)

@Entity public class Account { @Id Long id; BigDecimal balance; @Version Long version; // Her güncelleme artırılır } @Transactional public void withdraw(Long accountId, BigDecimal amount) { Account account = accountRepo.findById(accountId).get(); if (account.getBalance().compareTo(amount) >= 0) { account.setBalance(account.getBalance().subtract(amount)); // Eğer version değişmişse: OptimisticLockingFailureException accountRepo.save(account); } } // Çağrıcı tarafında retry: int retry = 3; while (retry > 0) { try { withdraw(accountId, amount); break; } catch (OptimisticLockingFailureException e) { retry--; if (retry == 0) throw e; Thread.sleep(100); // Geri kalan retry'lar için bekleme } }

Çözüm 3: Atomik SQL Güncelleme (En İyi)

@Transactional public void withdraw(Long accountId, BigDecimal amount) { int updated = accountRepo.decrementBalanceIfSufficient(accountId, amount); if (updated == 0) { throw new InsufficientFundsException(); } } // Repository @Query(""" UPDATE Account a SET a.balance = a.balance - :amount WHERE a.id = :id AND a.balance >= :amount """) @Modifying int decrementBalanceIfSufficient( @Param("id") Long id, @Param("amount") BigDecimal amount );

Ek Güvenlik Mekanizmaları:

Idempotency Anahtarı:

  • Her işlem için UUID oluştur (client tarafından)
  • Veritabanına depo et
  • Aynı UUID ile tekrar gelirse önceki sonucu dön
@Table(uniqueConstraints = @UniqueConstraint(columnNames = "idempotencyKey")) public class Transaction { @Id Long id; String idempotencyKey; // Unique! BigDecimal amount; Status status; } // İlk istek transactionRepo.findByIdempotencyKey("abc-123-def"); // Bulunamadı, işlem yap // Tekrar istek (same idempotencyKey) transactionRepo.findByIdempotencyKey("abc-123-def"); // Bulundu, sonucu dön
Çoklu instance ortamında: pessimistic locking veritabanı seviyesinde çalışır, bu da güvendir. Optimistic locking retry gerektir fakat throughput daha yüksektir.

Soru 12:
Aspect-Oriented Programming (AOP) Nedir?

AOP Nedir?

Cross-cutting concerns'leri (logging, security, transaction) ana business logic'ten ayırmaya yarayan teknik.

AOP Temel Terimleri:

AOP Sözlüğü:

  • Aspect: AOP modülü (class)
  • Join Point: Advice uygulanabilen kod noktası (method call, exception)
  • Pointcut: Join point'leri seçen expression (@Pointcut)
  • Advice: Pointcut'a yapılacak işlem (Before, After, Around)

Pratik Örnek: Logging Aspect

@Aspect @Component public class LoggingAspect { @Pointcut("execution(* com.example.service.*.*(..))") public void serviceLayer() {} @Before("serviceLayer()") public void logBefore(JoinPoint joinPoint) { String methodName = joinPoint.getSignature().getName(); logger.info("Metod çağrıldı: " + methodName); } @After("serviceLayer()") public void logAfter(JoinPoint joinPoint) { logger.info("Metod tamamlandı: " + joinPoint.getSignature().getName()); } @Around("serviceLayer()") public Object logAround(ProceedingJoinPoint pjp) throws Throwable { long start = System.currentTimeMillis(); Object result = pjp.proceed(); // Asıl metod çalışır long duration = System.currentTimeMillis() - start; logger.info("Süre: " + duration + "ms"); return result; } }

Annotation-Based Pointcut Örneği:

// 1. Custom annotation tanımla @Target(ElementType.METHOD) @Retention(RetentionPolicy.RUNTIME) public @interface LogExecution { } // 2. Aspect'i yazıyor @Aspect @Component public class ExecutionLogAspect { @Around("@annotation(LogExecution)") public Object log(ProceedingJoinPoint pjp) throws Throwable { System.out.println("START: " + pjp.getSignature()); Object result = pjp.proceed(); System.out.println("END: " + pjp.getSignature()); return result; } } // 3. Service'te kullan @Service public class UserService { @LogExecution // Bu metod log'lanacak public void createUser(User user) { // business logic } }

Self-Invocation Problemi:

@Service public class PaymentService { @Transactional public void pay(Order order) { deductBalance(order.getAmount()); // Aspect çalışmaz! } @Transactional private void deductBalance(BigDecimal amount) { // ... } } // Sorun: pay() içinden deductBalance() çağrıldığında, // proxy'den geçmediği için Aspect uygulanmaz. // Çözüm 1: Inject ApplicationContext ve bean'i çağır // Çözüm 2: deductBalance'ı başka bir service'e taşı // Çözüm 3: public yap (iyi practice değildir)
Spring AOP proxy-based'dir, yani reflection kullanır. Buna rağmen hızlı ama tüm reflection sınırlamaları vardır (private metod, constructor vs.)
AspectJ kullanarak bytecode manipulation yapabilirsiniz (constructor, private metod vs. için), ancak setup daha karmaşıktır.
Soru 13:
Spring Circular Dependencies Nasıl Yönetir?

Circular Dependency Nedir?

A bean'i B bean'e, B bean'i ise A bean'e bağımlı olduğunda meydana gelir.

Durum 1: Constructor Injection - BAŞARISIZ

@Service public class ServiceA { private ServiceB serviceB; // Constructor injection public ServiceA(ServiceB serviceB) { // ❌ Circular! this.serviceB = serviceB; } } @Service public class ServiceB { private ServiceA serviceA; public ServiceB(ServiceA serviceA) { // ❌ Circular! this.serviceA = serviceA; } } // Başlarken: UnsatisfiedDependencyException!

Durum 2: Setter/Field Injection - BAŞARILI (Dikkatli)

@Service public class ServiceA { @Autowired // ✓ Setter/field injection private ServiceB serviceB; } @Service public class ServiceB { @Autowired // ✓ Setter/field injection private ServiceA serviceA; } // Spring bunu çözer (early bean reference'lar sayesinde) // Ancak service'ler başlangıçta null olabilir!

Çözüm 1: Architecture Tasarımını Değiştir

// Sorunlu tasarım: // ServiceA -> ServiceB -> ServiceA // Çözüm: Yeni service ekle @Service public class ServiceC { @Autowired private ServiceA serviceA; @Autowired private ServiceB serviceB; public void doSomething() { serviceA.doA(); serviceB.doB(); } }

Çözüm 2: Events Kullan (Decoupled)

// Event tanımı public class OrderCreatedEvent { private Order order; // getter/setter } // ServiceA - event yayınlayan @Service public class ServiceA { @Autowired private ApplicationEventPublisher eventPublisher; public void createOrder(Order order) { eventPublisher.publishEvent(new OrderCreatedEvent(order)); } } // ServiceB - event dinleyen (bağımlı değil!) @Service public class ServiceB { @EventListener public void handleOrderCreated(OrderCreatedEvent event) { // Order işleme } } // Hiç circular dependency yok!

Çözüm 3: Lazy Initialization

@Service public class ServiceA { @Autowired @Lazy private ServiceB serviceB; // İhtiyaç duyulduğunda başlatılır }
En iyi uygulama: Circular dependency'i tasarımdan çıkarmaktır. Event-driven yaklaşımı kullanın.

JWT ve OAuth 2.0 ile REST API'ları Nasıl Secure Yaparım?

Authentication vs Authorization

Authentication: "Siz kimsiniz?" (giriş yapan kişi)

Authorization: "Ne yapabilirsiniz?" (izin kontrolü)

JWT (JSON Web Token) Nedir?

İmzalı bir token, kendi içinde kullanıcı bilgisi taşır. Server-side session gerektirmez.

// JWT yapısı: Header.Payload.Signature // eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhbGkiLCJpYXQiOjE2MzQ3NTY4MDB9.xxx // Header: {"alg":"HS256"} // Payload: {"sub":"ali","iat":1634756800,"exp":1634760400} // Signature: HMAC-SHA256(Header.Payload, secret_key)

OAuth 2.0 Authorization Code Flow

1. User: Uygulamaya giriş için OAuth provider'a yönlendir 2. Provider: User login yap, permission sor 3. Provider: Authorization code gönder 4. App Backend: Authorization code + client_secret ile token iste 5. Provider: Access token ve refresh token gönder 6. App Backend: Access token ile API çağrılarını yap

First-Level Cache vs. Second-Level Cache

Hibernate, tekrarlanan veritabanı erişimlerini azaltmak için önbellekleme mekanizmaları sağlar.

  • First-level cache (Birinci Seviye Önbellek): Kalıcılık bağlamıyla ilişkilidir (Persistence Context - Session veya EntityManager) ve genellikle varsayılan olarak etkindir. Her bir oturum için geçerlidir.
  • Second-level cache (İkinci Seviye Önbellek): Yapılandırıldığında ve bir önbellek sağlayıcı tarafından desteklendiğinde kalıcılık bağlamları arasında (farklı oturumlar arasında) paylaşılır.

Kapsamlarını, geçersiz kılma mekanizmalarını, tutarlılık sorunlarını ve varlıkları önbelleğe almanın ne zaman uygun olduğunu açıklayın. Ayrıca varlık önbellekleme ile sorgu önbellekleme arasındaki farkı da belirtin.

First-Level Cache (Oturum Önbelleği):

  • Kapsam: Her Session veya EntityManager nesnesi kendi birinci seviye önbelleğine sahiptir. Bu önbellek, bir işlem süresince geçerlidir.
  • Çalışma Prensibi: Bir varlık (entity) veritabanından yüklendiğinde veya kaydedildiğinde, bu önbelleğe alınır. Aynı oturum içinde aynı varlık tekrar istendiğinde, veritabanına gitmek yerine önbellekten döner.
  • Thread Güvenliği: Thread güvenli değildir, çünkü her oturum kendi önbelleğine sahiptir ve farklı thread'ler farklı oturumlar kullanmalıdır.
  • Kullanım: Genellikle otomatik olarak yönetilir ve devre dışı bırakılamaz.

Second-Level Cache (Paylaşılan Önbellek):

  • Kapsam: SessionFactory veya EntityManagerFactory seviyesindedir, yani tüm uygulamadaki oturumlar (session'lar) tarafından paylaşılır. Farklı oturumlar ve thread'ler arasında geçerlidir.
  • Çalışma Prensibi: Varlık verileri veritabanından yüklendiğinde, ikinci seviye önbelleğe alınır. Başka bir oturumda aynı varlık istendiğinde, veritabanına gitmeden önce ikinci seviye önbelleğe bakılır.
  • Thread Güvenliği: Thread güvenlidir ve eş zamanlı erişim sorunlarını yönetir.
  • Kullanım: Varsayılan olarak kapalıdır. EhCache, Redis, Infinispan gibi harici önbellek sağlayıcıları ile etkinleştirilmelidir. Performans artışı sağlayabilir ancak tutarlılık yönetimi karmaşıklığını artırır.

Varlık Önbellekleme (Entity Caching) vs. Sorgu Önbellekleme (Query Caching):

  • Varlık Önbellekleme: Tek tek varlıkları (User, Product vb.) önbelleğe alır. @Cacheable gibi anotasyonlarla veya yapılandırma ile etkinleştirilir.
  • Sorgu Önbellekleme: Belirli bir sorgunun sonuçlarını (sorgunun kendisi ve parametreleri) önbelleğe alır. Aynı sorgu tekrar çalıştırıldığında, veritabanına gitmeden önbelleğe alınmış sonuçları döndürür. Varlıkları değil, sorgu sonuç listelerini önbelleğe alır. Genellikle query.setCacheable(true) ile etkinleştirilir.

Optimistic Locking vs. Pessimistic Locking in JPA

Her iki yaklaşım da verileri çakışan eş zamanlı güncellemelerden korumaya yardımcı olur.

  • Optimistic Locking (İyimser Kilitleme): Çakışan değişiklikleri tespit etmek için genellikle @Version ile açıklama eklenen bir sürüm alanı (version field) kullanır.
  • Pessimistic Locking (Kötümser Kilitleme): İşlem aktifken rekabet eden işlemleri kısıtlamak için veritabanı kilitleri edinir.

Düşük çekişmeli güncellemeler ile yüksek çekişmeli envanter veya finansal kayıtlar için hangi yaklaşımı seçeceğinizi tartışın. Kilit zaman aşımı (lock timeout) ve işlem yeniden denemelerinin (transaction retries) nasıl ele alınması gerektiğini açıklayın.

Optimistic Locking (İyimser Kilitleme):

  • Prensip: Çakışmaların nadiren meydana geldiği varsayımına dayanır. Kaydı okurken herhangi bir kilit uygulamaz. Kayıt güncellenirken, okunduğundan bu yana değişip değişmediğini kontrol etmek için bir sürüm numarası veya zaman damgası gibi bir mekanizma kullanır. Eğer değişmişse, güncelleme reddedilir ve bir istisna fırlatılır (OptimisticLockException).
  • Uygulama: JPA'da bir varlık alanına @Version anotasyonu eklenerek kolayca uygulanır (örneğin, private int version; veya private LocalDateTime lastUpdated;). Hibernate veya JPA sağlayıcısı, bu sürüm alanını otomatik olarak yönetir.
  • Avantajlar: Yüksek eş zamanlılık sağlar, veritabanı kaynaklarını daha az kullanır, deadlock riski düşüktür.
  • Dezavantajlar: Çakışma durumunda işlemin yeniden denenmesi gerekir. Yüksek çekişme durumlarında sık sık yeniden deneme gerektirebilir ve performansı düşürebilir.
  • Kullanım Alanları: Düşük ila orta düzeyde veri çekişmesi olan senaryolar (örneğin, kullanıcı profili güncellemeleri, makale düzenlemeleri).

Pessimistic Locking (Kötümser Kilitleme):

  • Prensip: Çakışmaların sıkça meydana geldiği varsayımına dayanır. Bir işlem bir kaydı okuduğunda, başka hiçbir işlemin o kaydı değiştirmesini engellemek için doğrudan veritabanı kilidi uygular. Kilit serbest bırakılana kadar diğer işlemler bekler veya hata alır.
  • Uygulama: JPA'da EntityManager.lock() metodu veya sorgularda LockModeType kullanılarak uygulanır (örneğin, LockModeType.PESSIMISTIC_WRITE). Bu, veritabanında SELECT ... FOR UPDATE gibi kilit ifadeleri tetikler.
  • Avantajlar: Veri tutarlılığını garanti eder, çakışma yönetimi basittir (bekleme veya hata).
  • Dezavantajlar: Eş zamanlılığı azaltır, deadlock riski daha yüksektir, veritabanı kaynaklarını daha yoğun kullanır.
  • Kullanım Alanları: Yüksek çekişmeli senaryolar, kritik finansal işlemler, envanter yönetimi gibi veri bütünlüğünün mutlak öncelik olduğu yerler.

Kilit Zaman Aşımı ve İşlem Yeniden Denemeleri:

  • Optimistic Locking İçin: OptimisticLockException alındığında, istemcinin işlemi yeniden denemesi veya kullanıcıya bir hata mesajı göstermesi gerekir. Yeniden denemeler genellikle belirli bir strateji (örneğin, üstel geri çekilme - exponential backoff) ile yapılır.
  • Pessimistic Locking İçin: Veritabanı kilitleri nedeniyle bir işlem kilit için uzun süre beklerse, bir kilit zaman aşımı (lock timeout) hatası alabilir (örneğin, PessimisticLockException). Bu durumda da işlem yeniden denenebilir veya kullanıcıya bilgi verilebilir. Kilit süreleri ve veritabanı ayarları önemlidir.

What Is Dirty Checking in Hibernate?

Dirty checking (Kirli Kontrol), Hibernate'in yönetilen varlıklar (managed entities) üzerindeki değişiklikleri tespit etmesini ve bu değişiklikleri bir flush (bellekteki değişiklikleri veritabanına yazma) sırasında veritabanı ile senkronize etmesini sağlar.

Kalıcılık bağlamının (persistence context) varlık durumunu nasıl izlediğini ve yönetilen bir varlığın güncellemeleri için açık bir save() çağrısının neden her zaman gerekli olmadığını açıklayın. Ayrıca işlem sınırlarını (transaction boundaries), flush davranışını ve gereksiz varlık yüklemenin performansı nasıl etkileyebileceğini tartışın.

Dirty Checking Nedir?

Dirty Checking, Hibernate'in en güçlü özelliklerinden biridir ve performans optimizasyonu sağlar. Bir varlık (entity) Persistent (kalıcı) durumdayken (yani, bir Hibernate Session veya JPA EntityManager tarafından yönetiliyorken) yapılan değişiklikleri otomatik olarak algılar ve veritabanına yansıtır.

  1. Bir varlık veritabanından yüklendiğinde, Hibernate bu varlığın başlangıç durumunu (snapshot) kalıcılık bağlamında saklar.
  2. Varlık üzerinde yapılan herhangi bir değişiklik (setter metotları aracılığıyla alan değerlerinin değiştirilmesi) doğrudan veritabanına yansıtılmaz.
  3. İşlem sonlandığında (commit edildiğinde) veya belirli bir flush olayı tetiklendiğinde (örneğin, bir sorgu çalıştırıldığında), Hibernate mevcut varlık durumu ile başlangıç durumunu karşılaştırır.
  4. Eğer bir fark (yani "kirli" bir varlık) tespit edilirse, Hibernate otomatik olarak ilgili UPDATE sorgularını oluşturur ve veritabanında çalıştırır. Bu mekanizmaya Dirty Checking denir.

Neden Açık Bir save() Gerekli Değildir?

Yönetilen (Persistent) bir varlık üzerinde değişiklik yaptığınızda, Hibernate zaten bu varlığın takibini yaptığı için save(), update() veya merge() gibi explicit metotları çağırmanıza gerek yoktur. Bu, Hibernate'in "write-behind" (arkaplan yazma) veya "automatic dirty checking" özelliği sayesinde olur. Değişiklikler, işlem bittiğinde veya flush edildiğinde otomatik olarak veritabanına gönderilir.


Session session = sessionFactory.openSession();
Transaction tx = session.beginTransaction();

User user = session.get(User.class, 1L); // Varlık yüklenir ve persistent hale gelir
user.setEmail("new.email@example.com"); // Varlık üzerinde değişiklik yapılır

// session.update(user); // Gerek yok! Hibernate otomatik olarak değişiklikleri algılar.

tx.commit(); // Flush tetiklenir, UPDATE sorgusu çalışır
session.close();

İşlem Sınırları ve Flush Davranışı:

  • İşlem Sınırları: Dirty checking ve flush işlemleri genellikle bir veritabanı işlemi (transaction) içinde gerçekleşir. İşlem başladığında bir Session açılır, işlem bittiğinde (commit veya rollback) Session kapanır.
  • Flush Davranışı: Değişikliklerin veritabanına ne zaman yazılacağını belirler. Varsayılan olarak, Hibernate aşağıdaki durumlarda otomatik olarak bir flush yapar:
    • İşlem commit edildiğinde.
    • Bir sorgu çalıştırılmadan önce (bu sorgu önbellekteki kirli verilerden etkilenebileceği için).
    • Session.flush() açıkça çağrıldığında.

Gereksiz Varlık Yüklemenin Performansa Etkisi:

Eğer bir varlığı sadece okuyup, üzerinde hiçbir değişiklik yapmayacaksanız, onu Persistent duruma getirmek ve Dirty Checking mekanizmasını çalıştırmak gereksiz yere kaynak tüketimine neden olabilir. Read-only işlemler için varlıkları sadece okuyup kapatmak veya Hibernate'i read-only modda kullanmak (session.setDefaultReadOnly(true)) performansı artırabilir, çünkü bu durumda başlangıç snapshot'ı alınmaz ve değişiklik takibi yapılmaz.

Soru 23:
Explain the Hibernate Entity Lifecycle States.

Dört yaygın olarak tartışılan varlık durumunu anlayın:

  • Transient (Geçici): Kalıcılık bağlamıyla ilişkili olmayan, yeni oluşturulmuş bir nesne.
  • Persistent (Kalıcı): Mevcut kalıcılık bağlamı tarafından yönetilen bir varlık.
  • Detached (Ayrılmış): Daha önce yönetilmiş ancak artık o bağlamla ilişkili olmayan bir varlık.
  • Removed (Kaldırılmış): Silinmek üzere işaretlenmiş, yönetilen bir varlık.

persist(), merge() ve remove() gibi işlemlerin varlık durumunu nasıl etkilediğini açıklayın.

Hibernate/JPA'daki bir varlık, yaşam döngüsü boyunca farklı durumlardan geçer. Bu durumları anlamak, varlıkların veritabanıyla nasıl etkileşim kurduğunu kavramak için kritik öneme sahiptir.

1. Transient (Geçici) Durum:

  • Tanım: Bir varlık nesnesi Java kodu içinde new anahtar kelimesiyle oluşturulduğunda ve henüz bir Hibernate Session veya JPA EntityManager ile ilişkilendirilmediğinde bu durumdadır.
  • Özellikler:
    • Henüz bir veritabanı kimliği (ID) atanmamıştır (eğer ID üretimi stratejisi Hibernate/JPA tarafından yönetiliyorsa).
    • Bellekte bulunur ancak veritabanında karşılığı yoktur.
    • Hibernate/JPA tarafından herhangi bir şekilde yönetilmez (dirty checking, caching vb. uygulanmaz).
  • Örnek: User newUser = new User("John Doe", "john.doe@example.com");
  • Geçiş:
    • persist() veya save() çağrıldığında Persistent duruma geçer.

2. Persistent (Kalıcı) Durum:

  • Tanım: Bir varlık nesnesi, bir Hibernate Session veya JPA EntityManager tarafından yönetildiğinde bu durumdadır.
  • Özellikler:
    • Veritabanında karşılığı vardır ve bir kimliği (ID) bulunur.
    • Kalıcılık bağlamı (Persistence Context) tarafından izlenir (dirty checking yapılır).
    • Kalıcılık bağlamındaki değişiklikler veritabanına otomatik olarak senkronize edilir (flush mekanizması).
  • Örnekler:
    • session.persist(newUser); (Transient'ten Persistent'a geçiş)
    • User existingUser = session.get(User.class, 1L); (Veritabanından yüklenen varlık)
  • Geçiş:
    • session.evict(user); veya session.clear(); çağrıldığında Detached duruma geçer.
    • session.close(); veya session.clear(); çağrıldığında (tüm oturum kapanırsa) tüm yönetilen varlıklar Detached duruma geçer.
    • session.remove(user); çağrıldığında Removed duruma geçer.

3. Detached (Ayrılmış) Durum:

  • Tanım: Daha önce Persistent durumda olan ancak artık bir kalıcılık bağlamı tarafından yönetilmeyen bir varlık bu durumdadır.
  • Özellikler:
    • Hala bir veritabanı kimliğine (ID) sahiptir.
    • Bellekte bulunur, ancak üzerinde yapılan değişiklikler otomatik olarak veritabanına yansıtılmaz.
    • Dirty checking ve diğer Hibernate/JPA yönetimi durmuştur.
  • Örnek: session.close(); çağrıldıktan sonra, oturumdan yüklenmiş olan varlıklar Detached hale gelir.
  • Geçiş:
    • session.merge(detachedUser); çağrıldığında tekrar Persistent duruma geçebilir.
    • Yeni bir Session içinde session.update(detachedUser); (Hibernate spesifik) çağrıldığında da Persistent duruma geçer.

4. Removed (Kaldırılmış) Durum:

  • Tanım: Persistent durumda iken silinmek üzere işaretlenmiş bir varlık bu durumdadır.
  • Özellikler:
    • remove() çağrıldığında hemen silinmez, veritabanından silinmek üzere işaretlenir.
    • İşlem commit edildiğinde veya flush gerçekleştiğinde, veritabanından kalıcı olarak silinir.
    • Silindikten sonra teknik olarak Transient duruma geri döner, çünkü artık veritabanında karşılığı yoktur ve bir ID ile ilişkilendirilemez.
  • Örnek: session.remove(existingUser);
  • Geçiş:
    • İşlem commit edildiğinde veritabanından silinir ve bellekteki nesne Transient gibi davranır (artık bir veritabanı kaydını temsil etmez).
    • İşlem geri alınırsa (rollback), varlık Persistent durumuna geri döner.

persist(), merge(), remove() Etkileri:

  • persist(entity): Bir Transient varlığı Persistent duruma geçirir. Veritabanına yeni bir kayıt ekler.
  • merge(entity): Bir Detached varlığı tekrar Persistent duruma getirir veya bir Transient varlığı veritabanında kaydeder. Mevcut bir ID varsa günceller, yoksa yeni bir kayıt oluşturur ve yönetilen bir kopyasını döndürür. Orijinal nesne (merge edilen) Detached kalır.
  • remove(entity): Bir Persistent varlığı Removed duruma geçirir. İşlem commit edildiğinde veritabanından silinir.
Soru 24:
How Would You Prevent Inconsistent Stock Updates When Multiple Users Purchase the Same Product?

Aynı anda birden fazla kullanıcının aynı ürünü satın almaya çalıştığı bir senaryoyu düşünün.

Olası çözümler şunları içerebilir:

  • @Version ile iyimser kilitleme (optimistic locking).
  • JPA kilit modlarını kullanarak kötümser kilitleme (pessimistic locking).
  • Atomik koşullu SQL güncellemeleri.
  • Veritabanı kısıtlamaları ve işlem yönetimi.
  • İyimser kilitleme başarısız olduğunda kontrollü yeniden denemeler.

Çekişme, verim ve iş gereksinimlerine göre bir yaklaşımı nasıl seçeceğinizi açıklayın. Çözümünüz, farklı uygulama örnekleri işlemleri yapsa bile aşırı satışı (overselling) engellemelidir.

Birden fazla kullanıcının aynı anda aynı ürünü satın almaya çalıştığı ve stok güncellemelerinin tutarsız olmasına yol açabilecek bir senaryo, dağıtık sistemlerde sıkça karşılaşılan kritik bir problemdir. Çözüm, iş gereksinimlerine (veri tutarlılığı seviyesi, eş zamanlılık ihtiyacı) ve sistemin mimarisine (tekil uygulama mı, dağıtık mikroservisler mi) bağlı olarak değişir.

Olası Yaklaşımlar ve Seçim Kriterleri:

1. Optimistic Locking (İyimser Kilitleme) ile @Version:

  • Prensip: Her ürün stok kaydına bir sürüm numarası (@Version anotasyonu ile) eklenir. Bir kullanıcı ürünü satın almak için stok miktarını okuduğunda, bu sürüm numarasını da alır. Stok güncellemesi yapılırken (UPDATE sorgusu), veritabanında bu sürüm numarasının değişip değişmediği kontrol edilir. Eğer değişmişse, başka bir işlemin araya girip stoğu güncellediği anlamına gelir ve işlem başarısız olur (OptimisticLockException).
  • Uygulama: 
    
@Entity
public class Product {
    @Id
    private Long id;
    private String name;
    private int stock;
    @Version
    private int version; // Optimistic locking için
    // Getters and setters
}

// İşlem içinde:
Product product = productRepository.findById(productId).orElseThrow(...);
if (product.getStock() >= quantity) {
    product.setStock(product.getStock() - quantity);
    productRepository.save(product); // @Version kontrolü burada yapılır
} else {
    // Stok yetersiz
}
  • Avantajlar: Yüksek eş zamanlılık sağlar, veritabanı kilitlerine ihtiyaç duymaz, deadlock riski düşüktür.
  • Dezavantajlar: Çakışma durumunda işlem yeniden denenmelidir. Yeniden deneme mekanizmaları (üstel geri çekilme ile) istemci tarafında veya servis tarafında uygulanmalıdır. Yüksek çekişmede sık yeniden denemeler performans sorunlarına yol açabilir.
  • Seçim Kriteri: Çakışmaların nispeten nadir olduğu ve işlemin yeniden denenebileceği durumlar için idealdir. Dağıtık ortamlarda, aynı anda birden fazla uygulama örneğinin aynı stoğu güncellemeyi denemesi durumunda da çalışır.

2. Pessimistic Locking (Kötümser Kilitleme) ile JPA Lock Modları:

  • Prensip: Bir işlem stok kaydını güncellemeyi hedeflediğinde, o kayıt üzerinde özel bir veritabanı kilidi (FOR UPDATE gibi) uygular. Diğer işlemler, bu kilit serbest bırakılana kadar beklemek zorunda kalır.
  • Uygulama: JPA'da sorgularda LockModeType.PESSIMISTIC_WRITE kullanılarak uygulanır. 
    
@Transactional
public Product purchaseProductPessimistic(Long productId, int quantity) {
    Product product = entityManager.find(Product.class, productId, LockModeType.PESSIMISTIC_WRITE);
    if (product.getStock() >= quantity) {
        product.setStock(product.getStock() - quantity);
        // entityManager.merge(product); // Değişiklikler otomatik algılanır
        return product;
    } else {
        throw new InsufficientStockException("Stok yetersiz.");
    }
}
  • Avantajlar: Veri tutarlılığını garanti eder, çakışma durumlarında beklemeyi veya hatayı net bir şekilde yönetir.
  • Dezavantajlar: Eş zamanlılığı azaltır, veritabanı kilitleri nedeniyle deadlock riski artar, performans düşüşlerine yol açabilir, kilit zaman aşımı (lock timeout) yönetimi gerektirir.
  • Seçim Kriteri: Yüksek çekişmeli durumlarda, veri tutarlılığının mutlak öncelik olduğu ve eş zamanlılıkta hafif bir düşüşün kabul edilebilir olduğu senaryolar (örneğin, finansal işlemler, kritik envanter güncellemeleri). Dağıtık ortamlarda, veritabanı kilitleri farklı uygulama örneklerinden gelen işlemleri koordine edebilir.

3. Atomik Koşullu SQL Güncellemeleri:

  • Prensip: Stok güncellemesini tek bir atomik SQL sorgusu içinde gerçekleştirir. Bu sorgu, stok seviyesini kontrol eder ve aynı anda günceller. 
    
UPDATE products
SET stock = stock - ?
WHERE id = ? AND stock >= ?;
    Bu sorgu, sadece stock >= ? koşulu sağlandığında güncelleme yapar ve etkilenen satır sayısını döndürür. Eğer 0 satır etkilenirse, stok yetersiz demektir.
  • Avantajlar: Çok yüksek performans, doğrudan veritabanı tarafından yönetilen atomiklik, kilit mekanizmalarına göre daha hafif. Dağıtık ortamlarda bile tutarlılık sağlar, çünkü veritabanı işlemleri atomiktir.
  • Dezavantajlar: JPA/Hibernate'in otomatik nesne yönetimi modelinden biraz uzaklaşır, native SQL veya JPA'nın @Query anotasyonu ile daha dikkatli kullanım gerektirir.
  • Seçim Kriteri: Çok yüksek hacimli ve çekişmeli stok güncellemeleri için mükemmel bir çözümdür. Doğrudan veritabanı seviyesinde atomiklik sağladığı için en güvenilir yaklaşımlardan biridir.

4. Veritabanı Kısıtlamaları ve İşlem Yönetimi:

  • Prensip: Stok miktarının negatif olmamasını sağlamak için veritabanında CHECK kısıtlamaları kullanılabilir. Ancak bu, eş zamanlı çekişmeyi tek başına yönetmez, sadece geçersiz durumları önler. İşlemler (transactions) bu durumların ele alınmasında temeldir.
  • Uygulama: SQL CHECK (stock >= 0) veya JPA'da validator'lar. İşlemler @Transactional ile yönetilir.
  • Avantajlar: Veri bütünlüğünü sağlamanın temel bir yolu.
  • Dezavantajlar: Eş zamanlı satın alımlarda "overselling" sorununu tek başına çözmez, sadece bir satın alma işlemi negatif stok bırakmaya çalışırsa hata fırlatır.

5. Kontrollü Yeniden Denemeler:

  • Prensip: Optimistic locking veya diğer geçici hatalarda (örneğin, deadlock'lar) işlemi belirli bir sayıda ve belirli bir gecikmeyle (üstel geri çekilme ile) yeniden denemek.
  • Uygulama: Spring Retry gibi kütüphaneler veya manuel olarak döngülerle.
  • Avantajlar: Geçici hatalardan kurtulmayı sağlar, kullanıcı deneyimini iyileştirir.
  • Dezavantajlar: İyi tasarlanmazsa sistemin daha fazla yük altına girmesine neden olabilir. Sonsuz döngülere veya yığılmalara dikkat edilmelidir.

Dağıtık Ortamlarda Çözüm Seçimi:

Farklı uygulama örnekleri işlemleri yapsa bile aşırı satışı engellemek için:

  • Optimistic Locking: Her bir uygulama örneği, veritabanına yazdığı zaman sürüm numarasını kontrol edeceği için, veritabanı seviyesinde tutarlılık sağlanır. İşlem seviyesinde yeniden denemeler yapılmalıdır.
  • Pessimistic Locking: Veritabanı kilitleri, farklı uygulama örneklerinden gelen SELECT FOR UPDATE isteklerini koordine eder ve sadece birinin kilidi almasına izin verir.
  • Atomik Koşullu SQL: Bu en etkili çözümdür çünkü veritabanı, UPDATE sorgusunun atomik bir şekilde çalışmasını sağlar ve birden fazla örnek aynı anda denese bile sadece birisi başarılı olur.

Genellikle, Optimistic Locking (yeniden denemelerle birlikte) ve Atomik Koşullu SQL, hem performans hem de tutarlılık açısından dağıtık sistemler için daha uygun seçeneklerdir.

Soru 25:
Design an E-Commerce Order Tracking System.

Siparişin verilmesinden teslimata kadar bir siparişi takip eden bir sistem tasarlayın.

Aşağıdaki konuları ele alın:

  • Sipariş oluşturma ve kalıcı depolama.
  • Sipariş durum geçişleri.
  • Envanter rezervasyonu ve ödeme işleme.
  • Olay tabanlı güncellemeler.
  • Sevkiyat takibi entegrasyonları.
  • Müşteri bildirimleri.
  • API tasarımı ve veri tutarlılığı.
  • Gözlemlenebilirlik (observability), yeniden denemeler ve hata kurtarma.

Yinelemeli sipariş oluşturmayı nasıl önleyeceğinizi ve aşağı akış hizmetleri geçici olarak kullanılamadığında sipariş durumunu nasıl doğru tutacağınızı açıklayın.

Bir E-ticaret sipariş takip sistemi tasarımı, karmaşık bir dağıtık sistemin birçok temel parçasını içerir. İşte kapsamlı bir yaklaşım:

1. Sistem Mimarisi: Mikroservis Yaklaşımı

Sistemi ayrı, bağımsız mikroservislere bölmek, ölçeklenebilirlik, esneklik ve bakım kolaylığı sağlar. Ana servisler:

  • Order Service: Sipariş oluşturma, yönetme, durum geçişleri.
  • Inventory Service: Stok yönetimi, rezervasyon.
  • Payment Service: Ödeme işlemlerini yönetme.
  • Shipping Service: Sevkiyat entegrasyonları, takip.
  • Notification Service: Müşteri bildirimleri (e-posta, SMS).
  • User Service: Müşteri ve adres bilgileri.

Bu servisler birbirleriyle ağırlıklı olarak olay tabanlı (event-driven) mimari ve asenkron mesajlaşma (Kafka, RabbitMQ) aracılığıyla iletişim kuracaktır. Senkron API çağrıları kritik, hemen yanıt gerektiren durumlar için kullanılabilir.

2. Sipariş Oluşturma ve Kalıcı Depolama:

  • Veritabanı: Order Service, sipariş verilerini tutmak için kendi veritabanını kullanır (örneğin, PostgreSQL). Her servis kendi veritabanına sahip olmalıdır (Database per Service pattern) veri bağımsızlığı için.
  • Sipariş Yapısı:
    • Order: ID, UserID, SiparişTarihi, ToplamTutar, AdresBilgileri, Durum (CREATED, PENDING_PAYMENT, PAID, CONFIRMED, SHIPPED, DELIVERED, CANCELLED), OluşturmaZamanı, GüncellemeZamanı.
    • OrderItem: ID, OrderID, ProductID, Quantity, UnitPrice.
  • Yinelemeli Sipariş Oluşturmayı Önleme (Idempotency):
    • İstemci, sipariş oluşturma isteğiyle birlikte benzersiz bir Idempotency Key (örneğin, bir UUID) göndermelidir.
    • Order Service, bu anahtarı kontrol ederek aynı anahtarla daha önce bir sipariş oluşturulup oluşturulmadığını kontrol eder. Eğer oluşturulmuşsa, mevcut siparişin sonucunu döndürür, yeni bir sipariş oluşturmaz. Bu, ağ gecikmeleri veya istemci tarafındaki yeniden denemelerden kaynaklanan çift siparişleri önler.

3. Sipariş Durum Geçişleri (Event-Driven):

Sipariş durumu geçişleri, olaylar aracılığıyla yönetilir. Bu, servislerin gevşek bağlanmasını (loose coupling) sağlar ve sistemin daha esnek olmasını sağlar.

  1. OrderCreatedEvent: Order Service, yeni bir sipariş oluşturulduğunda bu olayı yayınlar.
  2. InventoryService: OrderCreatedEvent'i dinler, envanteri rezerve eder ve InventoryReservedEvent veya InventoryReservationFailedEvent yayınlar.
  3. PaymentService: InventoryReservedEvent'i dinler, ödeme işlemini başlatır ve PaymentProcessedEvent veya PaymentFailedEvent yayınlar.
  4. OrderService: İlgili olayları dinler ve siparişin durumunu günceller (PENDING_PAYMENT -> PAID -> CONFIRMED).
  5. ShippingService: OrderConfirmedEvent'i dinler, sevkiyatı başlatır ve OrderShippedEvent yayınlar.
  6. NotificationService: Tüm ilgili olayları dinler ve müşteriye e-posta/SMS gönderir.

Bu, Saga Pattern'in bir formudur. Özellikle Choreography-based Saga, servislerin birbirini doğrudan çağırmak yerine olaylar aracılığıyla etkileşim kurmasını sağlar.

4. Envanter Rezervasyonu ve Ödeme İşleme:

  • Envanter Rezervasyonu: Bir sipariş oluşturulduğunda, Inventory Service ilgili ürünlerin stokunu "rezerv" durumuna alır (gerçek stoktan düşmeden önce). Ödeme başarılı olursa kesin düşüş yapılır, başarısız olursa rezervasyon geri alınır. Optimistic Locking veya atomik SQL güncellemeleri, eş zamanlı rezervasyonları yönetmek için kullanılır.
  • Ödeme İşleme: Payment Service, harici ödeme sağlayıcıları (Stripe, Braintree vb.) ile entegre olur. Ödeme başarısız olursa, Order Service'e PaymentFailedEvent gönderir ve sipariş durumu CANCELLED'a geçer.

5. Sevkiyat Takibi Entegrasyonları:

  • Shipping Service, UPS, FedEx, DHL gibi kargo firmalarının API'leriyle entegre olur.
  • Sevkiyat durum güncellemelerini (Shipped, In Transit, Out for Delivery, Delivered) kargo firmalarından alıp Order Service'e veya doğrudan Notification Service'e iletir (Webhook veya Polling).

6. Müşteri Bildirimleri:

  • Notification Service, sipariş durumu değişiklikleri (Onaylandı, Kargoya Verildi, Teslim Edildi, İptal Edildi) için müşterilere e-posta, SMS veya push bildirimi gönderir.
  • Bildirim şablonları merkezi olarak yönetilir.

7. API Tasarımı ve Veri Tutarlılığı:

  • RESTful API'ler: Servisler dış dünyaya (frontend, mobil uygulama) RESTful API'ler sunar (örneğin, GET /orders/{orderId}, POST /orders).
  • Veri Tutarlılığı:
    • Eventual Consistency (Nihai Tutarlılık): Dağıtık sistemlerde yaygın bir yaklaşımdır. Farklı servisler kendi verilerini tutar ve olaylar aracılığıyla senkronize olurlar. Bir olay yayınlandıktan sonra diğer servislerin bu olayı işlemesi zaman alabilir, bu nedenle veriler kısa bir süre tutarsız görünebilir ancak sonunda tutarlı hale gelir.
    • ACID İşlemleri: Her mikroservis kendi etki alanındaki veriler için ACID (Atomicity, Consistency, Isolation, Durability) garantisi sağlayan işlemleri kullanır. Servisler arası işlemler için dağıtık işlem (distributed transaction) yerine Saga pattern tercih edilir.

8. Gözlemlenebilirlik (Observability), Yeniden Denemeler ve Hata Kurtarma:

  • Gözlemlenebilirlik:
    • Logging: Tüm servisler merkezi bir log sistemine (ELK Stack, Grafana Loki) log gönderir. Correlation ID'ler, bir isteğin birden fazla servis üzerindeki tüm loglarını izlemeyi sağlar.
    • Monitoring: Prometheus/Grafana ile servis metrikleri (latency, error rates, throughput, CPU/Memory usage) izlenir.
    • Distributed Tracing: Jaeger, Zipkin gibi araçlarla isteklerin servisler arasında nasıl hareket ettiği izlenir, darboğazlar tespit edilir.
  • Yeniden Denemeler (Retries):
    • Geçici ağ hataları veya servis meşguliyeti durumları için HTTP çağrılarında üstel geri çekilme (exponential backoff) ve jitter ile yeniden denemeler uygulanır.
    • Mesaj kuyruklarındaki tüketiciler, bir hata durumunda mesajı tekrar işlemeyi denemeli veya bir "dead-letter queue" (DLQ) göndermelidir.
  • Hata Kurtarma:
    • Circuit Breaker: Bir servis sürekli olarak hata veriyorsa, diğer servislerin ona çağrı yapmasını belirli bir süre durdurarak sistemin diğer bölümlerinin sağlıklı kalmasını sağlar. Hystrix veya Resilience4j gibi kütüphanelerle uygulanır.
    • Idempotent Tüketiciler: Mesaj kuyruklarından aynı mesaj birden fazla kez gelse bile iş operasyonunun sadece bir kez uygulanmasını sağlar (yukarıdaki Idempotency Key kullanımı).
    • Transaction Outbox Pattern: Bir servis kendi veritabanına veri yazıp aynı işlemde bir olay yayınlaması gerektiğinde kullanılır. Bu, hem veritabanı yazımının hem de olay yayınlamanın atomik olmasını sağlar.

Aşağı Akış Hizmetleri Geçici Olarak Kullanılamadığında Sipariş Durumunu Doğru Tutma:

  • Asenkron Mesajlaşma ve Olaylar: Bu mimarinin temelidir. Eğer Inventory Service geçici olarak kullanılamazsa, Order Service yine de OrderCreatedEvent'i yayınlar. Inventory Service geri geldiğinde, kuyruktaki mesajı işleyebilir.
  • Dead-Letter Queues (DLQ): Bir mesaj tekrar tekrar işlenemiyorsa DLQ'ye gönderilir. Bu mesajlar daha sonra manuel olarak incelenebilir veya bir hata kurtarma işlemi tetiklenebilir.
  • Compensating Transactions (Tazmin Edici İşlemler): Saga pattern'da, bir adım başarısız olursa, daha önceki adımların etkilerini geri almak için tazmin edici işlemler tetiklenebilir (örneğin, ödeme başarısız olursa envanter rezervasyonunu iptal et).
  • Retry Mekanizmaları: Servisler arası API çağrıları veya mesaj kuyruğu işlemleri için yeniden deneme mekanizmaları, geçici kesintilerde otomatik kurtarma sağlar.
  • Monitoring ve Uyarılar: Servislerin durumunu aktif olarak izlemek ve herhangi bir sorun durumunda hızlıca uyarı almak, manuel müdahaleyi hızlandırır.
Soru 26:
Design a Distributed Rate Limiter.

Bir hız sınırlayıcı (rate limiter), bir kullanıcının, istemcinin veya hizmetin belirli bir zaman aralığında yapabileceği istek sayısını kontrol eder.

Aşağıdaki konuları tartışın:

  • Sabit pencere (fixed window), kayan pencere (sliding window) ve token bucket algoritmaları.
  • Kullanıcı başına ve istemci başına kotalar.
  • Redis veya başka bir paylaşılan veri deposu.
  • Eş zamanlı trafik altında atomik güncellemeler.
  • Dağıtık dağıtım ve hata davranışı.
  • Hız sınırlaması yanıt kodları ve yeniden deneme rehberliği.

Tasarımın birden fazla API ağ geçidi örneğinde nasıl ölçekleneceğini ve uygulamanın nasıl makul ölçüde tutarlı kalacağını açıklayın.

Dağıtık bir hız sınırlayıcı (Rate Limiter) tasarımı, mikroservis mimarilerinde sistemin aşırı yüklenmesini önlemek ve adil kaynak kullanımı sağlamak için kritik öneme sahiptir. Temel fikir, belirli bir zaman diliminde (örneğin, 1 dakika) belirli bir API için izin verilen istek sayısını kısıtlamaktır.

1. Hız Sınırlama Algoritmaları:

  • a. Fixed Window Counter (Sabit Pencere Sayacı):
    • Prensip: Belirli bir zaman penceresi (örneğin, 1 dakika) tanımlanır. Bu pencere içindeki tüm istekler sayılır. Sayaç, pencerenin sonunda sıfırlanır.
    • Dezavantaj: Pencere sınırlarında "burst" (patlama) istekler alabilir. Örneğin, bir pencerenin sonunda max istek ve hemen yeni pencerenin başında max istek gelirse, aslında 2 katı istek almış olur.
    • Kullanım Alanı: Basit ve uygulaması kolay senaryolar.
  • b. Sliding Window Log (Kayan Pencere Günlüğü):
    • Prensip: Her isteğin zaman damgasını bir günlükte tutar. Bir istek geldiğinde, mevcut pencere içinde (geçerli zaman - pencere boyutu) kalan tüm zaman damgalarını sayar. Belirli bir limiti aşan eski zaman damgalarını temizler.
    • Avantaj: Fixed Window'un burst sorununu çözerek daha pürüzsüz bir sınırlama sağlar.
    • Dezavantaj: Her istek için zaman damgasını saklamak ve saymak daha fazla bellek ve işlem gücü gerektirir.
    • Kullanım Alanı: Daha hassas ve adil sınırlama gerektiren durumlar.
  • c. Sliding Window Counter (Kayan Pencere Sayacı):
    • Prensip: Hem mevcut pencerenin hem de önceki pencerenin sayaçlarını kullanır. İki pencerenin ağırlıklı ortalaması alınarak daha doğru bir tahmin yapılır. Fixed Window'dan daha iyi, Sliding Window Log'dan daha hafiftir.
    • Kullanım Alanı: Performans ve doğruluk arasında iyi bir denge isteyen durumlar.
  • d. Token Bucket (Jeton Kovası):
    • Prensip: Sürekli olarak bir kovaya jeton (token) eklenir (belirli bir hızda). Bir istek geldiğinde, kovada yeterli jeton varsa istek işlenir ve jeton kovadan çıkarılır. Yeterli jeton yoksa istek reddedilir. Kovanın maksimum bir kapasitesi vardır.
    • Avantaj: Kısa süreli burst istekleri karşılayabilir (kovanın kapasitesi kadar), ardından sınırlama yapar.
    • Dezavantaj: Uygulaması diğerlerine göre biraz daha karmaşıktır.
    • Kullanım Alanı: Burst toleransı istenen ancak ortalama hızın sınırlanması gereken durumlar.

2. Kullanıcı/İstemci Başına Kotalar:

  • Hız sınırlama, genellikle kimliği doğrulanmış kullanıcılar (user ID), API anahtarları (API key), IP adresleri veya istemci ID'leri (client ID) üzerinden uygulanır.
  • Bu ID'ler, Redis anahtarlarının bir parçası olarak kullanılır (örneğin, rate_limit:{userId}:{apiPath} veya rate_limit:{ipAddress}).

3. Redis veya Başka Bir Paylaşılan Veri Deposu:

  • Dağıtık bir sistemde, hız sınırlayıcının durumunu (sayaçlar, zaman damgaları, jeton miktarları) birden fazla API ağ geçidi örneği arasında paylaşmak esastır.
  • Redis: Yüksek performanslı, in-memory ve tek thread'li yapısı sayesinde atomik işlemlere izin veren popüler bir seçimdir. INCR, EXPIRE, ZADD, ZRANGEBYSCORE gibi komutlar hız sınırlama algoritmaları için çok uygundur.
  • Diğer Seçenekler: Apache Cassandra (daha yüksek ölçek, biraz daha yüksek gecikme), etcd/ZooKeeper (daha çok konfigürasyon ve koordinasyon için, hız sınırlama için ideal değil).

4. Eş Zamanlı Trafik Altında Atomik Güncellemeler:

  • Birden fazla API ağ geçidi örneği aynı anda bir kullanıcının sayacını güncellemeye çalışabilir. Bu, yarış koşullarına (race condition) yol açabilir.
  • Redis Atomik İşlemler:
    • INCR komutu Redis'te atomiktir ve sayaçları güvenle artırır.
    • Lua komut dosyaları (script) veya Redis Transaction (MULTI/EXEC) kullanılarak birden fazla komut atomik olarak çalıştırılabilir. Bu, özellikle Sliding Window Log veya Token Bucket algoritmaları için kritiktir.
    
-- Token Bucket Algoritması için Redis Lua Script örneği
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local fill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local tokens = redis.call('get', key)
tokens = tokens and tonumber(tokens) or capacity
local last_refill = redis.call('get', key .. ':ts')
last_refill = last_refill and tonumber(last_refill) or 0

local delta_time = math.max(0, now - last_refill)
tokens = math.min(capacity, tokens + delta_time * fill_rate)

if tokens >= requested then
    tokens = tokens - requested
    redis.call('set', key, tokens)
    redis.call('set', key .. ':ts', now)
    return 1
else
    return 0
end

5. Dağıtık Dağıtım ve Hata Davranışı:

  • Gateway Katmanı: Hız sınırlayıcı, genellikle API Gateway (Nginx, Kong, Spring Cloud Gateway) katmanında uygulanır. Bu, trafiği çekirdek servislere ulaşmadan önce kontrol etmeyi sağlar.
  • Redis Kümesi (Cluster): Yüksek kullanılabilirlik ve ölçeklenebilirlik için Redis Cluster kullanılır. Ana-yedek (master-replica) setleri veya sharding ile veriler birden fazla Redis düğümüne dağıtılır.
  • Hata Davranışı:
    • Redis bağlantısı kesilirse veya Redis yavaşlarsa: Hız sınırlayıcının "fail-open" (tüm isteklere izin ver) veya "fail-closed" (tüm istekleri reddet) davranışını belirlemek önemlidir. Genellikle fail-open, sistemin tamamen durmasını önlemek için tercih edilir, ancak bu, sistemin aşırı yüklenmesi riskini taşır.
    • Ön bellek (in-memory cache) + Redis: Her API Gateway örneği, kendi içinde küçük bir ön bellek tutabilir ve Redis'e gitmeden önce bu ön belleği kontrol edebilir. Bu, Redis'e olan yükü azaltır ancak dağıtık tutarlılığı hafifçe zayıflatır (nihai tutarlılık).

6. Hız Sınırlaması Yanıt Kodları ve Yeniden Deneme Rehberliği:

  • Bir istek hız sınırlamasına takıldığında, istemciye uygun bir HTTP durum kodu döndürülmelidir. Genellikle:
    • 429 Too Many Requests: En yaygın ve uygun kod.
    • Yanıt başlıkları (Response Headers): İstemcilere ne zaman yeniden deneyebilecekleri hakkında bilgi sağlamak için kullanılır:
      • X-RateLimit-Limit: Penceredeki maksimum istek sayısı.
      • X-RateLimit-Remaining: Kalan istek sayısı.
      • X-RateLimit-Reset: Yeniden deneme yapabilecekleri zaman (Unix timestamp veya saniye cinsinden).
  • Yeniden Deneme Rehberliği: İstemcilerin 429 durum kodu aldıklarında hemen tekrar denemek yerine X-RateLimit-Reset başlığını kullanarak veya üstel geri çekilme (exponential backoff) stratejisi ile yeniden denemeleri teşvik edilmelidir. Bu, sistemin daha da yüklenmesini önler.

Birden Fazla API Ağ Geçidi Örneğinde Ölçeklenebilirlik ve Tutarlılık:

  • Merkezi Redis: Tüm API Gateway örnekleri, hız sınırlama durumunu tek bir merkezi Redis kümesinden okuyup yazarak tutarlılığı sağlar. Redis'in yüksek performansı ve atomik işlemleri sayesinde, birden fazla ağ geçidi örneği bile doğru sayma ve sınırlama yapabilir.
  • Shardlama: Eğer hız sınırlayıcı verisi çok büyürse, Redis verileri kullanıcı ID'sine veya IP adresine göre shardlanabilir (parçalara ayrılabilir). Bu, yükü birden fazla Redis düğümüne dağıtır.
  • Ağırlıklı Sınırlama: Farklı API'ler veya istemciler için farklı hız sınırlama politikaları (örneğin, kritik API'ler için daha sıkı sınırlamalar) tanımlanabilir ve bu politikalar Redis anahtarlarının bir parçası olarak saklanabilir.
Soru 27:
Design a URL Shortener.

Uzun URL'leri kompakt, paylaşılabilir bağlantılara dönüştüren bir hizmet tasarlayın.

Önemli alanlar şunları içerir:

  • URL oluşturma ve yeniden yönlendirme API'leri.
  • Benzersiz kısa kod üretimi.
  • Veritabanı şeması ve indeksleme.
  • Çakışma yönetimi.
  • Sık erişilen URL'leri önbelleğe alma.
  • Süre sonu (expiration), kötüye kullanım önleme ve analitik.
  • Yüksek kullanılabilirlik ve yatay ölçeklendirme.

Rastgele tanımlayıcılar, sayaç tabanlı yaklaşımlar ve kodlanmış benzersiz kimlikler arasında nasıl seçim yapacağınızı tartışın.

Bir URL kısaltıcı hizmeti (URL Shortener), uzun bir URL'yi daha kısa, akılda kalıcı ve kolay paylaşılabilir bir bağlantıya dönüştüren bir sistemdir. Temel işlevselliği, kısa URL'yi alan bir isteği orijinal uzun URL'ye yönlendirmektir.

1. Temel İşlevsellik ve API'ler:

  • Kısa URL Oluşturma API:
    • Endpoint: POST /shorten
    • Request: { "longUrl": "https://www.example.com/very/long/path/to/resource", "customAlias": "myalias" (optional), "expirationDate": "2024-12-31" (optional) }
    • Response: { "shortUrl": "https://short.url/abcd", "longUrl": "...", "customAlias": "..." }
    • customAlias alanı, kullanıcının kendi istediği kısa kodu belirlemesine olanak tanır.
  • Yönlendirme API:
    • Endpoint: GET /{shortCode}
    • İşlev: Kısa kodu kullanarak orijinal uzun URL'yi veritabanından/önbellekten bulur ve HTTP 301 (Moved Permanently) veya 302 (Found) durumuyla orijinal URL'ye yönlendirir. 301, SEO için daha iyidir (kalıcı yönlendirme), ancak 302 daha esnektir (kısa URL değiştirilebilir). Genellikle 302 kullanılır.

2. Benzersiz Kısa Kod Üretimi:

Kısa kodun benzersiz ve yeterince kısa olması gerekir. Genellikle 6-8 karakter uzunluğunda ve alfanümerik karakterlerden (a-z, A-Z, 0-9) oluşur. Bu, 62^6 ila 62^8 kombinasyon sağlar, bu da milyarlarca URL için yeterlidir.

  • a. Rastgele Tanımlayıcılar (Random Identifiers):
    • Prensip: Her uzun URL için rastgele bir alfanümerik dize (örn. abcdEF) oluşturulur. Bu kodun veritabanında daha önce var olup olmadığı kontrol edilir. Eğer varsa, yeni bir rastgele kod oluşturulur ve tekrar kontrol edilir (çakışma yönetimi).
    • Avantajlar: Dağıtık sistemlerde kolay uygulanabilir, herhangi bir merkezi sıra (sequence) yönetimi gerektirmez. Kısa kodlar öngörülemez.
    • Dezavantajlar: Çakışma olasılığı (özellikle çok fazla URL kısaltılırsa), yeniden deneme gerektirebilir.
    • Seçim: En yaygın ve önerilen yöntemdir. Çakışma olasılığı düşüktür ve yönetilebilir.
  • b. Sayaç Tabanlı Yaklaşımlar (Counter-Based Approaches):
    • Prensip: Monotonik olarak artan bir sayı (veritabanı auto-increment ID'si gibi) alır ve bunu Base62 (veya benzeri bir kodlama) kullanarak alfanümerik bir kısa koda dönüştürür. Örneğin, ID 1000 ise Base62'de 'gS' olabilir.
    • Avantajlar: Çakışma riski yoktur (ID'ler benzersiz olduğu sürece), daha kompakt kodlar üretebilir.
    • Dezavantajlar: Merkezi bir sayaç veya ID üreticisi gerektirir (dağıtık sistemlerde darboğaz veya tek hata noktası olabilir). Kısa kodlar sıralı olacağından tahmin edilebilir.
    • Seçim: Tekil (monolithic) sistemler için uygun olabilir, ancak dağıtık sistemlerde merkezi sayaç yönetimi karmaşıktır.
  • c. Kodlanmış Benzersiz Kimlikler (Encoded Unique IDs - Hash Fonksiyonları):
    • Prensip: Uzun URL'nin bir hash'i alınır (örneğin MD5, SHA256) ve bu hash'in ilk birkaç karakteri veya belirli bir kısmı kısa kod olarak kullanılır.
    • Avantajlar: Aynı uzun URL için her zaman aynı kısa kodu üretir (URL kısaltıcı tarafından değil, hash fonksiyonu tarafından).
    • Dezavantajlar: Hash çakışmaları (collision) mümkündür (farklı uzun URL'ler için aynı kısa kod). Hash'in boyutu genelde kısadır, bu da çakışma olasılığını artırır. Hash'in ilk kısımlarını almak da çakışma olasılığını artırır.
    • Seçim: Hash çakışmalarını yönetmek zor olabileceğinden, genellikle doğrudan hash kullanmak yerine, hash'i bir benzersizlik kontrol mekanizmasıyla birleştirmek (rastgele ID oluşturma gibi) daha güvenlidir.

Özetle, rastgele tanımlayıcılar ve çakışma yönetimi, dağıtık ve ölçeklenebilir bir URL kısaltıcı için en iyi yaklaşımdır.

3. Veritabanı Şeması ve İndeksleme:

Basit bir ilişkisel veritabanı (PostgreSQL, MySQL) yeterli olacaktır.


CREATE TABLE short_urls (
    id BIGINT PRIMARY KEY AUTO_INCREMENT, -- Sayaç tabanlı olursa
    short_code VARCHAR(10) UNIQUE NOT NULL,
    long_url TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    expiration_date TIMESTAMP,
    click_count INT DEFAULT 0,
    user_id BIGINT,
    -- Diğer analitik alanlar
    INDEX idx_short_code (short_code) -- Kısa kod üzerinde hızlı arama için
);
  • short_code üzerinde benzersiz indeks, hızlı arama ve benzersizlik garantisi için kritik.
  • long_url üzerinde de bir indeks, aynı uzun URL'nin birden fazla kez kısaltılmasını önlemek için düşünülebilir, ancak TEXT alanlarda indeksleme maliyetli olabilir. Daha iyi bir yaklaşım, long_url'ün hash'ini tutup bu hash üzerinde indeksleme yapmaktır.

4. Çakışma Yönetimi (Collision Handling):

  • Rastgele Kod İçin: Yeni bir rastgele kısa kod oluşturulduğunda, veritabanında bu kodun zaten var olup olmadığını kontrol edin. Eğer varsa, yeni bir kod oluşturup tekrar deneyin. Bu, bir döngü içinde belirli sayıda deneme ile yapılabilir. Çakışma olasılığı düşük olduğu için genellikle 3-5 deneme yeterlidir.
  • Custom Alias İçin: Kullanıcı özel bir takma ad (alias) istediğinde, o takma adın zaten kullanımda olup olmadığını kontrol edin. Eğer kullanımdaysa, kullanıcıya başka bir takma ad seçmesini bildirin.

5. Sık Erişilen URL'leri Önbelleğe Alma:

  • Yönlendirme trafiği çok yüksek olacağı için, sık erişilen kısa kodları önbelleğe almak performansı kritik derecede artıracaktır.
  • Redis veya Memcached: Kısa kodları (anahtar) ve bunlara karşılık gelen uzun URL'leri (değer) saklamak için kullanılır.
  • TTL (Time-To-Live): Önbellekteki girişler için TTL belirleyin. Bu, veritabanındaki değişikliklerin (örneğin, bir URL'nin süresinin dolması) önbelleğe yansımasını sağlar.
  • Önbellek Geçersiz Kılma (Cache Invalidation): Bir kısa URL silinirse veya süresi dolarsa, önbellekten de temizlenmelidir.

6. Süre Sonu, Kötüye Kullanım Önleme ve Analitik:

  • Süre Sonu (Expiration): Kullanıcılar, kısa URL'lerin belirli bir tarihte süresinin dolmasını isteyebilir. Veya sistem varsayılan bir süre sonu belirleyebilir. Süresi dolan URL'ler yönlendirme yapmamalıdır. Veritabanında bir expiration_date alanı ile yönetilir. Arka planda çalışan bir cron işi, süresi dolan URL'leri temizleyebilir veya pasif hale getirebilir.
  • Kötüye Kullanım Önleme:
    • Kara Liste (Blacklisting): Kötü amaçlı veya spam içerik barındıran uzun URL'leri kısaltmayı engellemek için bir kara liste tutulabilir.
    • Rate Limiting: Bir kullanıcının belirli bir zaman aralığında kısaltabileceği URL sayısını sınırlamak için Rate Limiter uygulanır (IP adresi, API Anahtarı başına).
    • Captcha: Çoklu kısaltma istekleri için Captcha doğrulaması kullanılabilir.
  • Analitik:
    • Tıklama Sayısı: Her yönlendirmede click_count alanını artırın.
    • Coğrafi Konum: IP adresinden coğrafi konum bilgisi çıkarılabilir.
    • Referans Kaynakları: HTTP Referer başlığı ile tıklamanın nereden geldiği (Facebook, Twitter vb.) izlenebilir.
    • Tarayıcı/Cihaz Bilgisi: HTTP User-Agent başlığından çıkarılabilir.
    Bu veriler, ayrı bir analitik veritabanına (örneğin, zaman serisi veritabanı - InfluxDB veya veri ambarı - Redshift) veya bir mesaj kuyruğu (Kafka) üzerinden işlenmek üzere gönderilebilir.

7. Yüksek Kullanılabilirlik ve Yatay Ölçeklendirme:

  • Web Katmanı (API Sunucuları): API'leri sağlayan sunucular (Spring Boot uygulamaları), stateless olacak şekilde tasarlanır ve yük dengeleyici (load balancer) arkasına yerleştirilir. Bu sayede yatay olarak ölçeklenebilirler.
  • Veritabanı:
    • Replika Setleri: Ana veritabanı (master) ve birden fazla okuma replikası (read replica) ile okuma yükü dağıtılır.
    • Sharding: Çok büyük veri hacmi için, veritabanı sharding (örneğin, short_code'un ilk karakterine göre) uygulanabilir.
  • Önbellek (Redis): Redis Cluster veya Redis Sentinel ile yüksek kullanılabilirlik ve yatay ölçeklendirme sağlanır.
  • Asenkron İşleme: Analitik verilerin işlenmesi veya süresi dolan URL'lerin temizlenmesi gibi arka plan görevleri için mesaj kuyrukları (Kafka) ve worker servisler kullanılır.
Soru 28:
Design a Distributed Key-Value Store Similar to Redis.

Anahtarla değerleri depolayan ve büyük ölçekte getiren bir hizmeti nasıl tasarlayacağınızı açıklayın.

Aşağıdaki konuları göz önünde bulundurun:

  • Anahtar-değer veri yapıları ve desteklenen işlemler.
  • Bellek içi depolama ve kalıcılık.
  • Veri bölümlendirme (partitioning) ve tutarlı hashleme (consistent hashing).
  • Replikasyon ve hata toleransı (failover).
  • Çıkarma politikaları (eviction policies) ve süre sonu.
  • Tutarlılık garantileri.
  • Hatalardan sonra izleme ve kurtarma.

Düşük gecikme, dayanıklılık (durability), kullanılabilirlik (availability) ve operasyonel karmaşıklık arasındaki dengeyi tartışmaya hazır olun.

Redis benzeri dağıtık bir Anahtar-Değer Deposu (Distributed Key-Value Store) tasarlamak, temel olarak CAP Teoremi (Consistency, Availability, Partition Tolerance) etrafında döner ve düşük gecikme, yüksek performans ve veri bütünlüğünü hedefler.

1. Anahtar-Değer Veri Yapıları ve Desteklenen İşlemler:

  • Temel Anahtar-Değer: Anahtarlar string, değerler string olabilir. (SET key value, GET key)
  • Zengin Veri Yapıları: Redis'in sunduğu gibi, Listeler (LPUSH, RPUSH, LPOP), Hash'ler (HSET, HGET), Set'ler (SADD, SMEMBERS), Sıralı Set'ler (ZADD, ZRANGE).
  • İşlemler: Atomik artırma/azaltma (INCR, DECR), TTL (Time-To-Live) ayarlama (EXPIRE), mevcutsa ekleme (SETNX), vs.

2. Bellek İçi Depolama (In-Memory Storage) ve Kalıcılık (Persistence):

  • Bellek İçi Depolama: Verilerin büyük çoğunluğu veya tamamı RAM'de tutulur, bu da çok düşük gecikmeli okuma/yazma işlemleri sağlar. Her bir düğüm, kendi bölümündeki verileri bellekte saklar.
  • Kalıcılık Mekanizmaları:
    • Snapshotting (RDB): Belirli aralıklarla veya belirli sayıda yazma işleminden sonra bellekteki verilerin bir anlık görüntüsü diske yazılır. Tam bir veri kümesinin kurtarılması için iyidir, ancak son snapshot ile anlık çökme arasındaki veriler kaybedilebilir.
    • Append-Only File (AOF): Her yazma işlemini bir log dosyasına kaydeder. Sunucu yeniden başlatıldığında, bu log dosyasını yeniden oynatarak verileri kurtarır. Daha yüksek veri dayanıklılığı sağlar ancak RDB'ye göre daha yavaş kurtarma süresi ve daha büyük dosya boyutu olabilir.
    • Karma Yaklaşım: Hem RDB hem de AOF birlikte kullanılabilir.

3. Veri Bölümlendirme (Partitioning) ve Tutarlı Hashleme (Consistent Hashing):

  • Veri Bölümlendirme: Veri kümesini birden fazla düğüm arasında dağıtarak yatay ölçeklenebilirlik sağlar. Her düğüm, veri kümesinin bir alt kümesini (partition) tutar.
  • Tutarlı Hashleme: Düğüm eklenip çıkarıldığında veri hareketini en aza indiren bir hashleme şemasıdır.
    • Prensip: Bir hash halkası (hash ring) oluşturulur. Hem düğümler hem de anahtarlar bu halka üzerinde hashlenir. Bir anahtarın hangi düğüme atandığı, halka üzerinde anahtarın hash değerinden sonraki ilk düğüm tarafından belirlenir.
    • Avantaj: Bir düğüm eklendiğinde veya çıkarıldığında, halkadaki sadece küçük bir veri alt kümesinin yeniden dağıtılması gerekir, bu da sistemin kararlılığını artırır ve yeniden yapılandırma maliyetini azaltır.
  • Sanal Düğümler (Virtual Nodes): Tutarlı hashleme halkasında, her fiziksel düğümün birden fazla sanal düğümü temsil etmesi sağlanır. Bu, veri dağılımını daha homojen hale getirir ve düğüm ekleme/çıkarma durumunda yükün daha dengeli dağılmasını sağlar.

4. Replikasyon (Replication) ve Hata Toleransı (Failover):

  • Replikasyon: Veri kaybını önlemek ve okuma ölçeklenebilirliğini artırmak için her veri parçasının (partition) birden fazla kopyası (replikası) farklı düğümlerde tutulur.
    • Her anahtarın en az N kopyası olmalıdır (çoğunlukla 3).
    • Yazma işlemi, belirli bir çoğunluk (quorum) replikaya ulaştığında başarılı sayılabilir.
  • Hata Toleransı (Failover): Bir düğüm çöktüğünde veya kullanılamaz hale geldiğinde, sistemin otomatik olarak sağlıklı replikalardan servis vermeye devam etmesidir.
    • Lider Seçimi (Leader Election): Çoğunluk mekanizmaları (Paxos, Raft) ile bir replika setindeki lider düğüm belirlenir. Yazma işlemleri genellikle lider düğüme yönlendirilir.
    • Otomatik Geçiş (Automatic Failover): İzleme mekanizmaları (örneğin, Gossip protokolü veya harici bir koordinasyon servisi gibi) düğüm arızalarını tespit eder ve otomatik olarak yeni bir lider seçer veya trafiği sağlıklı düğümlere yönlendirir.

5. Çıkarma Politikaları (Eviction Policies) ve Süre Sonu (Expiration):

  • TTL (Time-To-Live): Her anahtar için belirli bir süre sonra otomatik olarak silinmesini sağlayan bir süre sonu mekanizması (EXPIRE key seconds). Bu, önbellekleme ve oturum yönetimi gibi senaryolar için kritiktir.
  • Çıkarma Politikaları (Eviction Policies): Bellek dolduğunda hangi anahtarların silineceğini belirleyen stratejiler:
    • LRU (Least Recently Used): En son kullanılanlar arasından en az kullanılanı sil.
    • LFU (Least Frequently Used): En sık kullanılanlar arasından en az kullanılanı sil.
    • Random: Rastgele sil.
    • No Eviction: Bellek dolduğunda yazma işlemlerini reddet.

6. Tutarlılık Garantileri (Consistency Guarantees):

Dağıtık bir sistemde mutlak tutarlılık (ACID) elde etmek çok zordur ve performans maliyeti yüksektir. Genellikle CAP Teoremi doğrultusunda bir denge bulunur.

  • Eventual Consistency (Nihai Tutarlılık): Bir yazma işlemi tamamlandıktan sonra, verilerin tüm replikalara yayılması ve sonunda tutarlı hale gelmesi garanti edilir. Redis genellikle bu modele yakın çalışır (ana-yedek replikasyonunda).
  • Strong Consistency (Güçlü Tutarlılık): Bir yazma işlemi tamamlandığında, tüm replikalarda o verinin en güncel hali okunabilir. Bu, daha yavaş olabilir ancak veri bütünlüğü kritik olduğunda tercih edilir (örneğin, dağıtık kilitler için Raft/Paxos kullanan bir sistem). Bir dağıtık KV deposu bu garantiyi, çoğunluğa (quorum) yazma ve okuma yaparak sağlayabilir.

7. Hatalardan Sonra İzleme (Monitoring) ve Kurtarma (Recovery):

  • İzleme:
    • Metrikler: Bellek kullanımı, CPU kullanımı, ağ trafiği, okuma/yazma gecikmeleri, hata oranları, replikasyon gecikmeleri, önbellek isabet oranları gibi düğüm ve küme düzeyinde metrikler toplanır (Prometheus, Grafana).
    • Uyarılar: Belirlenen eşik değerleri aşıldığında (örneğin, bellek kullanımı %90'ın üzerine çıktığında) otomatik uyarılar tetiklenir (Alertmanager).
  • Kurtarma:
    • Çökmüş bir düğüm yeniden başlatıldığında, kalıcılık mekanizmalarından (RDB/AOF) verilerini yükleyerek kümeye tekrar katılır.
    • Replikasyon mekanizmaları, çöken bir düğümün geri gelmesi veya yeni bir düğümün eklenmesi durumunda verileri otomatik olarak senkronize eder.
    • İşletimsel Runbook'lar: Çeşitli hata senaryoları için adım adım kurtarma prosedürleri belgelenmelidir.

Düşük Gecikme, Dayanıklılık, Kullanılabilirlik ve Operasyonel Karmaşıklık Arasındaki Denge:

  • Düşük Gecikme: Bellek içi depolama, optimize edilmiş veri yapıları ve ağ protokolleri (örneğin, hafif TCP/IP protokolü) ile sağlanır.
  • Dayanıklılık: Kalıcılık mekanizmaları (RDB, AOF) ve replikasyon ile sağlanır. Daha yüksek dayanıklılık, genellikle yazma gecikmesini artırabilir.
  • Kullanılabilirlik: Replikasyon, hata toleransı ve tutarlı hashleme ile sağlanır. Düğüm arızalarında bile sistemin servis vermeye devam etmesi önemlidir.
  • Operasyonel Karmaşıklık: Dağıtık bir sistemin yönetimi, tekil bir sistemden her zaman daha karmaşıktır. Küme yönetimi, izleme, hata giderme, yükseltmeler ve ölçeklendirme, dikkatli otomasyon ve araçlar gerektirir. Basit bir tasarım, daha düşük operasyonel karmaşıklık anlamına gelirken, daha fazla özellik ve yüksek garanti, karmaşıklığı artırır.

Redis, genellikle AP (Availability and Partition Tolerance) ağırlıklı bir sistemdir ve çoğunlukla nihai tutarlılık (eventual consistency) sağlar, ancak güçlü tutarlılık gerektiren dağıtık kilitler gibi bazı özellikler için senkronizasyon mekanizmaları da sunar.

Soru 29:
Design a User Authentication System.

Web ve mobil uygulamalar için güvenli bir kimlik doğrulama sistemi tasarlayın.

Aşağıdaki konuları ele alın:

  • Kayıt ve giriş (login).
  • Parola hashleme ve kimlik bilgisi koruması.
  • Oturum yönetimi veya token tabanlı kimlik doğrulama.
  • Erişim token'ı (access token) süre sonu ve yenileme token'ı (refresh token) rotasyonu.
  • Çok faktörlü kimlik doğrulama (MFA).
  • Hesap kurtarma ve kaba kuvvet saldırısı koruması.
  • Yetkilendirme (authorization) ve rol yönetimi.
  • Denetim günlükleri (audit logs), hız sınırlama (rate limiting) ve şüpheli giriş tespiti.

Token'ları nasıl koruyacağınızı, gerektiğinde oturumları nasıl iptal edeceğinizi ve yaygın kimlik doğrulama zafiyetlerini nasıl önleyeceğinizi açıklayın.

Güvenli bir kullanıcı kimlik doğrulama (Authentication) sistemi tasarlamak, hem kullanıcı deneyimi hem de güvenlik açısından dikkatli bir denge gerektirir. Modern uygulamalar genellikle token tabanlı (JWT) ve OAuth 2.0/OpenID Connect standartlarını kullanır.

1. Kayıt (Registration) ve Giriş (Login):

  • Kayıt:
    • Kullanıcı adı/e-posta ve parola girişi.
    • Parola politikaları (min uzunluk, karmaşıklık, özel karakter).
    • E-posta doğrulama: Kayıt sonrası kullanıcıya bir doğrulama bağlantısı içeren e-posta gönderilir. Bu, e-posta adresinin geçerliliğini sağlar ve bot kaydını önler.
  • Giriş (Login):
    • Kullanıcı adı/e-posta ve parola ile kimlik doğrulama.
    • Başarılı giriş sonrası Access Token ve Refresh Token verilir.
    • Başarısız girişler için jenerik hata mesajı (örneğin, "Kullanıcı adı veya parola hatalı"). Özel hata mesajları (örneğin, "Kullanıcı adı bulunamadı") saldırganlara bilgi verebilir.

2. Parola Hashleme ve Kimlik Bilgisi Koruması:

  • Parola Hashleme: Parolalar asla düz metin olarak saklanmamalıdır. Bunun yerine, tek yönlü bir hash algoritması kullanılarak (örneğin, Argon2, scrypt, bcrypt) hashlenmelidir. SHA256 veya MD5 gibi algoritmalar yavaşlatıcı olmadıkları için doğrudan kullanılmamalıdır.
  • Salt: Her parola için benzersiz, rastgele oluşturulmuş bir "salt" (tuz) kullanılmalıdır. Bu, aynı parolaya sahip iki kullanıcının farklı hash'lere sahip olmasını sağlar ve "rainbow table" saldırılarını önler. Salt, hash ile birlikte saklanır.
  • Kullanıcı Adı/E-posta Koruması: E-posta adresleri veya kullanıcı adları da hassas bilgi olabilir, bu yüzden veri ihlallerine karşı korumak önemlidir.

// Bcrypt ile parola hashleme örneği (Spring Security'de yaygın kullanılır)
BCryptPasswordEncoder passwordEncoder = new BCryptPasswordEncoder();
String hashedPassword = passwordEncoder.encode("mysecretpassword");
boolean isMatch = passwordEncoder.matches("mysecretpassword", hashedPassword);

3. Oturum Yönetimi veya Token Tabanlı Kimlik Doğrulama:

  • Oturum Yönetimi (Geleneksel):
    • Sunucu tarafında oturum bilgileri (session ID, kullanıcı bilgileri) saklanır.
    • Kullanıcıya bir Session ID içeren çerez (cookie) gönderilir.
    • Her istekte sunucu, çerezdeki Session ID'yi kontrol ederek kullanıcının kimliğini doğrular.
    • Avantajlar: Oturumları kolayca iptal etme, daha basit yönetim.
    • Dezavantajlar: Dağıtık sistemlerde oturum replikasyonu veya merkezi oturum deposu gerektirir (ölçeklenebilirlik sorunu), Cross-Site Request Forgery (CSRF) saldırılarına karşı dikkatli olunmalıdır.
  • Token Tabanlı Kimlik Doğrulama (JWT - JSON Web Tokens):
    • Prensip: Sunucu, başarılı bir giriş sonrası bir JWT (Access Token) oluşturur ve istemciye gönderir. İstemci bu token'ı (genellikle Authorization: Bearer <token> başlığı ile) her istekte sunucuya gönderir. Token, kullanıcının kimliğini ve yetkilerini içerir ve sunucu tarafından doğrulanır (imza kontrolü ile). Token sunucu tarafında saklanmaz (stateless).
    • Avantajlar: Yatay ölçeklenebilirlik (stateless olduğu için), mobil uygulamalar ve mikroservisler arası iletişim için ideal, CORS sorunlarını azaltır.
    • Dezavantajlar: Token'ın süresi dolana kadar iptal edilmesi zordur (blacklist mekanizması gerekebilir), daha büyük token boyutu, Cross-Site Scripting (XSS) saldırılarına karşı dikkatli olunmalıdır.

4. Erişim Token'ı Süre Sonu ve Yenileme Token'ı Rotasyonu:

  • Access Token (Erişim Token'ı): Kısa ömürlü olmalıdır (örneğin, 5-15 dakika). Bir saldırgan tarafından ele geçirilse bile sınırlı bir süre için kullanılabilir. Kullanıcının doğrudan kaynaklara erişimini sağlar.
  • Refresh Token (Yenileme Token'ı): Uzun ömürlüdür (örneğin, 7 gün ila 1 yıl). Erişim token'ı süresi dolduğunda, istemci yeni bir erişim token'ı almak için yenileme token'ını kullanır.
    • Depolama: Yenileme token'ları genellikle veritabanında saklanır ve tek kullanımlık olmalıdır (yenileme token'ı kullanıldıktan sonra yeni bir yenileme token'ı oluşturulur).
    • Rotasyon: Her yenileme token'ı kullanıldığında yeni bir yenileme token'ı oluşturulup eskisini iptal etmek, saldırganın ele geçirdiği bir yenileme token'ının uzun süreli kullanımını engeller.
  • Token Depolama (İstemci Tarafı):
    • Access Token: Web uygulamalarında genellikle tarayıcının belleğinde (memory) veya HTTP-only olmayan çerezlerde saklanır (XSS riski). Mobil uygulamalarda güvenli depolama alanları (keychain) kullanılır.
    • Refresh Token: HTTP-only çerezlerde (XSS riskini azaltır) veya mobil uygulamalarda güvenli depolama alanlarında saklanmalıdır. CSRF'ye karşı korunmalıdır.

5. Çok Faktörlü Kimlik Doğrulama (MFA - Multi-Factor Authentication):

  • Giriş sürecine ek bir güvenlik katmanı ekler. Kullanıcı, parola dışında başka bir doğrulama faktörü (örneğin, SMS ile gelen kod, Authenticator uygulaması kodu, biyometrik veri) sağlamalıdır.
  • TOTP (Time-Based One-Time Password) veya HOTP (HMAC-Based One-Time Password) algoritmaları yaygın olarak kullanılır.

6. Hesap Kurtarma ve Kaba Kuvvet Saldırısı Koruması:

  • Hesap Kurtarma:
    • Parola sıfırlama: Kayıtlı e-posta veya telefon numarasına gönderilen tek kullanımlık bir bağlantı/kod ile yapılır. Bağlantı/kod kısa ömürlü olmalı ve sadece bir kez kullanılabilmelidir.
    • Güvenlik soruları: Genellikle tavsiye edilmez, çünkü cevaplar tahmin edilebilir veya araştırılarak bulunabilir.
  • Kaba Kuvvet Saldırısı Koruması:
    • Hız Sınırlama (Rate Limiting): Belirli bir IP adresinden veya kullanıcı adından gelen başarısız giriş denemelerinin sayısını sınırlayın. Belirli bir sayıda başarısız denemeden sonra hesabı geçici olarak kilitleyin veya Captcha isteyin.
    • Hesap Kilitleme: Çok sayıda başarısız denemeden sonra hesabı belirli bir süre (örneğin, 30 dakika) veya yöneticinin kilidi açmasını gerektirecek şekilde kilitleyin.

7. Yetkilendirme (Authorization) ve Rol Yönetimi:

  • Yetkilendirme: Kullanıcının kimliği doğrulandıktan sonra, hangi kaynaklara veya işlemlere erişim izni olduğunu belirleme sürecidir.
  • Rol Tabanlı Erişim Kontrolü (RBAC): Kullanıcılara roller atanır (örneğin, ADMIN, EDITOR, VIEWER). Her role belirli izinler (örneğin, Product.create, Product.read) verilir. Kullanıcının erişimi, atanmış olduğu rollerin izinlerine göre belirlenir.
  • Spring Security: Java backend'de yetkilendirme için güçlü bir çerçevedir (@PreAuthorize, hasRole('ADMIN')).

8. Denetim Günlükleri (Audit Logs), Hız Sınırlama ve Şüpheli Giriş Tespiti:

  • Denetim Günlükleri: Tüm kritik güvenlik olaylarını (başarılı/başarısız girişler, parola değişiklikleri, rol atamaları, token yenilemeleri) kaydet. Bu günlükler merkezi bir SIEM (Security Information and Event Management) sistemine gönderilmeli ve incelenmelidir.
  • Hız Sınırlama: Login, kayıt, parola sıfırlama gibi endpoint'lerde Rate Limiter kullanarak kötüye kullanımı önleyin.
  • Şüpheli Giriş Tespiti:
    • Anormal IP adresi değişiklikleri (örneğin, aynı anda farklı coğrafi konumlardan giriş).
    • Yeni bir cihazdan ilk giriş.
    • Anormal giriş zamanları.
    Bu tür durumlar için uyarılar oluşturulabilir veya ek doğrulama adımları (MFA gibi) tetiklenebilir.

Token'ları Koruma, Oturumları İptal Etme ve Zafiyetleri Önleme:

  • Token Koruması:
    • JWT'ler yalnızca HTTPS üzerinden gönderilmelidir (man-in-the-middle saldırılarını önlemek için).
    • Refresh Token'lar HTTP-only ve Secure flag'li çerezlerde saklanmalıdır (XSS'i önlemek için).
    • Access Token'lar bellekte (memory) tutulmalı veya XSS zafiyetlerine karşı dikkatli olunmalıdır.
    • JWT'ler kısa ömürlü olmalı ve gizli anahtarla (secret key) imzalanmalıdır. Anahtar güvenli bir yerde saklanmalı ve düzenli olarak rotasyon yapılmalıdır.
  • Oturumları/Token'ları İptal Etme:
    • Session Tabanlı: Sunucu tarafındaki oturum tablosundan oturum kaydını silerek anında iptal edilebilir.
    • Token Tabanlı (JWT): JWT'ler stateless olduğu için doğrudan iptal edilemez. İptal için bir "blacklist" (kara liste) veya "revocation list" (iptal listesi) tutulur. İptal edilen token'lar bu listeye eklenir ve her istekte kontrol edilir. Bu, ek bir veritabanı/önbellek sorgusu anlamına gelir ve JWT'nin stateless avantajını bir ölçüde azaltır. Refresh token'lar ise tek kullanımlık yapılarak ve veritabanında izlenerek iptal edilebilir.
    • Kullanıcı parolasını değiştirdiğinde veya şüpheli aktivite algılandığında, tüm aktif oturumları/token'ları iptal edin.
  • Yaygın Kimlik Doğrulama Zafiyetlerini Önleme:
    • SQL Enjeksiyonu: Hazırlanmış ifadeler (prepared statements) veya ORM kütüphaneleri kullanın.
    • XSS (Cross-Site Scripting): Kullanıcı girdilerini sanitize edin ve uygun başlıkları (Content-Security-Policy) kullanın. JWT'leri HTTP-only çerezlerde saklayarak XSS'in etkisini azaltın.
    • CSRF (Cross-Site Request Forgery): CSRF token'ları kullanın veya SameSite=Lax/Strict çerez politikaları uygulayın.
    • Yanlış Konfigürasyon: Güvenli varsayılan değerler kullanın, hassas bilgileri (veritabanı şifreleri) kaynak kontrolüne dahil etmeyin.
    • Man-in-the-Middle (MITM): Her zaman HTTPS kullanın.
    • Kaba Kuvvet ve Sözlük Saldırıları: Rate limiting, hesap kilitleme ve Captcha kullanın.
    • Parola Yeniden Kullanımı: Kullanıcıları zayıf ve daha önce ihlal edilmiş parolaları kullanmaktan caydırın (Have I Been Pwned API'si entegrasyonu gibi).

Soru 30:
How Does CompletableFuture Work, and When Would You Use It?

CompletableFuture'ın Java'da eş zamansız programlamayı nasıl desteklediğini açıklayın.

  • Future ile CompletableFuture arasındaki fark.
  • thenApply(), thenCompose() ve thenCombine() kullanımı.
  • exceptionally() ve handle() kullanarak hataları ele alma.
  • Birden fazla bağımsız API çağrısını birleştirme.
  • Thread havuzlarını yönetme ve bloklama işlemlerinden kaçınma.

Senaryo: Bir API'nin üç bağımsız mikroservisten veri alması gerekiyor. Bunları eş zamanlı olarak nasıl çağırır ve yanıt sürelerini gereksiz yere artırmadan yanıtlarını nasıl birleştirirsiniz?

CompletableFuture, Java 8 ile tanıtılan ve eş zamansız (asynchronous) programlamayı kolaylaştıran güçlü bir araçtır. Gelecekte tamamlanacak bir işlemin sonucunu temsil eder ve zincirleme (chaining) ve birleştirme (composition) gibi özellikler sunarak callback cehennemini (callback hell) önlemeye yardımcı olur.

Future ile CompletableFuture Arasındaki Fark:

Özellik Future CompletableFuture
API Daha temel, eş zamansız işlem sonucunu temsil eder. Daha zengin, eş zamansız işlemleri oluşturma, birleştirme ve yönetme yeteneği sunar.
Zincirleme (Chaining) Doğrudan zincirleme veya dönüştürme yeteneği yoktur. Bloklama get() çağrıları gerektirebilir. Zincirleme metotları (thenApply, thenCompose, thenAccept) ile non-blocking dönüşümler ve ardışık işlemler kolayca yapılabilir.
Birleştirme (Composition) Birden fazla Future sonucunu birleştirmek karmaşıktır (genellikle ExecutorService.invokeAll() ve bloklama çağrıları). thenCombine, allOf, anyOf gibi metotlarla birden fazla eş zamansız işlemi birleştirmek kolaydır.
Manuel Tamamlama Dışarıdan bir işlemle tamamlanamaz. Sadece Callable veya Runnable tarafından tamamlanır. complete(), completeExceptionally() metotları ile harici olarak tamamlanabilir. Bu, reaktif programlama desenleri için önemlidir.
Hata Yönetimi get() metodu bir istisna fırlatır. Daha az esnek hata yönetimi. exceptionally(), handle() gibi metotlarla akış içinde hatayı yakalama ve işleme yeteneği.
Blocking Genellikle sonucunu almak için get() çağrısı bloklama yapar. Bloklama yapmayan metotlar sunar. Bloklama ancak join() veya get() çağrıldığında gerçekleşir.

thenApply(), thenCompose() ve thenCombine() Kullanımı:

  • thenApply(Function<? super T, ? extends U> fn): Bir CompletableFuture tamamlandığında, sonucunu senkron (aynı thread'de devam edebilir) olarak başka bir türe dönüştürür. Geriye bir CompletableFuture<U> döndürür. 
    
CompletableFuture<String> greetingFuture = CompletableFuture.supplyAsync(() -> "Hello")
    .thenApply(s -> s + " World!"); // "Hello World!"
  • thenCompose(Function<? super T, ? extends CompletionStage<U>> fn): Bir CompletableFuture tamamlandığında, sonucunu kullanarak yeni bir CompletableFuture başlatır ve bu yeni future'ın sonucunu döndürür. Bu, bir eş zamansız işlemin sonucuna bağımlı olan başka bir eş zamansız işlemi zincirlemek için kullanılır (flattening nested Futures). 
    
// Kullanıcı ID'si ile kullanıcı adını, sonra kullanıcı adıyla e-postayı getirme
CompletableFuture<String> userEmailFuture = CompletableFuture.supplyAsync(() -> "user123") // userId
    .thenCompose(userId -> CompletableFuture.supplyAsync(() -> getUserName(userId))) // userName
    .thenCompose(userName -> CompletableFuture.supplyAsync(() -> getUserEmail(userName))); // userEmail
  • thenCombine(CompletionStage<? extends U> other, BiFunction<? super T, ? super U, ? extends V> fn): İki bağımsız CompletableFuture tamamlandığında, her ikisinin sonuçlarını alır ve bunları birleştirip yeni bir sonuca dönüştürür. 
    
CompletableFuture<String> future1 = CompletableFuture.supplyAsync(() -> "Hello");
CompletableFuture<String> future2 = CompletableFuture.supplyAsync(() -> "World");

CompletableFuture<String> combinedFuture = future1.thenCombine(future2, (s1, s2) -> s1 + " " + s2); // "Hello World"
  • thenAccept(Consumer<? super T> action): Bir CompletableFuture tamamlandığında sonucunu alır ve bir eylem gerçekleştirir (void dönüş tipi). Yanıtı işlemek ancak yeni bir değer döndürmemek için kullanılır.
  • allOf(CompletableFuture<?>... cfs): Tüm verilen CompletableFuture'lar tamamlandığında tamamlanan bir CompletableFuture<Void> döndürür. Bağımsız paralel işlemlerin hepsinin bitmesini beklemek için idealdir.
  • anyOf(CompletableFuture<?>... cfs): Verilen CompletableFuture'lardan herhangi biri tamamlandığında tamamlanan bir CompletableFuture<Object> döndürür. İlk tamamlanan future'ın sonucunu döndürür.

exceptionally() ve handle() Kullanarak Hataları Ele Alma:

  • exceptionally(Function<Throwable, ? extends T> fn): Bir önceki CompletableFuture bir istisna fırlattığında çağrılır. İstisnayı yakalar ve bir yedek değer döndürerek akışın devam etmesini sağlar. 
    
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
    if (Math.random() < 0.5) throw new RuntimeException("Error!");
    return "Success";
}).exceptionally(ex -> {
    System.err.println("Hata oluştu: " + ex.getMessage());
    return "Fallback Value"; // Hata durumunda dönecek değer
});
  • handle(BiFunction<? super T, Throwable, ? extends U> fn): Bir önceki CompletableFuture ister başarılı ister hatalı tamamlansın, her iki durumda da çağrılır. Hem sonuç hem de istisna parametre olarak gelir, böylece hata olup olmadığını kontrol edebilir ve duruma göre işlem yapabilirsiniz. Daha esnek hata işleme sağlar. 
    
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
    if (Math.random() < 0.5) throw new RuntimeException("Error!");
    return "Success";
}).handle((result, ex) -> {
    if (ex != null) {
        System.err.println("Hata oluştu: " + ex.getMessage());
        return "Handled Error";
    }
    return result + " (Handled)";
});

Thread Havuzlarını Yönetme ve Bloklama İşlemlerinden Kaçınma:

  • CompletableFuture'ın supplyAsync() ve runAsync() metotları, varsayılan olarak ForkJoinPool.commonPool()'u kullanır. Ancak, I/O yoğun veya uzun süreli bloklama işlemleri yaparken kendi özel ExecutorService'inizi sağlamak önemlidir. Bu, ortak havuzu bloklamaktan kaçınır ve iş yükünü daha iyi yönetmenizi sağlar.
  • supplyAsync(Supplier<U> supplier, Executor executor) veya thenApplyAsync(Function<? super T, ? extends U> fn, Executor executor) gibi metotlar ile özel thread havuzu belirtilebilir.

Senaryo: Üç Bağımsız Mikroservisten Veri Alıp Yanıtları Birleştirme:

Bir API'nin, UserService'den kullanıcı bilgilerini, ProductService'den ürün detaylarını ve RecommendationService'den önerileri eş zamanlı olarak alıp bunları birleştirmesi gerektiğini varsayalım.


                import java.util.concurrent.*;

                public class ApiAggregator {

                    // Özel thread havuzları tanımlıyoruz
                    private final ExecutorService userServiceExecutor = Executors.newFixedThreadPool(2);
                    private final ExecutorService productServiceExecutor = Executors.newFixedThreadPool(2);
                    private final ExecutorService recommendationServiceExecutor = Executors.newFixedThreadPool(2);

                    public CompletableFuture<ApiResponse> getAggregatedData(String userId, String productId) {

                        // 1. Kullanıcı bilgilerini eş zamansız olarak al
                        CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(() -> {
                            System.out.println("Fetching User in " + Thread.currentThread().getName());
                            // Simüle edilmiş servis çağrısı
                            try { Thread.sleep(200); } catch (InterruptedException e) {}
                            return new User(userId, "John Doe");
                        }, userServiceExecutor).exceptionally(ex -> {
                            System.err.println("User Service hatası: " + ex.getMessage());
                            return new User(userId, "Guest"); // Fallback
                        });

                        // 2. Ürün detaylarını eş zamansız olarak al
                        CompletableFuture<Product> productFuture = CompletableFuture.supplyAsync(() -> {
                            System.out.println("Fetching Product in " + Thread.currentThread().getName());
                            // Simüle edilmiş servis çağrısı
                            try { Thread.sleep(300); } catch (InterruptedException e) {}
                            return new Product(productId, "Awesome Gadget", 99.99);
                        }, productServiceExecutor).exceptionally(ex -> {
                            System.err.println("Product Service hatası: " + ex.getMessage());
                            return new Product(productId, "N/A", 0.0); // Fallback
                        });

                        // 3. Önerileri eş zamansız olarak al
                        CompletableFuture<Recommendation> recommendationFuture = CompletableFuture.supplyAsync(() -> {
                            System.out.println("Fetching Recommendation in " + Thread.currentThread().getName());
                            // Simüle edilmiş servis çağrısı
                            try { Thread.sleep(250); } catch (InterruptedException e) {}
                            return new Recommendation("Buy more awesome gadgets!");
                        }, recommendationServiceExecutor).exceptionally(ex -> {
                            System.err.println("Recommendation Service hatası: " + ex.getMessage());
                            return new Recommendation("No recommendations available."); // Fallback
                        });

                        // Tüm Future'lar tamamlandığında sonuçları birleştir
                        return CompletableFuture.allOf(userFuture, productFuture, recommendationFuture)
                            .thenApply(v -> {
                                // allOf, bir CompletableFuture<Void> döndürdüğü için v parametresi kullanılmaz.
                                // Sonuçlar, ayrı ayrı Future nesnelerinden alınır.
                                User user = userFuture.join(); // join() bloklama yapar ama burada zaten tamamlandı
                                Product product = productFuture.join();
                                Recommendation recommendation = recommendationFuture.join();

                                return new ApiResponse(user, product, recommendation);
                            });
                    }

                    // Yardımcı sınıflar
                    static class User { String id, name; public User(String id, String name) { this.id = id; this.name = name; } }
                    static class Product { String id, name; double price; public Product(String id, String name, double price) { this.id = id; this.name = name; this.price = price; } }
                    static class Recommendation { String text; public Recommendation(String text) { this.text = text; } }
                    static class ApiResponse { User user; Product product; Recommendation recommendation; public ApiResponse(User user, Product product, Recommendation recommendation) { this.user = user; this.product = product; this.recommendation = recommendation; } }

                    public static void main(String[] args) throws ExecutionException, InterruptedException {
                        ApiAggregator aggregator = new ApiAggregator();
                        long startTime = System.currentTimeMillis();

                        CompletableFuture<ApiResponse> resultFuture = aggregator.getAggregatedData("user1", "prodA");

                        // Ana thread'in bloklamamasını sağlamak için join() veya get() kullanırız.
                        // main thread'in eş zamansız işlemin bitmesini beklemesi gerekiyorsa kullanılır.
                        ApiResponse response = resultFuture.join();
                        long endTime = System.currentTimeMillis();

                        System.out.println("\nAggregated Response: " + response.user.name + ", " + response.product.name + ", " + response.recommendation.text);
                        System.out.println("Total time: " + (endTime - startTime) + "ms");

                        // ExecutorService'leri kapatmayı unutmayın
                        aggregator.userServiceExecutor.shutdown();
                        aggregator.productServiceExecutor.shutdown();
                        aggregator.recommendationServiceExecutor.shutdown();
                    }
                }

Bu senaryoda, üç servis çağrısı paralel olarak yapılır. En uzun süren çağrı (300ms) toplam yanıt süresini belirler, ki bu da ardışık çağrılara göre önemli bir iyileşmedir (200+300+250 = 750ms yerine ~300ms).

How Would You Troubleshoot an OutOfMemoryError in a Production Application?

Üretim uygulamasında bir OutOfMemoryError'u tanımlama yaklaşımınızı açıklayın.

Aşağıdaki konuları inceleyin:

  • Heap kullanımı ve garbage collection günlüklerini analiz etme.
  • Heap dump'ları alma ve inceleme.
  • Bellek sızıntılarını ve beklenmedik şekilde tutulan nesneleri tanımlama.
  • Büyük koleksiyonları, önbellekleri ve statik referansları araştırma.
  • Heap yapılandırmasını ve garbage collector davranışını gözden geçirme.

Senaryo: Bir Spring Boot uygulaması dağıtımdan sonra normal çalışıyor ancak birkaç saat sonra OutOfMemoryError ile çöküyor. Temel nedeni nasıl belirler ve kalıcı bir düzeltme nasıl uygularsınız?

Üretim ortamında bir OutOfMemoryError (OOM) ile karşılaşmak, kritik bir performans ve stabilite sorunudur. OOM genellikle uygulamanın heap belleğini tamamen tüketmesi sonucu ortaya çıkar. Etkili bir sorun giderme süreci, sorunun kök nedenini bulmak ve kalıcı bir çözüm uygulamak için sistematik adımlar gerektirir.

Genel Yaklaşım ve Adımlar:

1. Anında Müdahale ve Bilgi Toplama:

  • Uygulama Yeniden Başlatma: Genellikle hızlı bir çözüm olarak uygulamayı yeniden başlatmak gerekebilir, ancak bu sadece semptomu geçici olarak giderir.
  • Logları Kontrol Etme: Uygulama logları ve sunucu loglarında (örneğin, catalina.out, /var/log/messages) OutOfMemoryError mesajının tam metnini bulun. Hata mesajı genellikle hangi heap alanının (Java Heap Space, Metaspace, GC Overhead Limit Exceeded) dolduğunu belirtir, bu da ilk ipucudur.
  • GC Loglarını Etkinleştirme: Eğer henüz etkin değilse, JVM başlatma parametrelerine GC günlüklerini ekleyin (örneğin, -Xlog:gc*:file=gc.log:time,level,tags -XX:+PrintGCDetails -XX:+PrintGCDateStamps). Bu, GC davranışını ve heap kullanımını anlamak için çok önemlidir.
  • Heap Dump Alma (Otomatik veya Manuel): OOM oluştuğunda otomatik olarak heap dump almak için JVM'e şu parametreleri ekleyin: -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/to/dumps/heapdump.hprof. Manuel olarak da jmap -dump:format=b,file=heapdump.hprof <pid> komutu ile heap dump alınabilir.

2. Heap Kullanımı ve Garbage Collection Günlüklerini Analiz Etme:

  • GC Loglarını İnceleme Araçları: GCViewer, GCeasy, IBM Pattern Analyzer gibi araçları kullanarak GC günlüklerini analiz edin.
  • Anahtar Metrikler:
    • GC Sıklığı ve Süresi: GC'nin çok sık çalışıp çalışmadığını veya uzun süreli duraklamalara (pause time) neden olup olmadığını kontrol edin.
    • Heap Kullanım Trendleri: Her GC sonrası heap boyutunun düşmesi beklenir. Eğer heap sürekli büyüyor ve GC sonrasında serbest bırakılan bellek miktarı çok azsa, bu bir bellek sızıntısına işaret edebilir.
    • Promotion Rate: Nesnelerin Young Generation'dan Old Generation'a ne kadar hızlı terfi ettiğini gözlemleyin. Hızlı terfi, Young Generation'ın yetersiz veya çok fazla kısa ömürlü nesnenin oluştuğunu gösterebilir.
    • OOM Türü: java.lang.OutOfMemoryError: Java heap space (genç veya yaşlı nesneler), java.lang.OutOfMemoryError: Metaspace (sınıf meta verileri), java.lang.OutOfMemoryError: GC overhead limit exceeded (GC çok zaman harcıyor ve çok az bellek kurtarıyor).

3. Heap Dump'ları Alma ve İnceleme:

  • Araçlar: Eclipse Memory Analyzer (MAT) veya VisualVM gibi araçları kullanarak .hprof dosyasını açın.
  • Şüpheli Nesneleri Bulma:
    • Leak Suspects (Sızıntı Şüphelileri): MAT, otomatik olarak olası bellek sızıntılarını ve bunlara neden olan nesneleri analiz eder ve raporlar.
    • Top Consumers (En Büyük Tüketiciler): Heap'te en çok yer kaplayan nesnelerin listesini ve bunların referans ağaçlarını inceleyin. H
    • Dominator Tree: Hangi nesnelerin diğer nesneleri domine ettiğini (yani, o nesne olmadan diğer nesnelerin GC edilemeyeceğini) gösterir. Bu, bellek sızıntısının kök nedenini bulmak için çok güçlü bir araçtır.
    • Duplicate Classes: Uygulama sunucularında veya farklı classloader'larda aynı sınıftan birden fazla kez yüklenmesi durumlarını kontrol edin, bu da Metaspace OOM'a yol açabilir.

4. Bellek Sızıntılarını ve Beklenmedik Şekilde Tutulan Nesneleri Tanımlama:

  • Büyük Koleksiyonlar/Önbellekler: Uygulamanın kullandığı List, Map, Set gibi koleksiyonların veya harici önbelleklerin (Guava Cache, Caffeine) beklenenden daha fazla nesne tuttuğunu veya gerektiği gibi temizlenmediğini kontrol edin.
  • Statik Referanslar: Uygulama kapanışında veya yeniden dağıtımında temizlenmeyen statik alanlardaki nesneler. Özellikle uygulama sunucularında (Tomcat, JBoss) sıkça karşılaşılan bir sorundur.
  • ThreadLocal Sızıntıları: ThreadLocal değişkenleri, thread havuzları kullanılırken düzgün bir şekilde temizlenmezse bellek sızıntılarına yol açabilir. Her isteğin sonunda threadLocal.remove() çağrısı yapılmalıdır.
  • Olay Dinleyicileri (Event Listeners) ve Callback'ler: Bir objenin yaşam döngüsü bitmesine rağmen başka bir objeye referans vermeye devam etmesi.

5. Heap Yapılandırmasını ve Garbage Collector Davranışını Gözden Geçirme:

  • Heap Boyutları (-Xmx, -Xms): Uygulamanın gereksinimlerine göre doğru heap boyutunu ayarlayın. Çok küçük olması OOM'a, çok büyük olması uzun GC duraklamalarına neden olabilir.
  • Young/Old Generation Oranları: -XX:NewRatio veya -Xmn ile genç ve yaşlı nesil boyutlarını ayarlayın. Uygulamanın nesne yaşam süresine göre optimize edilebilir.
  • Garbage Collector Seçimi:
    • Varsayılan GC (JDK 8'de Parallel, JDK 11'den itibaren G1) iyi bir başlangıç noktasıdır.
    • Düşük gecikme (latency) kritikse ZGC veya Shenandoah gibi daha gelişmiş GC'ler düşünülebilir (ancak daha fazla konfigürasyon ve maliyet gerektirebilir).
    • GC overhead limit exceeded hatası alıyorsanız, heap'in yetersiz olduğunu veya GC'nin çok verimsiz çalıştığını gösterir.

Senaryo: Spring Boot Uygulaması Dağıtımdan Sonra Birkaç Saat Sonra OOM ile Çöküyor:

Bu senaryo tipik bir bellek sızıntısına işaret eder, çünkü uygulama başlangıçta normal çalışıyor ancak zamanla bellek tüketimi artarak OOM'a neden oluyor.

Kök Nedeni Belirleme Adımları:

  1. GC Loglarını Etkinleştirin: Uygulamayı -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/opt/app/dumps/heapdump.hprof -Xlog:gc*:file=/opt/app/logs/gc.log:time,level,tags gibi parametrelerle yeniden başlatın.
  2. OOM'u Bekleyin (veya Tetikleyin): Uygulamanın tekrar çökmesini bekleyin. Heap dump otomatik olarak alınacak ve GC logları oluşacaktır.
  3. GC Loglarını İnceleyin:
    • gc.log dosyasını GCeasy gibi bir araçla analiz edin.
    • Beklenti: Heap kullanımı her GC döngüsü sonrası düşmeli.
    • Şüpheli durum: Eğer heap kullanımı sürekli artıyor ve GC'ler sonrasında bile serbest bırakılan bellek miktarı giderek azalıyorsa, bu belirgin bir bellek sızıntısı işaretidir. Old Generation'ın (yaşlı nesiller alanı) sürekli dolduğunu görebilirsiniz.
  4. Heap Dump'ı Analiz Edin (MAT ile):
    • heapdump.hprof dosyasını Eclipse Memory Analyzer (MAT) ile açın.
    • "Leak Suspects" Raporunu Kontrol Edin: MAT, genellikle bellek sızıntısına neden olan en olası nesneleri ve bunların neden tutulduğunu gösterir.
    • "Dominator Tree" ve "Top Consumers" Raporlarını İnceleyin: En büyük nesneleri ve onların referans yollarını (GC köklerine kadar) belirleyin. Bu, hangi nesnelerin beklenmedik bir şekilde bellekte tutulduğunu anlamanıza yardımcı olur. Örneğin, çok büyük bir ArrayList veya HashMap, veya beklenmedik statik alanlara referans veren nesneler görebilirsiniz.
    • Örnek Olası Kök Nedenler:
      • Düzgün kapatılmayan ThreadLocal'lar.
      • Sınırsız büyüyen bir önbellek (HashMap veya ConcurrentHashMap'e eklenen ve asla temizlenmeyen nesneler).
      • Veritabanı bağlantı havuzlarında sızan bağlantılar.
      • Düzgün iptal edilmeyen olay dinleyicileri veya RxJava/Reactor gibi reaktif akışlardaki abonelikler.
      • Loglama çerçevelerinin (Log4j, Logback) yanlış konfigürasyonu sonucu oluşan bellek sızıntıları.
  5. Kod İncelemesi: Heap dump analizinden elde ettiğiniz bilgilerle kodda ilgili kısımları inceleyin. Hangi nesnelerin referansları tarafından tutulduğunu anlayın.

Kalıcı Bir Düzeltme Uygulama:

  • Sızıntı Nedenini Giderin: Eğer sorun sınırsız büyüyen bir önbellekse, onu sınırlayın (LRU cache gibi) veya doğru TTL ile yapılandırın. Eğer ThreadLocal ise, threadLocal.remove() çağrısı eklendiğinden emin olun (özellikle Spring'in RequestContextHolder gibi yerlerde). Statik referanslar doğru temizlendiğinden emin olun.
  • Test Edin: Düzeltmeyi test ortamında (uzun süreli yük testleri ile) doğrulayın. Heap kullanımı ve GC loglarını izleyerek sızıntının giderildiğinden emin olun.
  • GC Ayarlarını Optimize Edin: Eğer bellek sızıntısı yoksa ancak heap boyutu yine de yetersizse, -Xmx değerini artırmayı düşünebilirsiniz. Ayrıca, uygulamanızın profiline uygun bir GC algoritması seçmek ve Young/Old Generation oranlarını ayarlamak performansı iyileştirebilir.
  • Gözlemlenebilirlik (Observability) Arttırın: Üretim ortamında sürekli bellek kullanımı ve GC metriklerini izlemek için APM (Application Performance Monitoring) araçları (Dynatrace, New Relic, AppDynamics) veya Prometheus/Grafana gibi çözümler kullanın. Bu, sorunların erken tespit edilmesine yardımcı olur.
Soru 32:
What Is the Difference Between HashMap and ConcurrentHashMap?

Bu koleksiyonların thread güvenliği, performansı ve eş zamanlı erişim altındaki davranışları açısından nasıl farklılaştığını açıklayın.

  • HashMap, harici senkronizasyon olmadan birden fazla thread tarafından eş zamanlı değişiklik için tasarlanmamıştır.
  • ConcurrentHashMap, dahili senkronizasyon mekanizmalarıyla eş zamanlı erişimi destekler.

ConcurrentHashMap'deki null anahtar ve null değer kısıtlamalarını anlayın. putIfAbsent() ve computeIfAbsent() gibi atomik işlemleri tartışın.

Senaryo: Birden fazla thread, paylaşılan bir bellek içi önbelleği güncelliyor. Uygun koleksiyonu nasıl seçer ve yarış koşullarını nasıl önlersiniz?

HashMap ve ConcurrentHashMap, Java'daki Map arayüzünün iki farklı implementasyonudur ve temel farkları thread güvenliği ve eş zamanlı erişim altındaki davranışlarındadır.

HashMap:

  • Thread Güvenliği: Thread güvenli değildir. Birden fazla thread aynı HashMap üzerinde eş zamanlı olarak yazma veya yapısal değişiklik (boyutlandırma, eleman ekleme/çıkarma) yapmaya çalışırsa, yarış koşulları (race conditions), sonsuz döngüler veya tutarsız veriler oluşabilir. Okuma işlemleri genellikle güvendir ancak yazma sırasında okuma da tutarsız veri görebilir.
  • Performans: Tek thread'li ortamlarda veya dışarıdan senkronize edildiğinde (Collections.synchronizedMap(new HashMap<>()) gibi), yüksek performans sunar çünkü herhangi bir senkronizasyon mekanizması içermez.
  • Null Anahtar/Değer: Hem null anahtarlara hem de null değerlere izin verir.
  • Kullanım: Yalnızca tek thread tarafından erişilen veya tamamen dışarıdan senkronize edilen senaryolar için uygundur.

ConcurrentHashMap:

  • Thread Güvenliği: Thread güvenlidir. Birden fazla thread'in eş zamanlı olarak okuma ve yazma işlemlerini sorunsuz bir şekilde gerçekleştirmesine izin verir. Bunu, dahili olarak parçalı kilitleme (segment locking veya bucket-level locking) ve CAS (Compare-And-Swap) işlemleri gibi mekanizmalarla başarır.
  • Performans: Yüksek eş zamanlılık altında bile iyi performans gösterir. Java 8'den itibaren, Node tabanlı bir yapıya geçerek synchronized blokları yerine CAS operasyonlarını ve volatile anahtar kelimesini daha yoğun kullanır. Bu, genel kilitleme yerine sadece ilgili "bucket" veya "node" üzerinde kilitleme yaparak okuma ve yazma işlemlerinin çoğunun eş zamanlı çalışmasına olanak tanır.
  • Null Anahtar/Değer: Null anahtarlara veya null değerlere izin vermez. Bunun nedeni, null değerin bir anahtarın bulunmadığı veya bir değerin hesaplanmadığı (örneğin computeIfAbsent'te) durumları belirsiz hale getirmesidir.
  • Kullanım: Birden fazla thread tarafından eş zamanlı olarak erişilen ve değiştirilen tüm senaryolar için uygundur (örneğin, önbellekler, sayaçlar, paylaşılan konfigürasyonlar).

Dahili Çalışma Mekanizması Evrimi (Java 7 vs. Java 8+):

  • Java 7: Segment adı verilen fixed-size diziler (yaklaşık 16 segment) kullanıyordu. Her Segment kendi kilidine sahipti. Yazma işlemi yalnızca ilgili segmenti kilitlerken, diğer segmentlere eş zamanlı erişim mümkündü. Okuma işlemleri kilit gerektirmiyordu (volatile kullanarak).
  • Java 8 ve Sonrası: Node dizisi (hash tablosunun kendisi) ve her düğümde (bucket) bir synchronized blok veya volatile ve CAS işlemleri kullanır. Genellikle sadece belirli bir bucket'taki bağlantılı liste veya kırmızı-siyah ağaç üzerinde kilitlenir. Bu, daha ince taneli kilitleme (fine-grained locking) sağlayarak daha yüksek eş zamanlılık sunar.

Atomik İşlemler (putIfAbsent() ve computeIfAbsent()):

ConcurrentHashMap, yaygın eş zamanlı kullanım durumları için atomik (atomic) işlemler sunar. Bu işlemler, birden fazla adımı tek bir bölünmez operasyon olarak gerçekleştirir ve dışarıdan ek senkronizasyona ihtiyaç duymaz:

  • V putIfAbsent(K key, V value): Eğer belirtilen anahtar zaten bir değerle eşleşiyorsa, mevcut değeri döndürür. Aksi takdirde, anahtarı belirtilen değerle eşleştirir ve null döndürür. Bu işlem atomiktir. 
    
ConcurrentHashMap<String, Integer> cache = new ConcurrentHashMap<>();
cache.putIfAbsent("counter", 0); // Sadece "counter" anahtarı yoksa 0 ekler
cache.putIfAbsent("counter", 10); // "counter" zaten var (0), 0 döner, 10 eklenmez
  • V computeIfAbsent(K key, Function<? super K, ? extends V> mappingFunction): Eğer belirtilen anahtar (key) zaten bir değerle eşleşiyorsa, mevcut değeri döndürür. Aksi takdirde, anahtarı mappingFunction tarafından hesaplanan değeriyle eşleştirir ve bu değeri döndürür. Bu işlem de atomiktir. Bu, bir değeri hesaplamanın maliyetli olduğu ve yalnızca ihtiyaç duyulduğunda hesaplanması gereken senaryolar için çok kullanışlıdır. 
    
ConcurrentHashMap<String, String> userCache = new ConcurrentHashMap<>();
// userCache.get("user123") -> null ise, lambda çalıştırılır ve sonucu eklenir.
String userName = userCache.computeIfAbsent("user123", k -> fetchUserNameFromDB(k));

Senaryo: Birden Fazla Thread Paylaşılan Bellek İçi Önbelleği Güncelliyor. Uygun Koleksiyonu Seçme ve Yarış Koşullarını Önleme:

Bu senaryo için açıkça ConcurrentHashMap en uygun seçimdir.

  1. Koleksiyon Seçimi:
    • HashMap: Kesinlikle hayır. Birden fazla thread eş zamanlı olarak yazma yaparsa, önbellek bozulur ve beklenmedik davranışlar (sonsuz döngüler, yanlış değerler) ortaya çıkar.
    • Collections.synchronizedMap(new HashMap<>()): Bu, tüm Map üzerinde bir kilitleme (intrinsic lock) yapar. Bu, Map'i thread güvenli hale getirir, ancak her okuma ve yazma işlemi için tüm Map'i kilitler. Yüksek eş zamanlılık durumunda performans darboğazı yaratır. ConcurrentHashMap'e göre daha az ölçeklenebilirdir.
    • ConcurrentHashMap: En iyi seçimdir. İnce taneli kilitleme ve atomik operasyonlar sayesinde, birden fazla thread'in eş zamanlı olarak okuma ve yazma işlemlerini yüksek verimlilikle gerçekleştirmesine olanak tanır.
  2. Yarış Koşullarını Önleme:
    • ConcurrentHashMap'in kendisi, temel put(), get(), remove() gibi işlemler için dahili olarak yarış koşullarını önler.
    • Ancak, eğer değerin okunup değiştirilip tekrar yazıldığı "read-modify-write" gibi bileşik işlemler yapılıyorsa (örneğin, bir sayaçı artırma: cache.get(key) + 1 ve cache.put(key, newValue)), bu işlemlerin de atomik olduğundan emin olmak gerekir. Bu durumda ConcurrentHashMap'in atomik metotları kullanılmalıdır:
      • Sayaç Artırma: cache.compute(key, (k, v) -> v == null ? 1 : v + 1); veya cache.merge(key, 1, Integer::sum);
      • Değerin Yalnızca Mevcut Değilse Ekleme: cache.putIfAbsent(key, initialValue);
      • Değeri Yalnızca Mevcut Değilse Hesaplayıp Ekleme: cache.computeIfAbsent(key, k -> expensiveCalculation(k));

Özetle, paylaşılan bellek içi önbellek için ConcurrentHashMap'i seçmeli ve bileşik işlemler için putIfAbsent(), computeIfAbsent(), compute(), merge() gibi atomik metotlarını kullanmalısınız.

Soru 33:
How Does @Transactional Work Internally in Spring?

Spring'in @Transactional aracılığıyla veritabanı işlemlerini nasıl yönettiğini açıklayın.

  • Bildirimsel (declarative) işlem yönetimi ve proxy tabanlı müdahale.
  • REQUIRED ve REQUIRES_NEW gibi işlem yayılım modları (propagation modes).
  • İzolasyon seviyeleri (isolation levels) ve geri alma kuralları (rollback rules).
  • Kendi kendine çağırma (self-invocation) sınırlamaları.
  • İşlem sınırları ve bağlantı yönetimi.

Senaryo: @Transactional ile açıklama eklenmiş bir metot, aynı sınıfta başka bir metodu çağırıyor ancak beklenen işlem davranışı gerçekleşmiyor. Bunu nasıl gidereceksiniz?

Spring'deki @Transactional anotasyonu, bildirimsel (declarative) işlem yönetiminin temelini oluşturur. Bu, geliştiricilerin işlem mantığını doğrudan iş kodlarına yazmak yerine, anotasyonlar aracılığıyla belirtebilmesini sağlar. Spring, bu anotasyonları kullanarak arka planda karmaşık işlem yönetimini otomatik olarak halleder.

1. Bildirimsel İşlem Yönetimi ve Proxy Tabanlı Müdahale:

  • AOP (Aspect-Oriented Programming): Spring'in işlem yönetimi, Aspect-Oriented Programming (AOP) prensiplerine dayanır. @Transactional anotasyonunu bir sınıf veya metod üzerine koyduğunuzda, Spring bu sınıf için çalışma zamanında bir proxy (vekil) oluşturur.
  • Proxy'nin Rolü: Uygulama kodunuzdaki metot çağrıları doğrudan orijinal bean'e değil, bu proxy'ye yapılır. Proxy, orijinal metot çağrılmadan önce ve sonra ek işlem mantığını (işlem başlatma, commit etme, geri alma) ekler.
  • Müdahale (Interception):
    • Metot çağrılmadan önce: Proxy bir veritabanı işlemi başlatır, bağlantıyı alır ve işlem özelliklerini (yayılım, izolasyon vb.) ayarlar.
    • Metot çağrıldıktan sonra (başarılı): Proxy işlemi commit eder ve bağlantıyı serbest bırakır.
    • Metot çağrıldıktan sonra (hata): Eğer metotdan kontrol edilmemiş bir istisna (RuntimeException) fırlatılırsa, proxy işlemi geri alır (rollback) ve bağlantıyı serbest bırakır.
  • Proxy Türleri:
    • JDK Dynamic Proxy: Eğer hedef sınıf bir arayüz (interface) implemente ediyorsa, Spring varsayılan olarak JDK dinamik proxy'lerini kullanır.
    • CGLIB Proxy: Eğer hedef sınıf bir arayüz implemente etmiyorsa (veya proxyTargetClass=true olarak ayarlanmışsa), Spring CGLIB proxy'lerini kullanır. CGLIB, bir sınıfın alt sınıfını oluşturarak çalışır.

2. İşlem Yayılım Modları (Propagation Modes):

Bir metodun zaten devam eden bir işlem bağlamında nasıl davranacağını belirler. En yaygın olanları:

  • REQUIRED (Varsayılan):
    • Eğer zaten bir işlem varsa, bu işlemi kullanır.
    • Eğer bir işlem yoksa, yeni bir işlem başlatır.
  • REQUIRES_NEW:
    • Her zaman yeni, bağımsız bir işlem başlatır.
    • Eğer zaten bir işlem varsa, mevcut işlemi askıya alır ve yeni işlemi başlatır. Yeni işlem kendi içinde commit edilir veya geri alınır, dış işlemden bağımsızdır.
  • SUPPORTS: Eğer bir işlem varsa, onu kullanır. Yoksa, işlemsel olmayan bir şekilde devam eder.
  • NOT_SUPPORTED: Eğer bir işlem varsa, onu askıya alır ve işlemsel olmayan bir şekilde devam eder.
  • NEVER: Eğer bir işlem varsa istisna fırlatır.
  • MANDATORY: Eğer bir işlem yoksa istisna fırlatır.
  • NESTED: JDBC'deki "savepoint"lere benzer. Bir dış işlem varsa, bu işlem içinde iç içe bir işlem başlatır.

3. İzolasyon Seviyeleri (Isolation Levels) ve Geri Alma Kuralları (Rollback Rules):

  • İzolasyon Seviyeleri: Veritabanı işlemlerinin birbirini ne kadar etkileyeceğini (dirty reads, non-repeatable reads, phantom reads gibi sorunları önleme) belirler.
    • DEFAULT (Veritabanının varsayılanını kullanır)
    • READ_UNCOMMITTED
    • READ_COMMITTED
    • REPEATABLE_READ
    • SERIALIZABLE
    Daha yüksek izolasyon seviyeleri daha fazla veri tutarlılığı sağlarken, eş zamanlılığı azaltır ve performans maliyetleri vardır.
  • Geri Alma Kuralları: Bir işlemde hangi istisnaların (exception) yakalandığında işlemin geri alınacağını (rollback) veya commit edileceğini belirler.
    • Varsayılan olarak, Spring RuntimeException ve Error'larda işlemi geri alır.
    • Checked Exception'larda (IOException gibi) işlemi commit eder.
    • Bu davranışı @Transactional(rollbackFor = MyCheckedException.class) veya @Transactional(noRollbackFor = MyRuntimeException.class) ile özelleştirebilirsiniz.

4. Kendi Kendine Çağırma (Self-Invocation) Sınırlamaları:

Bu, @Transactional ile ilgili en yaygın yanlış anlamalardan biridir.

  • Bir sınıf içinde, @Transactional ile anotasyonlu bir metot, aynı sınıfın başka bir metodu tarafından doğrudan çağrılırsa, işlem vekaleti (transactional proxy) devreye girmez. Yani, çağrılan metot üzerinde tanımlanan işlem özellikleri uygulanmaz.
  • Bunun nedeni, metot çağrısının doğrudan nesne referansı üzerinden yapılması ve Spring proxy'sinin araya girememesidir. Proxy, yalnızca dışarıdan (yani başka bir Spring bean'inden) yapılan çağrılar için etkinleşir.

@Service
public class MyService {

    @Transactional // Bu metot proxy tarafından sarmalanır
    public void publicMethod() {
        // İşlem burada başlar
        privateMethod(); // Kendi kendine çağırma - proxy atlanır!
        // İşlem burada devam eder, privateMethod() işlemsel özelliklerini almaz
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW) // Bu anotasyon uygulanmaz
    public void privateMethod() {
        // Bu metot işlemsel özellikler olmadan çalışır
    }
}

5. İşlem Sınırları ve Bağlantı Yönetimi:

  • İşlem Sınırı: @Transactional anotasyonlu metodun başlangıcında bir işlem başlar ve metodun sonunda (başarılı veya hatalı olarak) sona erer.
  • Bağlantı Yönetimi: Spring, veri kaynağı (DataSource) üzerinden bir veritabanı bağlantısı alır ve bu bağlantıyı işlem süresince kullanır. İşlem sonunda bağlantıyı havuza geri döndürür. Bu, JDBC kaynaklarının verimli bir şekilde kullanılmasını sağlar.
  • Hibernate/JPA Entegrasyonu: Spring, PlatformTransactionManager (örneğin, JpaTransactionManager) aracılığıyla JPA'daki EntityManager veya Hibernate'deki Session'ı yönetir. Aynı işlem içindeki tüm veritabanı operasyonları aynı EntityManager/Session ve dolayısıyla aynı veritabanı bağlantısını kullanır.

Senaryo: @Transactional Metot Aynı Sınıfta Başka Metodu Çağırıyor ve İşlem Davranışı Gerçekleşmiyor. Sorun Giderme:

Bu senaryo, yukarıda bahsedilen "kendi kendine çağırma (self-invocation) sınırlaması"nın klasik bir örneğidir.

Sorun Giderme Adımları:

  1. Logları İnceleyin: İşlemle ilgili hatalar veya uyarılar olup olmadığını kontrol edin. Ancak bu durumda Spring genellikle bir hata fırlatmaz, sadece işlem davranışı uygulanmaz.
  2. Spring AOP Debugging'i Etkinleştirin: Spring'in proxy oluşturup oluşturmadığını ve hangi metotların vekalet edildiğini görmek için AOP debug loglarını açın (logging.level.org.springframework.aop=DEBUG).
  3. Kod İncelemesi: @Transactional anotasyonunun nerede olduğunu ve hangi metotların çağrıldığını dikkatlice inceleyin. Eğer anotasyonlu bir metodun içinden aynı sınıfın başka bir anotasyonlu metodu çağrılıyorsa, bu sorunun kaynağıdır.

Çözüm Yolları:

Bu sorunu çözmek için birkaç yöntem vardır:

  • 1. İç Metodu Ayrı Bir Servise Taşıyın: En temiz ve tavsiye edilen çözümdür. İç metodun kendi işlem gereksinimleri varsa, onu ayrı bir Spring bean'ine (farklı bir @Service sınıfına) taşıyın. Bu durumda, dış metot bu yeni servisi çağıracak ve Spring proxy'si devreye girecektir. 
    
@Service
public class MyService {
    private final InnerService innerService;

    public MyService(InnerService innerService) {
        this.innerService = innerService;
    }

    @Transactional
    public void publicMethod() {
        // İşlem burada başlar
        innerService.privateMethod(); // Dış çağrı, proxy devreye girer
        // İşlem burada devam eder
    }
}

@Service
public class InnerService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void privateMethod() {
        // Yeni bir işlem başlatılır (publicMethod işlemi askıya alınır)
    }
}
  • 2. Kendini Enjekte Etme (Self-Injection): Aynı bean'i kendine enjekte ederek dolaylı bir çağrı yapabilirsiniz. Ancak bu yaklaşım bazıları tarafından kod kokusu (code smell) olarak görülebilir ve dikkatli kullanılmalıdır. 
    
@Service
public class MyService {
    @Autowired
    private MyService self; // Kendini enjekte etme

    @Transactional
    public void publicMethod() {
        // İşlem burada başlar
        self.privateMethod(); // Proxy üzerinden çağrı yapılır
        // İşlem burada devam eder
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void privateMethod() {
        // Yeni bir işlem başlatılır
    }
}
  • 3. TransactionTemplate Kullanımı: Eğer iç metodun işlem davranışını programatik olarak yönetmeniz gerekiyorsa, TransactionTemplate kullanabilirsiniz. Bu, bildirimsel yönetimden sapma anlamına gelir ancak kesin kontrol sağlar. 
    
@Service
public class MyService {
    private final TransactionTemplate transactionTemplate;

    public MyService(PlatformTransactionManager transactionManager) {
        this.transactionTemplate = new TransactionTemplate(transactionManager);
        this.transactionTemplate.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW);
    }

    @Transactional
    public void publicMethod() {
        // İşlem burada başlar
        transactionTemplate.execute(status -> {
            // privateMethod() içeriği buraya gelir
            // Yeni bir işlem başlatılır
            return null;
        });
        // İşlem burada devam eder
    }
}

İlk yöntem (iç metodu ayrı bir servise taşıma), kodu daha modüler ve anlaşılır hale getirdiği için genellikle tercih edilen çözümdür.

Soru 34:
How Would You Prevent Duplicate Message Processing in Kafka-Based Microservices?

Dağıtık mesajlaşma sistemleri bir mesajı birden fazla kez iletebilir, bu nedenle tüketicilerin yinelenen işlemeyi hesaba katması gerekir.

Aşağıdaki konuları tartışın:

  • İdempotent (tekrar işlenmeye dayanıklı) tüketici tasarımı.
  • Benzersiz olay tanımlayıcıları ve işlenmiş mesaj takibi.
  • Veritabanı işlemleri ve tekilleştirme (deduplication) kısıtlamaları.
  • Yeniden deneme ve "dead-letter topic" (DLQ) stratejileri.
  • Kafka üretici idempotence ve işlem yetenekleri.

Senaryo: Bir ödeme olayı iki kez iletiliyor ve bu da yinelenen işlemeye yol açıyor. Bir tüketici yeniden başlasa bile iş operasyonunun yalnızca bir kez uygulandığından nasıl emin olursunuz?

Kafka gibi dağıtık mesajlaşma sistemleri, mesajları "en az bir kez" (at-least-once) teslimat garantisiyle iletir. Bu, bir mesajın tüketiciye birden fazla kez teslim edilebileceği anlamına gelir. Bu nedenle, Kafka tabanlı mikroservislerde yinelenen mesaj işlemeyi önlemek kritik bir tasarım zorluğudur. Çözüm, idempotent (tekrar işlenmeye dayanıklı) tüketici tasarımı üzerine kuruludur.

1. İdempotent Tüketici Tasarımı:

  • Prensip: Bir işlem birden fazla kez yürütüldüğünde bile, sistemin durumunu yalnızca bir kez değiştiriyorsa veya aynı sonucu üretiyorsa, bu işlem idempotenttir.
  • Amaç: Tüketici, aldığı bir mesajı kaç kez işlediğinden bağımsız olarak, iş operasyonunun yalnızca bir kez etkili olmasını sağlamalıdır.

2. Benzersiz Olay Tanımlayıcıları (Unique Event Identifiers) ve İşlenmiş Mesaj Takibi:

  • Benzersiz Olay ID'si: Üretici, her mesaja benzersiz bir tanımlayıcı (örneğin, bir UUID veya iş bağlamında anlamlı bir ID) eklemelidir. Bu ID, mesajın anahtarı (key) olabilir veya mesajın payload'ında bir alan olarak bulunabilir (örneğin, paymentId, orderId). Bu ID, bir mesajın tekilliğini (uniqueness) doğrulamak için kullanılır.
  • İşlenmiş Mesaj Takibi (Deduplication Table): Tüketici servis, işlediği her benzersiz mesajın ID'sini bir veritabanında (veya kalıcı bir depoda) saklamalıdır.
    • Mesaj geldiğinde: Önce bu ID'nin zaten işlenip işlenmediğini kontrol eder.
    • Eğer işlenmişse: Mesajı göz ardı eder (tekrar işlemeyi önler).
    • Eğer işlenmemişse: Mesajı işler ve başarılı bir şekilde işledikten sonra ID'sini depoya kaydeder.

3. Veritabanı İşlemleri ve Tekilleştirme (Deduplication) Kısıtlamaları:

Tekilleştirme tablosu ve iş operasyonu aynı işlem içinde atomically (bölünmez bir şekilde) yapılmalıdır. Bu, "Transaction Outbox Pattern" veya "Atomic Write to Database and Message Processing" olarak bilinen yaklaşımlarla sağlanır.

  • Senaryo: Bir ödeme olayının işlenmesi, ödeme kaydını güncelleme ve işlenmiş mesaj ID'sini kaydetme adımlarını içeriyor.
  • Çözüm: Bu iki adımı aynı veritabanı işlemi (transaction) içinde birleştirin. 
    
@Transactional
public void processPaymentEvent(PaymentEvent event) {
    String eventId = event.getEventId();

    // 1. İşlenmiş mesajın daha önce kaydedilip kaydedilmediğini kontrol et
    if (processedMessageRepository.existsById(eventId)) {
        log.info("Duplicate event received, ignoring: {}", eventId);
        return;
    }

    // 2. İş operasyonunu gerçekleştir
    paymentService.updatePaymentStatus(event.getPaymentId(), event.getStatus());

    // 3. Mesajı işlenmiş olarak işaretle (aynı işlem içinde)
    processedMessageRepository.save(new ProcessedMessage(eventId));
}
  • Veritabanı Kısıtlaması: ProcessedMessage tablosundaki eventId alanı üzerinde UNIQUE kısıtlaması olmalıdır. Bu, aynı eventId ile birden fazla kayıt eklenmesini veritabanı seviyesinde engeller ve concurrency sorunlarında bile veri bütünlüğünü sağlar. İkinci denemede UniqueConstraintViolationException alınır ve işlem geri alınır (rollback).

4. Yeniden Deneme (Retry) ve "Dead-Letter Topic" (DLQ) Stratejileri:

  • Yeniden Deneme: Bir mesaj işlenirken geçici bir hata (örneğin, veritabanı bağlantı hatası, harici servis zaman aşımı) meydana gelirse, tüketici mesajı yeniden denemelidir.
    • Otomatik Yeniden Deneme: Spring Kafka gibi kütüphanelerle otomatik yeniden deneme mekanizmaları (üstel geri çekilme ile) yapılandırılabilir.
    • Gecikmeli Yeniden Deneme Konuları (Delayed Retry Topics): Mesaj, belirli bir gecikmeyle tekrar işlenmek üzere farklı bir Kafka konusuna (topic) gönderilebilir.
  • Dead-Letter Topic (DLQ): Bir mesaj belirli sayıda yeniden denemeye rağmen kalıcı bir hata (örneğin, veri formatı hatası, iş mantığı hatası) nedeniyle işlenemiyorsa, bu mesaj bir DLQ'ye gönderilmelidir.
    • DLQ'deki mesajlar manuel olarak incelenmeli, hata düzeltilmeli ve tekrar işlenmek üzere ana konuya yönlendirilmelidir.
    • Bu, hata veren mesajların ana tüketici kuyruğunu bloklamasını ve diğer sağlıklı mesajların işlenmesini engellemesini önler.

5. Kafka Üretici İdempotence ve İşlem Yetenekleri:

Kafka, "exactly-once" (tam olarak bir kez) semantiğini desteklemek için hem üretici hem de tüketici tarafında özellikler sunar.

  • Üretici İdempotence:
    • Prensip: Bir üretici, aynı mesajı birden fazla kez gönderse bile, Kafka broker'ları mesajın sadece bir kez kaydedilmesini garanti eder.
    • Uygulama: Kafka Producer'da enable.idempotence=true ayarlanarak etkinleştirilir. Bu, her üreticiye benzersiz bir Üretici Kimliği (Producer ID - PID) atanması ve her mesajın bir sıra numarası (sequence number) ile gönderilmesiyle çalışır. Broker'lar, aynı PID ve sıra numarasına sahip yinelenen mesajları filtreler.
    • Fayda: Üretici tarafındaki ağ hataları veya yeniden denemeler sonucu oluşan yinelenen mesajları broker seviyesinde engeller.
  • Kafka İşlemsel Yetenekleri (Transactional Capabilities - "Exactly-Once" Semantics):
    • Prensip: Bir üretici, birden fazla konuya (topic) mesaj gönderebilir ve bu mesajların hepsi bir işlem (transaction) kapsamında ya başarıyla gönderilir ya da hiçbiri gönderilmez. Ayrıca, bu işlem içinde tüketilen mesajların offset'leri de atomik olarak commit edilebilir.
    • Uygulama: transactional.id konfigürasyonu ile üreticide işlem yetenekleri etkinleştirilir. KafkaConsumer tarafında, isolation.level=read_committed ayarlanarak sadece commit edilmiş işlemlerin mesajlarını okuması sağlanır.
    • Fayda: Hem üretici hem de tüketici tarafında, birden fazla mesajın veya farklı servisler arasındaki entegrasyonların atomik olarak işlenmesini garanti eder.

Senaryo Çözümü: Tüketici Yeniden Başlasa Bile İş Operasyonunun Yalnızca Bir Kez Uygulandığından Nasıl Emin Olursunuz?

Bu senaryoda, ödeme olayının iki kez iletilmesi durumunda bile iş operasyonunun yalnızca bir kez uygulanmasını sağlamak için aşağıdaki adımları izleriz:

  1. Üretici İdempotence'i Etkinleştirin: Ödeme olayını üreten serviste Kafka Producer'ı enable.idempotence=true ile yapılandırın. Bu, üretici tarafındaki olası yinelenmeleri broker seviyesinde azaltır.
  2. Benzersiz Olay ID'si Kullanın: Her ödeme olayına benzersiz bir paymentEventId (UUID gibi) ekleyin.
  3. Veritabanı Tabanlı Tekilleştirme Uygulayın (Tüketici Tarafında):
    • Ödeme olayını işleyen tüketici servisinde, ödeme durumunu güncelleyen veritabanı işlemi ile paymentEventId'yi bir ProcessedEvents tablosuna kaydetme işlemini **aynı veritabanı işlemi (transaction)** içinde gerçekleştirin.
    • ProcessedEvents tablosunda paymentEventId üzerinde benzersiz bir kısıtlama (UNIQUE constraint) tanımlayın.
  4. İşleme Mantığı:
    • Tüketici bir PaymentEvent aldığında, ilk olarak paymentEventId'nin ProcessedEvents tablosunda olup olmadığını kontrol eder.
    • Eğer zaten varsa, bu bir yinelenen mesajdır ve sessizce göz ardı edilir (loglanır ancak işlem yapılmaz).
    • Yoksa, ödeme durumu güncellemesi ve paymentEventId'nin ProcessedEvents tablosuna eklenmesi aynı işlem içinde yapılır. Eğer bu iki adımdan biri başarısız olursa (örneğin, veritabanı hatası veya ikinci bir tüketici aynı anda aynı paymentEventId'yi eklemeye çalışırsa ve UNIQUE kısıtlaması ihlal edilirse), işlem tamamen geri alınır (rollback).
  5. Kafka Consumer Offset Yönetimi: Tüketici, mesajları işledikten ve veritabanı işlemine başarıyla commit ettikten sonra Kafka offset'ini commit etmelidir (enable.auto.commit=false ve manuel commit). Bu, "at-least-once" teslimat garantisi altında bile "tam olarak bir kez" işleme yaklaşımını sağlar.
  6. Yeniden Deneme ve DLQ: Geçici veritabanı hataları için yeniden deneme mekanizmaları ekleyin. Kalıcı hatalar için DLQ'ye göndererek manuel inceleme ve düzeltme yapın.

Bu yaklaşım, bir tüketici yeniden başlasa veya aynı mesaj Kafka tarafından iki kez gönderilse bile, benzersiz olay ID'si ve veritabanındaki UNIQUE kısıtlaması sayesinde iş operasyonunun sadece bir kez uygulanmasını sağlar.

Soru 35:
What Is the Difference Between REST and gRPC?

Dağıtık sistemlerde kullanılan iki yaygın iletişim yaklaşımını karşılaştırın.

  • REST genellikle kaynak odaklı uç noktalar ve JSON yükleri ile HTTP API'lerini kullanır.
  • gRPC, Protokol Tamponları (Protocol Buffers) kullanır ve güçlü türde hizmet sözleşmelerini destekler.

Performans, yük boyutu, akış (streaming), tarayıcı uyumluluğu ve hata ayıklamayı tartışın. Hizmetler arası iletişim gereksinimlerini açıklayın.

Senaryo: Sıkı gecikme gereksinimleri olan birkaç dahili mikroservis arasında iletişimi tasarlıyorsunuz. REST ve gRPC arasında seçiminizde hangi faktörler etkili olurdu?

REST (Representational State Transfer) ve gRPC (Google Remote Procedure Call), dağıtık sistemlerde servisler arası iletişim için kullanılan iki popüler mimari stildir. Her ikisinin de kendine özgü avantajları ve dezavantajları vardır ve seçim, projenin özel gereksinimlerine bağlıdır.

REST (Representational State Transfer):

  • İletişim Protokolü: Genellikle HTTP 1.1/2 kullanır.
  • Veri Biçimi: Çoğunlukla JSON veya XML kullanır.
  • Mimarisi: Kaynak odaklıdır. URL'ler (Uniform Resource Locators) kaynakları tanımlar ve HTTP metotları (GET, POST, PUT, DELETE) bu kaynaklar üzerinde gerçekleştirilecek işlemleri belirtir. "Stateless" (durumsuz) bir mimaridir.
  • Servis Sözleşmesi: Gayri resmi olarak HTTP metotları, URL yolları ve JSON/XML şemaları ile tanımlanır. Resmi bir IDL (Interface Definition Language) yoktur, bu yüzden genellikle dokümantasyon (Swagger/OpenAPI) kullanılır.
  • Tarayıcı Uyumluluğu: Doğrudan tarayıcılarla uyumludur, çünkü web tarayıcıları HTTP ve JSON'u doğal olarak destekler.
  • Öğrenme Eğrisi: Yaygınlığı ve basitliği nedeniyle öğrenmesi ve kullanması kolaydır.
  • Hata Ayıklama: HTTP ve JSON'un insan tarafından okunabilir olması sayesinde hata ayıklama genellikle daha kolaydır (cURL, Postman gibi araçlarla).
  • Akış (Streaming): HTTP 1.1'de tek yönlü akış (uzun süreli bağlantılar) zorludur, ancak HTTP 2 ile daha iyi desteklenir (ancak gRPC kadar doğal değildir).

gRPC (Google Remote Procedure Call):

  • İletişim Protokolü: Yüksek performanslı HTTP/2 üzerine kurulmuştur.
  • Veri Biçimi: Protokol Tamponları (Protocol Buffers - Protobuf) adı verilen ikili (binary) bir format kullanır. Protobuf, verileri sıkıştırılmış ve verimli bir şekilde serileştirir.
  • Mimarisi: RPC (Remote Procedure Call - Uzak Prosedür Çağrısı) odaklıdır. İstemci, uzak bir sunucudaki metodu çağırır gibi davranır.
  • Servis Sözleşmesi: .proto dosyaları kullanılarak Protobuf IDL ile tanımlanır. Bu dosyalar, servis arayüzlerini, metotlarını ve mesaj yapılarını açıkça belirtir. Bu tanım dosyalarından istemci ve sunucu tarafı kodları (stub'lar) otomatik olarak oluşturulabilir.
  • Tarayıcı Uyumluluğu: Doğrudan tarayıcılarla uyumlu değildir çünkü Protobuf ve HTTP/2'nin belirli özellikleri tarayıcılarda doğal olarak desteklenmez. gRPC-Web gibi bir proxy katmanı gereklidir.
  • Öğrenme Eğrisi: REST'e göre daha dik bir öğrenme eğrisine sahiptir, özellikle Protobuf IDL ve kod üretimi nedeniyle.
  • Hata Ayıklama: İkili format nedeniyle hata ayıklama daha zordur. Özel araçlar (gRPCurl, Wireshark ile Protobuf eklentisi) gerekebilir.
  • Akış (Streaming): HTTP/2'nin çoklamalı yapısı sayesinde tek yönlü (server-side streaming, client-side streaming) ve çift yönlü (bi-directional streaming) akışları doğal olarak destekler.

Karşılaştırma Tablosu:

Hizmetler Arası İletişim Gereksinimleri:

  • Verimlilik: Mikroservisler arasında ağ trafiğini ve gecikmeyi azaltmak kritik olabilir.
  • Güçlü Tip Güvenliği: Servisler arasındaki sözleşmelerin net olması ve derleme zamanında hataların yakalanabilmesi önemlidir.
  • Akış Yetenekleri: Büyük veri kümelerinin transferi veya gerçek zamanlı iletişim (örneğin, push bildirimleri) için akış desteği gerekebilir.
  • Geliştirme Hızı: Sözleşmelerin ve istemci/sunucu kodlarının hızlı bir şekilde oluşturulabilmesi.

Senaryo: Sıkı Gecikme Gereksinimleri Olan Dahili Mikroservis İletişimi:

Sıkı gecikme gereksinimleri olan dahili mikroservisler arası iletişim için gRPC, genellikle daha uygun bir seçim olacaktır. İşte etkili olacak faktörler:

  1. Performans ve Yük Boyutu:
    • gRPC, Protobuf'un ikili serileştirme formatı ve HTTP/2'nin multiplexing (çoklama) özellikleri sayesinde REST'e göre önemli ölçüde daha düşük gecikme ve daha küçük ağ yükleri sunar. Dahili servisler arasında bu, ağ bant genişliğinden tasarruf sağlar ve yanıt sürelerini kısaltır.
    • JSON'a göre daha az CPU kullanarak serileştirme/deserileştirme yapar.
  2. Güçlü Tip Güvenliği ve Servis Sözleşmesi:
    • Protobuf IDL (.proto dosyaları) sayesinde servisler arasındaki sözleşme açıkça tanımlanır. Bu, servisler arasında "zil sesinde" (compile-time) uyumsuzlukları yakalamaya yardımcı olur ve servis entegrasyonlarını daha güvenli hale getirir.
    • Otomatik kod üretimi, geliştiricilerin istemci ve sunucu kodunu elle yazma ihtiyacını azaltır, bu da hataları en aza indirir ve geliştirme hızını artırır (.proto dosyaları değiştiğinde otomatik olarak güncellenen kod).
  3. Akış (Streaming) Desteği:
    • Eğer mikroservisler arasında gerçek zamanlı veri akışı (örneğin, bir sensör veri akışı, canlı bildirimler veya uzun süreli hesaplamaların sonuçlarını adım adım gönderme) gerekiyorsa, gRPC'nin birinci sınıf akış desteği (tek yönlü ve çift yönlü) büyük bir avantajdır.
    • REST'in akış yetenekleri genellikle daha sınırlıdır ve daha karmaşık bir uygulama gerektirir.
  4. Dil Bağımsızlığı:
    • Protobuf IDL, dil bağımsızdır. Bu, farklı mikroservislerin farklı programlama dillerinde (Java, Go, Python, Node.js) yazılmış olsa bile sorunsuz bir şekilde iletişim kurabileceği anlamına gelir. Bu, büyük, poliglott (çok dilli) mikroservis ortamları için kritik bir avantajdır.

Ne Zaman REST Tercih Edilirdi?

  • Harici API'ler: Eğer API'ler genel istemciler (web tarayıcıları, mobil uygulamalar, üçüncü taraf geliştiriciler) tarafından kullanılacaksa, REST'in tarayıcı uyumluluğu, öğrenme eğrisi ve dokümantasyon kolaylığı (OpenAPI/Swagger) nedeniyle genellikle daha iyi bir seçimdir.
  • Basit CRUD İşlemleri: Eğer servisler temel CRUD (Create, Read, Update, Delete) operasyonlarını sunuyorsa ve karmaşık akış veya yüksek performans gereksinimleri yoksa, REST daha hızlı geliştirme sağlayabilir.

Sonuç olarak, dahili, yüksek performanslı ve sıkı tip güvenliği gerektiren mikroservis iletişimleri için gRPC, daha verimli ve sağlam bir çözüm sunar. Dışa açık, genel tüketimli API'ler için ise REST hala tercih edilen bir yaklaşımdır.

Soru 36:
How Do You Diagnose Database Connection Pool Exhaustion?

Bağlantı havuzları, her istek için yeni bağlantı oluşturma yükünü azaltmak için veritabanı bağlantılarını yeniden kullanır.

Aşağıdaki kavramları hazırlayın:

  • Maksimum havuz boyutu ve bağlantı alma zaman aşımı.
  • Bağlantı sızıntıları (connection leaks) ve uzun süreli sorgular.
  • İşlem süresi ve bloklanmış veritabanı işlemleri.
  • Havuz metrikleri ve veritabanı oturum izleme.
  • Uygun bağlantı havuzu boyutlandırması.

Senaryo: Spring Boot API'nız yoğun trafik sırasında bağlantı zaman aşımı hataları döndürmeye başlıyor, ancak veritabanı hala kullanılabilir durumda. Sorunun yavaş sorgulardan mı, sızan bağlantılardan mı yoksa yetersiz havuzdan mı kaynaklandığını nasıl belirlersiniz?

Veritabanı bağlantı havuzu tükenmesi (Connection Pool Exhaustion), genellikle uygulama yavaşlamalarına, hata mesajlarına ve sonuç olarak hizmet kesintilerine yol açan kritik bir performans sorunudur. Bir Spring Boot uygulamasında bu sorunu teşhis etmek sistematik bir yaklaşım gerektirir.

1. Temel Bağlantı Havuzu Kavramları:

  • Maksimum Havuz Boyutu (Maximum Pool Size): Havuzda aynı anda bulunabilecek maksimum aktif bağlantı sayısı. Bu sayı aşılırsa, yeni istekler bağlantı boşalana kadar bekler veya zaman aşımına uğrar.
  • Bağlantı Alma Zaman Aşımı (Connection Acquisition Timeout): Bir isteğin havuzdan bağlantı almak için ne kadar süre bekleyeceğini belirleyen süre. Bu süre aşılırsa, ConnectionTimeoutException veya benzeri bir hata fırlatılır.
  • Idle Timeout: Kullanılmayan (boşta duran) bir bağlantının havuzdan çıkarılmadan önce ne kadar süre bekleneceğini belirler.
  • Minimum Idle: Havuzda her zaman tutulacak minimum boşta bağlantı sayısı.

2. Bağlantı Sızıntıları (Connection Leaks) ve Uzun Süreli Sorgular:

  • Bağlantı Sızıntıları: Uygulama kodunun bir veritabanı bağlantısını kullanıp işi bittikten sonra havuzuna geri döndürmemesi durumudur. Bu, bağlantı havuzunun zamanla tükenmesine neden olur.
    • En yaygın nedenler: try-finally bloklarının eksikliği, açıkça kapatılmayan ResultSet, Statement veya Connection nesneleri. Spring Boot ve JPA/Hibernate genellikle bunu otomatik yönetir, ancak native JDBC kullanımında veya özel durumlarda ortaya çıkabilir.
  • Uzun Süreli Sorgular: Bir sorgunun tamamlanması çok uzun sürerse, o bağlantıyı uzun süre meşgul eder. Yeterince uzun süreli sorgular, diğer isteklerin bağlantı bulamamasına ve havuzun tükenmesine yol açabilir.

3. İşlem Süresi ve Bloklanmış Veritabanı İşlemleri:

  • Uzun Süreli İşlemler: Bir veritabanı işlemi (transaction) çok uzun sürerse, işlem boyunca kullanılan bağlantı da meşgul kalır. Bu, diğer işlemlerin bağlantı beklemesine neden olabilir.
  • Bloklanmış İşlemler (Deadlock/Lock Contention): Veritabanında kilitlenme (deadlock) veya yüksek kilit çekişmesi (lock contention) meydana gelirse, işlemler birbirini bekler ve bağlantılar serbest bırakılmaz.

4. Havuz Metrikleri ve Veritabanı Oturum İzleme:

  • Bağlantı Havuzu Metrikleri: Bağlantı havuzu kütüphaneleri (HikariCP, c3p0, Tomcat JDBC Pool) genellikle JMX (Java Management Extensions) veya uygulama metrikleri aracılığıyla izlenebilir metrikler sunar.
    • Aktif Bağlantı Sayısı: Şu anda kullanılan bağlantı sayısı.
    • Boşta Bağlantı Sayısı: Şu anda havuzda kullanılabilir olan bağlantı sayısı.
    • Bekleyen Bağlantı Sayısı: Bağlantı bekleyen istek sayısı.
    • Bağlantı Alma Süresi: Bir bağlantının havuzdan alınması ne kadar sürüyor.
    • Bağlantı Kullanım Süresi: Bir bağlantının ortalama ne kadar süre kullanıldığı.
  • Veritabanı Oturum İzleme: Veritabanı yönetim sistemlerinin (PostgreSQL, MySQL, Oracle SQL Server) kendi izleme araçları ve SQL sorguları ile aktif oturumları, uzun süreli sorguları, kilitlenmeleri ve beklemeleri izleyin.
    • SHOW PROCESSLIST; (MySQL)
    • pg_stat_activity; (PostgreSQL)
    • sp_who2 (SQL Server)
    Bu araçlar hangi sorguların uzun süre çalıştığını, hangi oturumların kilitlendiğini veya beklediğini gösterir.

5. Uygun Bağlantı Havuzu Boyutlandırması:

  • Bağlantı havuzu boyutu, uygulamanın eş zamanlı iş parçacığı (thread) sayısına ve veritabanı işlemlerinin süresine göre ayarlanmalıdır. Çok küçük havuzlar tükenmeye, çok büyük havuzlar veritabanı üzerinde gereksiz yüke yol açar.
  • Formula: connections = ((core_count * 2) + effective_spindle_count) (Popüler bir başlangıç noktası, ancak testlerle optimize edilmeli).
  • Test ve İzleme: En iyi boyutu bulmak için yük testleri yapmak ve havuz metriklerini sürekli izlemek önemlidir.

Senaryo: Spring Boot API Yoğun Trafik Sırasında Bağlantı Zaman Aşımı Hataları Döndürüyor, Veritabanı Halen Çalışır Durumda. Sorunun Kök Nedenini Belirleme:

Bu senaryo, bağlantı havuzu tükenmesinin tipik bir işaretidir. Sorunun yavaş sorgulardan mı, sızan bağlantılardan mı yoksa yetersiz havuzdan mı kaynaklandığını belirlemek için şu adımları izleyin:

Adım 1: İzleme ve Metrik Verilerini Toplama (Öncelikli):

  • Uygulama Metrikleri:
    • Prometheus/Grafana, Micrometer veya APM (Dynatrace, New Relic) kullanarak uygulamanın bağlantı havuzu metriklerini (HikariCP metrikleri gibi) izleyin:
      • hikari_connections_active (aktif bağlantı sayısı)
      • hikari_connections_idle (boşta bağlantı sayısı)
      • hikari_connections_waiting (bekleyen istek sayısı)
      • hikari_connections_timeout_total (toplam bağlantı zaman aşımı sayısı)
      Bu metrikler, hatanın başlamasıyla birlikte aktif bağlantıların maksimuma ulaştığını, boşta bağlantıların sıfıra düştüğünü ve bekleyen bağlantı sayısının arttığını gösterecektir.
    • Uygulamanın genel performans metriklerini (istek gecikmesi, CPU/Bellek kullanımı, iş parçacığı sayısı) de inceleyin. CPU normal kalırken gecikme artıyorsa, bu bir bekleme durumuna işaret eder.
  • Veritabanı Metrikleri: Veritabanı sunucusunun kendi metriklerini (aktif bağlantılar, çalışan sorgular, kilitlenmeler, disk I/O, CPU kullanımı) kontrol edin. Veritabanının kendi performansı normalse, sorun uygulamada demektir.
  • Loglar: Uygulama loglarında ConnectionTimeoutException veya benzeri hataları arayın. Hatanın stack trace'i, hangi kod parçasının bağlantı alamadığını gösterir.

  • Yüksek hikari_connections_active ve Düşük hikari_connections_idle:
    • Olası Neden: Uzun Süreli Sorgular:
      • Teşhis: Veritabanı izleme araçlarını kullanarak (örneğin, PostgreSQL için pg_stat_activity'i sorgulayarak) "aktif" durumdaki uzun süreli sorguları belirleyin. Hangi sorguların saatlerce veya dakikalarca çalıştığını görmek önemlidir. Sorguların yavaşlamasına yol açan indeks eksikliklerini veya kötü yazılmış SQL'leri tespit edin.
      • Çözüm: Sorguları optimize edin (indeks ekleme, EXPLAIN planı ile analiz), veritabanı şemasını iyileştirin. Gerekirse uzun süreli arka plan işlemleri için ayrı, daha büyük bir bağlantı havuzu kullanın.
    • Olası Neden: Bağlantı Sızıntıları (Connection Leaks):
      • Teşhis: Uygulama kodunda java.sql.Connection, Statement veya ResultSet'ın manuel olarak kullanıldığı yerleri kontrol edin. Bu nesnelerin finally blokları içinde düzgün bir şekilde kapatılıp kapatılmadığından emin olun. Eğer aktif bağlantı sayısı sürekli artıyor ve hiç düşmüyorsa, bu sızıntı işaretidir. APM araçları, bağlantı sızıntılarını ve bunların kaynaklandığı kod parçalarını tespit etmede yardımcı olabilir.
      • Çözüm: Sızan bağlantıları kapatmak için kodu düzeltin. Genellikle Spring Boot'un ORM entegrasyonu bağlantıları otomatik yönettiği için bu sorun daha çok native JDBC veya hatalı yapılandırılmış kütüphanelerde görülür.
    • Olası Neden: Yetersiz Havuz Boyutu:
      • Teşhis: Eğer aktif bağlantı sayısı sürekli olarak maksimum havuz boyutuna yakın seyrediyorsa ve bekleyen istekler varsa, ancak veritabanı tarafında yavaş sorgu veya sızıntı belirtisi yoksa, havuz boyutu yetersiz olabilir.
      • Çözüm: Havuz boyutunu kademeli olarak artırın (örneğin, spring.datasource.hikari.maximum-pool-size). Artırdıktan sonra performansı ve veritabanı yükünü tekrar izleyin. Çok büyük havuzlar, veritabanı sunucusunu aşırı yükleyebilir.
    • Olası Neden: Uzun Süreli Uygulama İşlemleri:
      • Teşhis: Veritabanı bağlantısını gerektirmeyen ancak uzun süren (CPU yoğun hesaplama, harici API çağrısı gibi) bir işlem, bağlantıyı gereksiz yere meşgul edebilir.
      • Çözüm: Bu tür işlemleri veritabanı işleminden ayırın veya asenkron olarak yürütün.

Adım 3: Düzeltme ve Doğrulama:

  1. Kök Nedeni Giderin: Yukarıdaki analizlere dayanarak sorunun temel nedenini düzeltin (sorguyu optimize et, sızıntıyı kapat, havuz boyutunu ayarla).
  2. Test Edin: Düzeltmeyi test ortamında (yük testleriyle) doğrulayın.
  3. Üretim Ortamında İzleyin: Düzeltmeyi üretim ortamına dağıttıktan sonra, ilgili metrikleri (bağlantı havuzu, veritabanı performansı, uygulama yanıt süresi) yakından izleyerek sorunun kalıcı olarak çözüldüğünden emin olun.

Bu sistematik yaklaşım, bağlantı havuzu tükenmesi sorunlarının kök nedenini belirlemenize ve etkili çözümler uygulamanıza yardımcı olacaktır.

Soru 37:
How Would You Design Reliable Retries and Timeouts for Microservices?

Yeniden denemeler (retries), geçici hatalardan kurtulmaya yardımcı olabilir, ancak yanlış yapılandırılmış yeniden denemeler bir kesintiyi büyütebilir.

Aşağıdaki konuları tartışın:

  • Bağlantı ve istek zaman aşımı (connection and request timeouts).
  • Üstel geri çekilme (exponential backoff) ile sınırlı yeniden denemeler.
  • Senkronize yeniden deneme patlamalarını önlemek için rastgele jitter.
  • Yeniden denenebilir (retryable) ve yeniden denenemez (non-retryable) hatalar.
  • Devre kesiciler (circuit breakers) ve bölmeler (bulkheads).
  • Tekrarlanabilecek işlemler (idempotency).

Senaryo: Aşağı akış bir ödeme hizmeti yavaşlıyor ve birden fazla hizmet başarısız istekleri yeniden denemeye başlıyor. Sistemdeki basamaklı hataları nasıl önlersiniz?

Mikroservis mimarilerinde, servisler arası iletişim ağ üzerinden gerçekleşir ve bu da geçici ağ sorunlarına, servis yavaşlamalarına veya kısa süreli arızalara yol açabilir. Bu durumlarda, güvenilir yeniden deneme (retry) ve zaman aşımı (timeout) stratejileri, sistemin dayanıklılığını ve hata toleransını artırmak için hayati öneme sahiptir. Ancak yanlış uygulanırsa, bir hizmetin yavaşlaması tüm sistemi çökerten "basamaklı hatalara" (cascading failures) yol açabilir.

1. Bağlantı ve İstek Zaman Aşımı (Connection and Request Timeouts):

  • Connection Timeout (Bağlantı Zaman Aşımı): Bir istemcinin uzak bir servise bağlantı kurmak için ne kadar süre bekleyeceğini belirler. Bu süre aşılırsa, bağlantı kurulamadığı için istek gönderilmeden hata döner. Genellikle kısa bir süre olmalıdır (örneğin, 1-3 saniye).
  • Request Timeout (İstek Zaman Aşımı / Read Timeout): Bir bağlantı kurulduktan sonra, istemcinin sunucudan bir yanıtın tamamını almak için ne kadar süre bekleyeceğini belirler. Bu süre aşılırsa, kısmi yanıt veya hiç yanıt gelmeden işlem kesilir. İşlemin karmaşıklığına göre ayarlanmalıdır (örneğin, 5-30 saniye).
  • Önemi: Zaman aşımlarının doğru yapılandırılması, istemcilerin sonsuza kadar bekleyerek kendi kaynaklarını (thread, bellek) tüketmesini önler ve hızlı hata geri bildirimi sağlar.

2. Üstel Geri Çekilme (Exponential Backoff) ile Sınırlı Yeniden Denemeler:

  • Prensip: Bir istek başarısız olduğunda, hemen yeniden denemek yerine belirli bir gecikmeyle (backoff) yeniden denemektir. Üstel geri çekilme, her başarısız denemede gecikme süresini katlayarak artırır (örneğin, 1sn, 2sn, 4sn, 8sn...).
  • Sınırlı Yeniden Denemeler: Yeniden denemelerin toplam sayısı (maksimum deneme sayısı) ve maksimum gecikme süresi (max backoff time) sınırlandırılmalıdır. Sonsuz veya çok sayıda deneme, zaten yavaş olan bir servisi daha da kötü duruma sokabilir.
  • Önemi: Yavaşlayan veya geçici olarak kullanılamayan servislere aşırı yük bindirmeyi önler, servisin kendini toparlaması için zaman tanır.

3. Rastgele Jitter (Randomized Jitter) ile Senkronize Yeniden Deneme Patlamalarını Önleme:

  • Sorun: Birçok istemci aynı anda bir hizmete istek gönderir ve hizmet çökerse, tüm istemciler aynı üstel geri çekilme algoritmalarını kullanıyorsa, aynı anda yeniden deneme yapmaya başlayabilirler. Bu, "thundering herd" (kükreyen sürü) etkisi olarak bilinen senkronize bir "deneme patlamasına" yol açar ve servisin daha da çökmesine neden olur.
  • Çözüm: Geri çekilme süresine küçük, rastgele bir gecikme ("jitter") eklenir. Bu, yeniden denemeleri zaman çizelgesinde dağıtarak sunucuya gelen yükü pürüzsüzleştirir. Örneğin, delay = min(max_delay, random(0, 1) * base_delay * 2^retries) gibi.

4. Yeniden Denenebilir (Retryable) ve Yeniden Denenemez (Non-Retryable) Hatalar:

  • Yeniden Denenebilir Hatalar: Geçici olduğu düşünülen hatalardır ve yeniden denemede başarılı olma olasılığı vardır.
    • HTTP 5xx durum kodları (500 Internal Server Error, 503 Service Unavailable, 504 Gateway Timeout).
    • Ağ bağlantısı hataları.
    • Veritabanı bağlantı havuzu tükenme hataları (eğer geçiciyse).
  • Yeniden Denenemez Hatalar: Kalıcı olduğu düşünülen hatalardır ve yeniden denemek durumu değiştirmeyecektir. Yeniden denemek kaynak israfıdır ve gecikmeyi artırır.
    • HTTP 4xx durum kodları (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Unprocessable Entity).
    • İş mantığı hataları (örneğin, geçersiz giriş, stok yetersizliği).
    • Programlama hataları (NullPointerException, IllegalArgumentException).
  • Önemi: Hata türüne göre doğru yeniden deneme politikası uygulamak, sistemi daha verimli ve dayanıklı hale getirir.

5. Devre Kesiciler (Circuit Breakers) ve Bölmeler (Bulkheads):

  • Devre Kesici (Circuit Breaker): Bir hizmete yapılan çağrıların sürekli olarak başarısız olduğunu algıladığında, bu hizmete yapılan tüm çağrıları belirli bir süre için otomatik olarak durdurur. Bu, arızalı bir hizmeti çağırmaya devam etmek yerine istemcinin hızlıca hata vermesini sağlar ve arızalı hizmetin kendini toparlamasına olanak tanır.
    • Durumları: Kapalı (Closed), Açık (Open), Yarı Açık (Half-Open).
    • Kütüphaneler: Resilience4j, Hystrix (bakımı durduruldu).
  • Bölme (Bulkhead): Uygulamanın farklı kısımlarını (mikroservis çağrıları, veritabanı erişimi, harici API entegrasyonları) izole ederek, bir bölümdeki hatanın tüm uygulamayı çökertmesini önler. Her kaynak için ayrı bir thread havuzu veya kaynak havuzu ayırır.
    • Önemi: Bir servisin veya bağımlılığın yavaşlaması/çökmesi durumunda, uygulamanın diğer fonksiyonlarının etkilenmeden çalışmaya devam etmesini sağlar.

6. Tekrarlanabilecek İşlemler (Idempotency) için Tasarım:

  • Yeniden denemeler bir işlemin birden fazla kez çalıştırılmasına yol açabilir. Eğer işlem idempotent değilse, bu sorunlara neden olabilir (örneğin, bir ödeme iki kez işlenir).
  • Idempotent Tasarım: Servislerin API'leri, aynı isteğin birden fazla kez gönderildiğinde bile aynı sonucu vermesini veya sistem durumunu sadece bir kez değiştirmesini sağlamalıdır (örneğin, benzersiz bir istek ID'si kullanarak).

Senaryo: Aşağı Akış Bir Ödeme Hizmeti Yavaşlıyor ve Birden Fazla Hizmet Başarısız İstekleri Yeniden Denemeye Başlıyor. Sistemdeki Basamaklı Hataları Nasıl Önlersiniz?

Bu, mikroservis mimarilerinde sıkça karşılaşılan bir felaket senaryosudur. Basamaklı hataları önlemek için katmanlı bir savunma yaklaşımı uygulanmalıdır:

  1. Zaman Aşımlarını Doğru Yapılandırın:
    • Ödeme servisini çağıran tüm upstream servislerde (örneğin, Order Service), ödeme API'si için makul bağlantı ve istek zaman aşımları belirleyin (örneğin, connectionTimeout=1s, readTimeout=5s). Bu, yavaşlayan ödeme servisinin sonsuza kadar bağlantıları meşgul etmesini önler.
  2. Yeniden Denemeleri Akıllıca Uygulayın (Upstream Servislerde):
    • Ödeme servisi yavaşladığında veya 5xx hata kodları döndürdüğünde, çağıran servisler (Order Service gibi) üstel geri çekilme ve jitter ile yeniden deneme yapmalıdır.
    • Yeniden deneme sayısı sınırlandırılmalıdır (örneğin, en fazla 3-5 deneme).
    • Yeniden denemelerin yalnızca "yeniden denenebilir" hatalar (ağ hataları, 5xx sunucu hataları) için tetiklendiğinden emin olun. 4xx hataları (örneğin, geçersiz ödeme bilgisi) yeniden denenmemelidir.
  3. Devre Kesici Uygulayın (Upstream Servislerde):
    • Order Service ve diğer ödeme servisinden etkilenen tüm upstream servislerde devre kesici (Circuit Breaker) kullanın (Resilience4j gibi).
    • Ödeme servisine yapılan çağrılar belirli bir hata oranı eşiğini aştığında (örneğin, %50 hata oranı), devre kesici "Açık" (Open) duruma geçmeli ve tüm çağrıları hızlıca başarısız etmelidir. Bu, ödeme servisine yönelik trafiği tamamen keser ve hem ödeme servisinin kendini toparlamasına olanak tanır hem de upstream servislerinin kaynaklarını boşa harcamasını önler.
    • Devre kesici "Yarı Açık" (Half-Open) duruma geçtiğinde, belirli aralıklarla küçük bir test isteği göndererek ödeme servisinin düzelip düzelmediğini kontrol eder.
  4. Bölmeler (Bulkheads) Kullanın:
    • Her bir harici servis çağrısı (ödeme servisi çağrısı dahil) için ayrı bir thread havuzu veya semafor havuzu (Resilience4j'deki SemaphoreBulkhead) ayırın.
    • Eğer ödeme servisi yavaşlarsa, sadece ödeme servisi için ayrılan thread havuzu tükenecek, ancak diğer servis çağrıları (örneğin, Inventory Service) için ayrılan thread havuzları etkilenmeyecektir. Bu, Order Service'in diğer fonksiyonlarının çalışmaya devam etmesini sağlar.
  5. Idempotent Tasarım Sağlayın:
    • Ödeme isteği API'sinin idempotent olduğundan emin olun. Yani, Order Service aynı ödeme isteğini birden fazla kez gönderirse, ödeme servisi bunu sadece bir kez işleyebilmelidir (örneğin, benzersiz bir işlem ID'si kullanarak). Bu, yeniden denemelerin istenmeyen yan etkilere yol açmasını engeller.
  6. Asenkron Mesajlaşma ve Kuyruklar:
    • Kritik olmayan veya nihai tutarlılık (eventual consistency) kabul edilebilen ödeme süreçlerinde, senkron API çağrıları yerine asenkron mesajlaşma (Kafka, RabbitMQ) kullanılabilir.
    • Order Service, ödeme isteğini bir mesaj kuyruğuna bırakır ve Payment Service bu mesajı kendi hızında işler. Eğer Payment Service yavaşlarsa, mesajlar kuyrukta bekler ancak Order Service bloke olmaz.
  7. İzleme ve Uyarılar:
    • Tüm servisler için kritik performans metriklerini (gecikme, hata oranı, CPU/bellek kullanımı) sürekli izleyin.
    • Ödeme servisi yavaşlamaya başladığında veya hata oranları arttığında otomatik uyarılar alın, böylece manuel müdahale hızlıca yapılabilir.

Bu stratejilerin kombinasyonu, bir hizmetteki sorunların tüm sisteme yayılmasını etkili bir şekilde önler ve dağıtık bir sistemin dayanıklılığını önemli ölçüde artırır.

Soru 38:
What Is the Difference Between Optimistic Locking and Database Isolation Levels?

Her iki kavram da eş zamanlı veri erişimini yönetmeye yardımcı olur, ancak tutarlılığın farklı yönlerini ele alırlar.

  • İyimser kilitleme (optimistic locking), genellikle bir sürüm alanı (version field) aracılığıyla çakışan güncellemeleri tespit eder.
  • İzolasyon seviyeleri (isolation levels), eş zamanlı veritabanı işlemlerinin nasıl etkileşeceğini kontrol eder.

Dirty reads, non-repeatable reads ve phantom reads kavramlarını anlayın. İşlem çakışmalarını, deadlock'ları ve yeniden deneme stratejilerini tartışın.

Senaryo: İki istek aynı anda aynı müşteri kaydını güncellemeye çalışıyor. Uygun bir kilitleme stratejisi ve işlem izolasyon seviyesini nasıl seçersiniz?

Optimistic Locking (İyimser Kilitleme) ve Database Isolation Levels (Veritabanı İzolasyon Seviyeleri), veritabanında eş zamanlı veri erişimini yönetmek için kullanılan temel ancak farklı kavramlardır. Her ikisi de veri tutarlılığını sağlamayı hedefler ancak farklı katmanlarda ve farklı yaklaşımlarla çalışırlar.

1. Optimistic Locking (İyimser Kilitleme):

  • Kapsam: Uygulama katmanında (JPA, Hibernate gibi ORM'ler aracılığıyla) veya özel uygulama kodunuzla uygulanır.
  • Prensip: Çoğu zaman çakışma olmayacağı varsayımına dayanır. Kayıtlar okunurken kilit uygulanmaz, bu nedenle okuma işlemleri hızlıdır ve eş zamanlılığı etkilemez. Bir kayıt güncellenmeye çalışıldığında, okunduğu zamandan bu yana değişip değişmediğini kontrol etmek için bir "sürüm" (version) mekanizması kullanılır.
    • Mekanizma: Genellikle bir @Version anotasyonu ile varlığa bir sürüm alanı (örneğin, int version veya timestamp last_updated) eklenir. Bir varlık okunduğunda sürüm değeri de alınır. Güncelleme yapılırken, veritabanındaki sürüm değeri ile uygulamadaki sürüm değeri karşılaştırılır. Eğer farklıysa, başka bir işlemin kaydı değiştirdiği anlaşılır ve güncelleme reddedilerek bir OptimisticLockException fırlatılır.
  • Ne Zaman Kullanılır: Düşük ila orta düzeyde veri çekişmesi olan senaryolar. Yüksek eş zamanlılığın önemli olduğu durumlarda, çünkü okuma işlemleri bloklanmaz.
  • Çakışma Yönetimi: Çakışmalar, uygulamanın yeniden deneme (retry) veya kullanıcıya hata mesajı gösterme mantığıyla ele alınmalıdır.

2. Database Isolation Levels (Veritabanı İzolasyon Seviyeleri):

  • Kapsam: Veritabanı yönetim sistemi (DBMS) seviyesinde uygulanır. Bir işlemin diğer eş zamanlı işlemlerden ne kadar izole edileceğini belirler.
  • Prensip: Bir işlemin, diğer eş zamanlı işlemlerin etkilerini ne kadar "göreceğini" kontrol eder. ACID özelliklerinden (Atomicity, Consistency, Isolation, Durability) "Isolation" (İzolasyon) ile doğrudan ilgilidir.
  • Yaygın İzolasyon Seviyeleri (artan izolasyon ve azalan eş zamanlılık sırasına göre):
    • READ UNCOMMITTED (En Düşük İzolasyon): "Kirli okumalar"a (Dirty Reads) izin verir. Bir işlem, commit edilmemiş başka bir işlemin yaptığı değişiklikleri görebilir. Eğer bu değişiklikler geri alınırsa, ilk işlem yanlış bir veri okumuş olur.
    • READ COMMITTED: Kirli okumaları önler. Bir işlem sadece commit edilmiş verileri görebilir. Ancak "tekrarlanamaz okumalar"a (Non-Repeatable Reads) izin verir. Aynı işlem içinde aynı sorgu iki kez çalıştırıldığında farklı sonuçlar döndürebilir, çünkü başka bir işlem arada commit edilmiş olabilir.
    • REPEATABLE READ: Kirli okumaları ve tekrarlanamaz okumaları önler. Aynı işlem içinde aynı sorgu her zaman aynı sonuçları döndürür. Ancak "hayalet okumalar"a (Phantom Reads) izin verir. Bir aralık sorgulandığında (örneğin, SELECT COUNT(*) FROM X WHERE Y > 10), başka bir işlem bu aralığa yeni kayıtlar ekleyip commit ederse, aynı aralık tekrar sorgulandığında farklı bir sayı (yeni eklenen kayıtlar) görülebilir.
    • SERIALIZABLE (En Yüksek İzolasyon): Kirli okumaları, tekrarlanamaz okumaları ve hayalet okumaları önler. İşlemler sanki seri olarak (birbiri ardına) çalışıyormuş gibi davranır. Yüksek düzeyde tutarlılık sağlar ancak eş zamanlılığı büyük ölçüde azaltır ve performans maliyeti çok yüksektir. Genellikle deadlock riski en fazladır.
  • Ne Zaman Kullanılır: Veri bütünlüğünün ve tutarlılığının kritik olduğu durumlarda. Veritabanının varsayılan izolasyon seviyesi (çoğunlukla READ COMMITTED veya REPEATABLE READ) iyi bir başlangıç noktasıdır.

İşlem Çakışmaları, Deadlock'lar ve Yeniden Deneme Stratejileri:

  • İşlem Çakışmaları: Birden fazla eş zamanlı işlemin aynı veriye erişmeye veya onu değiştirmeye çalışması durumunda ortaya çıkar. İyimser kilitlemede OptimisticLockException, kötümser kilitlemede bekleme veya kilit zaman aşımı hatası, izolasyon seviyelerine göre farklı tutarsızlık türleri (dirty reads vb.) olarak kendini gösterebilir.
  • Deadlock (Kilitlenme): İki veya daha fazla işlemin birbirlerinin serbest bırakmasını beklediği ve hiçbirinin ilerleyemediği durumdur. Genellikle kötümser kilitleme veya yüksek izolasyon seviyelerinde (SERIALIZABLE) ortaya çıkar. Veritabanları genellikle bir deadlock dedektörü içerir ve deadlock'a giren işlemlerden birini kurban seçerek geri alır.
  • Yeniden Deneme Stratejileri:
    • Optimistic Locking: Bir OptimisticLockException alındığında, istemci işlemi yeniden okuyup tekrar denemelidir. Üstel geri çekilme (exponential backoff) ile yeniden denemeler tavsiye edilir.
    • Deadlock: Veritabanı bir işlemi deadlock kurbanı seçip geri aldığında, uygulamanın işlemi yeniden denemesi gerekir.

Senaryo: İki İstek Aynı Anda Aynı Müşteri Kaydını Güncellemeye Çalışıyor. Uygun Bir Kilitleme Stratejisi ve İşlem İzolasyon Seviyesini Seçme:

Bu senaryoda, eş zamanlı güncelleme çakışmalarını yönetmek ve veri bütünlüğünü sağlamak için hem kilitleme stratejisi hem de izolasyon seviyesi dikkatle seçilmelidir.

1. Kilitleme Stratejisi Seçimi:

  • Önerilen: Optimistic Locking (@Version ile):
    • Neden: Müşteri kaydı güncellemeleri genellikle çok sık ve yoğun çekişmeli olmayabilir. Optimistic locking, okuma işlemlerini bloklamadığı için yüksek eş zamanlılık sağlar ve çoğu senaryo için yeterlidir.
    • Çalışma: İlk istek kaydı okur (sürüm X ile). İkinci istek de kaydı okur (sürüm X ile). İlk istek kaydı günceller ve sürümü X+1 yapar. İkinci istek de kaydı güncellemeyi denediğinde, beklenen sürüm X iken veritabanındaki sürüm X+1 olduğu için bir OptimisticLockException alır.
    • Sonuç: İkinci istek başarısız olur. Uygulama, bu istisnayı yakalayarak kullanıcıya bir hata mesajı gösterebilir ("Başka bir kullanıcı kaydı güncelledi, lütfen tekrar deneyin") veya belirli bir stratejiyle işlemi yeniden deneyebilir.
  • Alternatif: Pessimistic Locking (LockModeType.PESSIMISTIC_WRITE ile):
    • Neden: Eğer müşteri kayıtları son derece kritikse (örneğin, finansal bakiyeler) ve veri tutarlılığı eş zamanlılıktan daha önemliyse, veya çekişme seviyesi çok yüksekse düşünülebilir.
    • Çalışma: İlk istek kaydı okurken bir veritabanı kilidi (FOR UPDATE) uygular. İkinci istek aynı kaydı okumayı denediğinde, kilit serbest bırakılana kadar bekler. İlk işlem tamamlandığında (commit veya rollback), kilit serbest bırakılır ve ikinci işlem devam edebilir.
    • Sonuç: İkinci istek bloke olur. Belirli bir zaman aşımı sonrası kilit alamazsa hata alabilir (örneğin, PessimisticLockException). Deadlock riski artar.

2. İşlem İzolasyon Seviyesi Seçimi:

  • Önerilen: READ COMMITTED (Varsayılan):
    • Neden: Çoğu uygulama için iyi bir dengedir. Kirli okumaları önler, yani bir kullanıcının commit edilmemiş değişikliklerini görmesini engeller. Bu, temel veri tutarlılığı için yeterlidir.
    • Risk: "Tekrarlanamaz okumalar" mümkün olabilir. Yani, bir işlem içinde aynı müşteri kaydını iki kez okursanız, arada başka bir işlem kaydı güncelleyip commit ettiyse, ikinci okumanız farklı bir sonuç verebilir. Ancak genellikle bu, müşteri kaydı güncelleme senaryosunda kritik bir sorun değildir, çünkü genellikle kaydı bir kez okur, değiştirir ve kaydederiz.
  • Alternatif: REPEATABLE READ:
    • Neden: Eğer aynı işlem içinde aynı verinin birden fazla kez okunması ve her zaman aynı sonucu vermesi kritikse (örneğin, bir rapor oluştururken), REPEATABLE READ kullanılabilir. MySQL'in varsayılanı bu olabilir.
    • Risk: Eş zamanlılığı READ COMMITTED'e göre biraz daha azaltır ve daha fazla kilit kaynağı kullanır. Hayalet okumalar hala mümkün olabilir (ancak tek bir müşteri kaydı güncellenirken bu risk daha düşüktür).
  • SERIALIZABLE: Genel olarak tavsiye edilmez. Performans maliyeti çok yüksektir ve deadlock riskini aşırı artırır. Sadece mutlak en yüksek tutarlılığın (veya veritabanı seviyesinde işlemden geçirme garantisinin) gerekli olduğu çok özel durumlar için düşünülmelidir.

Karar:

Genellikle müşteri kayıtları gibi veriler için, Optimistic Locking (@Version ile) kullanmak ve veritabanı izolasyon seviyesini READ COMMITTED olarak bırakmak en dengeli ve tavsiye edilen yaklaşımdır. Bu kombinasyon, yüksek eş zamanlılık sağlarken, veri bütünlüğünü de etkili bir şekilde yönetir. Optimistic locking'in tetiklediği istisnaları uygun yeniden deneme mekanizmalarıyla ele almak önemlidir.

Soru 39:
How Would You Secure Sensitive Configuration and Secrets in Spring Boot?

Uygulamalar genellikle veritabanı kimlik bilgileri, API anahtarları, sertifikalar ve diğer hassas yapılandırmalara ihtiyaç duyar.

Aşağıdaki konuları tartışın:

  • Ortama özel yapılandırma.
  • Ortam değişkenleri ve bunların operasyonel sınırlamaları.
  • Bulut gizlilik yöneticileri (cloud secret managers) veya özel kasa çözümleri (dedicated vault solutions).
  • Gizlilik rotasyonu (secret rotation) ve en az ayrıcalık (least-privilege) erişimi.
  • Kimlik bilgilerinin kaynak kontrolüne, günlüklere ve hata yanıtlarına dahil edilmesinden kaçınma.
  • Geliştirme, test ve üretim ortamlarında güvenli yapılandırma.

Senaryo: Bir veritabanı parolası yanlışlıkla bir depoda (repository) ifşa edildi. Hangi acil adımları atar ve aynı olayın tekrar yaşanmasını nasıl önlersiniz?

Hassas yapılandırma (secrets) ve kimlik bilgilerinin güvenliği, herhangi bir modern uygulamanın kritik bir yönüdür. Veritabanı şifreleri, API anahtarları, sertifikalar gibi sırlar, doğru şekilde yönetilmezse ciddi güvenlik ihlallerine yol açabilir. Spring Boot uygulamalarında bu sırların güvenliğini sağlamak için çok katmanlı bir yaklaşım benimsenmelidir.

1. Ortama Özel Yapılandırma:

  • Spring Boot, application.properties veya application.yml dosyaları ve aktif profiller (spring.profiles.active=dev,prod) aracılığıyla ortama özel yapılandırmayı kolaylaştırır.
  • Farklı ortamlar (dev, test, prod) için farklı yapılandırma dosyaları (application-dev.yml, application-prod.yml) kullanılarak, hassas bilgiler her ortam için özelleştirilebilir.
  • Ancak, hassas bilgiler (şifreler) bu dosyalara doğrudan yazılmamalıdır. Bu dosyalar sadece gizlilik yöneticilerinden gelen referansları veya ortam değişkenlerini kullanmalıdır.

2. Ortam Değişkenleri (Environment Variables) ve Operasyonel Sınırlamaları:

  • Kullanım: Sırları Spring Boot uygulamasına enjekte etmenin basit ve yaygın bir yoludur. Örneğin, SPRING_DATASOURCE_PASSWORD=my_prod_db_pass. Uygulama, ortam değişkenlerini otomatik olarak okur.
  • Avantajlar: Kaynak kontrolüne (Git) dahil edilmezler, böylece yanlışlıkla ifşa riski azalır.
  • Operasyonel Sınırlamalar:
    • Denetlenebilirlik Eksikliği: Kimin ne zaman hangi sırrı değiştirdiğini takip etmek zordur.
    • Erişim Kontrolü: Sunucuya erişimi olan herkes ortam değişkenlerini okuyabilir, bu da ayrıntılı erişim kontrolünü zorlaştırır.
    • Rotasyon Zorluğu: Sır rotasyonu (değiştirilmesi), ortam değişkenlerini manuel olarak güncelleme gerektirdiği için daha hantaldır.
    • Container/Orkestrasyon Sistemleri: Kubernetes Secret'ları gibi daha güvenli mekanizmalar sunsalar da, bunlar hala konteyner içine ortam değişkenleri olarak enjekte edilebilir ve bellek içi görüntülenebilir hale gelebilir.

3. Bulut Gizlilik Yöneticileri (Cloud Secret Managers) veya Özel Kasa Çözümleri (Dedicated Vault Solutions):

Sır yönetimi için en güvenli ve tavsiye edilen yaklaşımdır.

  • Cloud Secret Managers:
    • AWS Secrets Manager / Parameter Store
    • Azure Key Vault
    • Google Cloud Secret Manager
  • Dedicated Vault Solutions:
    • HashiCorp Vault
  • Avantajlar:
    • Merkezi Yönetim: Tüm sırları tek bir yerde yönetir.
    • Erişim Kontrolü: Çok granüler erişim kontrolleri (kimin hangi sırra, hangi koşullarda erişebileceği) sağlar.
    • Denetim (Auditing): Sırlara kimin ne zaman eriştiğinin veya değiştirdiğinin tam kaydını tutar.
    • Rotasyon: Otomatik sır rotasyonu yetenekleri sunar.
    • Şifreleme: Sırları hem aktarımda (in-transit) hem de depoda (at-rest) şifreler.
    • Dinamik Sırlar: Veritabanı bağlantıları gibi, kısa ömürlü, isteğe bağlı olarak oluşturulan sırlar sağlayabilir.
  • Entegrasyon: Spring Cloud Config Server veya Spring Cloud Vault gibi projelerle Spring Boot uygulamalarına entegre edilebilir. Uygulama, başlangıçta bu yöneticilerden sırları çeker.

4. Gizlilik Rotasyonu (Secret Rotation) ve En Az Ayrıcalık (Least-Privilege) Erişimi:

  • Gizlilik Rotasyonu: Sırlar düzenli olarak (örneğin, 90 günde bir) veya bir olay (örneğin, ihlal şüphesi) durumunda otomatik veya yarı otomatik olarak değiştirilmelidir. Bu, bir sırrı ele geçiren bir saldırganın sonsuza kadar erişim sağlamasını önler. Gizlilik yöneticileri bu rotasyonu kolaylaştırır.
  • En Az Ayrıcalık (Least-Privilege) Erişimi: Uygulamalara ve kullanıcılara, yalnızca görevlerini yerine getirmeleri için kesinlikle gerekli olan en düşük düzeyde erişim izinleri verilmelidir. Bir uygulamanın sadece okuma izni gerektirdiği yerde yazma izni verilmemelidir.

5. Kimlik Bilgilerinin Kaynak Kontrolüne, Günlüklere ve Hata Yanıtlarına Dahil Edilmesinden Kaçınma:

  • Kaynak Kontrolü (Source Control / Git): Asla ve asla hassas bilgileri (şifreler, API anahtarları) Git depolarına commit etmeyin. .gitignore dosyasını doğru yapılandırın.
  • Günlükler (Logs): Hassas bilgileri (parolalar, token'lar) uygulama günlüklerine yazdırmaktan kaçının. Loglama yapılandırmanızı ve kodunuzu dikkatlice inceleyin. Spring Boot, logları maskelemek için bazı yerleşik yeteneklere sahiptir, ancak özel kodda dikkatli olunmalıdır.
  • Hata Yanıtları (Error Responses): API'ler, hata yanıtlarında hassas bilgileri asla ifşa etmemelidir. Jenerik hata mesajları döndürün.

6. Geliştirme, Test ve Üretim Ortamlarında Güvenli Yapılandırma:

  • Geliştirme: Yerel geliştirme ortamlarında kolaylık sağlamak için daha az katı bir sır yönetimi uygulanabilir (örneğin, yerel ortam değişkenleri veya basit application.properties). Ancak bunlar asla üretim sırlarını içermemelidir.
  • Test: Test ortamları, üretime mümkün olduğunca benzer olmalı ve üretim dışı sırlar (test veritabanı şifreleri) kullanmalıdır. Otomatik sır rotasyonunun ve erişim kontrollerinin test edildiğinden emin olun.
  • Üretim: En sıkı güvenlik önlemleri uygulanır. Mutlaka bir sır yöneticisi (cloud secret manager veya HashiCorp Vault) kullanılmalıdır. Tüm iletişim HTTPS üzerinden şifrelenmelidir.

Senaryo: Bir Veritabanı Parolası Yanlışlıkla Bir Depoda İfşa Edildi. Hangi Acil Adımları Atar ve Aynı Olayın Tekrar Yaşanmasını Nasıl Önlersiniz?

Bu çok ciddi bir güvenlik ihlalidir ve acil müdahale gerektirir.

Acil Adımlar:

  1. Parolayı Hemen Değiştirin: İfşa edilen veritabanı parolasını mümkün olan en kısa sürede değiştirin. Bu, saldırganın ele geçirdiği parolayla veritabanına erişmesini engellemenin ilk adımıdır.
  2. Etkilenen Tüm Sistemleri Güncelleyin: Parola değiştirildikten sonra, bu parolayı kullanan tüm uygulamaların, servislerin ve geliştirme ortamlarının yeni parolayı kullanacak şekilde güncellendiğinden ve yeniden başlatıldığından emin olun.
  3. Depodan İfşa Edilen Bilgiyi Kaldırın (Git History Rewriting):
    • DİKKAT: Bu, hassas bir işlemdir ve Git geçmişini değiştirir. Bu nedenle, tüm ekip üyelerinin yeni geçmişi çekmesi gerekecektir.
    • Git geçmişini (git filter-branch veya BFG Repo-Cleaner gibi araçlarla) yeniden yazarak ifşa edilen parolayı tüm geçmiş commit'lerinden tamamen kaldırın. Bu, deponun gelecekteki kopyalarında bile parolanın bulunmamasını sağlar.
    • Sadece .gitignore'a eklemek yeterli değildir, çünkü parola geçmişte zaten mevcuttur.
  4. Güvenlik Olayını Kaydedin ve Değerlendirin: İhlali bir güvenlik olayı olarak kaydedin, olayın nasıl gerçekleştiğini (kim, ne zaman, nasıl) belgeleyin. Olası etkilerini (veritabanına erişim sağlandı mı, veri çalındı mı?) değerlendirin.
  5. Kullanıcıları/Paydaşları Bilgilendirin (Gerekirse): Eğer kişisel veri veya hassas bilgi ifşa edilme riski varsa, ilgili yasalara (GDPR, KVKK) uygun olarak etkilenen kullanıcıları ve yetkilileri bilgilendirme planı yapın.

Aynı Olayın Tekrar Yaşanmasını Önlemek İçin Alınacak Önlemler:

  1. Sır Yöneticisi Uygulayın (HashiCorp Vault / Cloud Secret Managers): Hassas yapılandırmayı doğrudan kaynak kontrolünde tutmak yerine, merkezi bir sır yöneticisine taşıyın. Uygulamalar bu yöneticiden sırları güvenli bir şekilde çekecektir.
  2. Geliştirici Eğitimi ve Farkındalık: Tüm geliştiricilere güvenlik en iyi uygulamaları, özellikle hassas bilgilerin kaynak kontrolüne dahil edilmemesi, konusunda eğitim verin.
  3. Otomatik Tarama Araçları (Git Secret Scanners): Git depolarına commit yapılmadan önce veya yapıldıktan sonra hassas bilgileri (parola formatları, API anahtarları) otomatik olarak tarayan araçlar (örneğin, GitGuardian, TruffleHog) kullanın. Bu araçlar, yanlışlıkla yapılan commit'leri otomatik olarak tespit edebilir ve engelleyebilir.
  4. Pre-commit Hook'ları: Geliştiricilerin yerel Git depolarına, hassas bilgilerin commit edilmesini engelleyen pre-commit hook'ları (örneğin, Husky ile) kurmalarını zorunlu kılın.
  5. En Az Ayrıcalık Prensibi: Uygulama ve servisler için veritabanına erişim izinlerini en aza indirin. Her servise sadece ihtiyacı olan verilere erişim yetkisi verin.
  6. Sır Rotasyonu Politikaları: Veritabanı parolaları ve diğer sırlar için düzenli rotasyon politikaları uygulayın. Bir sır yöneticisiyle bu süreç otomatikleştirilebilir.
  7. Erişim Kontrolü ve Denetim: Sır yöneticisine kimlerin erişebileceğini sıkı bir şekilde kontrol edin ve tüm erişimleri denetleyin.
  8. Güvenlik İncelemeleri (Security Audits): Düzenli güvenlik incelemeleri ve sızma testleri yaparak sistemdeki zafiyetleri tespit edin.

Bu adımlar, hem mevcut ihlali ele almanıza hem de gelecekte benzer olayların yaşanmasını önlemek için sistemli bir güvenlik duruşu oluşturmanıza yardımcı olacaktır.

Soru 40:
How Would You Investigate a Sudden Increase in API Latency After Deployment?

Bir üretim dağıtımı, uygulama sağlıklı kalsa bile performans regresyonlarına neden olabilir.

Yapılandırılmış bir sorun giderme yaklaşımını kullanın:

  • Dağıtımdan önce ve sonra gecikme, hata oranları, verim ve kaynak kullanımını karşılaştırın.
  • Dağıtık izlemeleri (distributed traces) ve uygulama günlüklerini inceleyin.
  • Veritabanı sorgu planlarını, bağlantı havuzu metriklerini ve harici API gecikmelerini gözden geçirin.
  • Garbage collection, thread çekişmesi ve senkronizasyon darboğazlarını araştırın.
  • Yapılandırma ve bağımlılık değişikliklerini karşılaştırın.
  • Gerektiğinde hizmeti geri yüklemek için geri alın, ardından kök neden düzeltmesini doğrulayın.

Senaryo: Bir API'nin ortalama yanıt süresi, bir sürümden hemen sonra 300 milisaniyeden 5 saniyeye yükseliyor, CPU kullanımı normal kalırken. Nedeni nasıl izole edersiniz ve geri alma gerekip gerekmediğini nasıl belirlersiniz?

Bir dağıtımdan sonra API gecikmesinde ani bir artış, üretim ortamında karşılaşılabilecek en kritik performans sorunlarından biridir. Bu, hemen ele alınması gereken ve sistemli bir sorun giderme yaklaşımı gerektiren bir durumdur. Amaç, sorunun kök nedenini hızlıca belirlemek ve hizmeti normal durumuna döndürmektir.

Yapılandırılmış Sorun Giderme Yaklaşımı:

Adım 0: Durumu Değerlendirme ve İletişim (Acil Durum Yönetimi):

  • Etkiyi Değerlendirin: Gecikme artışı sadece belirli bir API'yi mi, yoksa tüm sistemi mi etkiliyor? Hata oranları da arttı mı?
  • İletişim: İlgili ekipleri (DevOps, SRE, Geliştirme) bilgilendirin. Bir "incident" (olay) başlatın.
  • Gerekirse Geri Alma (Rollback): Eğer etki genişse ve kritik bir hizmet etkileniyorsa, sorunun kök nedeni bulunana kadar hizmeti hemen önceki kararlı sürüme geri almak öncelik olabilir. Bu, daha fazla hasarı önler.

Adım 1: Temel Metrikleri Karşılaştırma (Öncelikli Teşhis):

  • Dağıtım Öncesi ve Sonrası Karşılaştırma: APM araçları (Dynatrace, New Relic, AppDynamics), Prometheus/Grafana veya diğer izleme sistemlerini kullanarak dağıtımdan hemen önce ve sonraki metrikleri karşılaştırın:
    • Gecikme (Latency): Hangi API uç noktalarının (endpoint) gecikmesinin arttığını belirleyin. Ortalama (p50), 95. persentil (p95) ve 99. persentil (p99) gecikme sürelerini kontrol edin.
    • Hata Oranları: Gecikme ile birlikte hata oranları da arttı mı? Hangi tür hatalar?
    • Verim (Throughput): İstek başına düşen işlem sayısı veya saniyedeki istek sayısı düştü mü?
    • Kaynak Kullanımı: CPU, bellek, disk I/O, ağ bant genişliği gibi sunucu/pod kaynak kullanımlarını karşılaştırın.
  • Senaryo Bilgisi: API'nin ortalama yanıt süresi 300ms'den 5s'ye yükseliyor, CPU kullanımı normal kalırken.
    • Çıkarım: CPU'nun normal kalması, uygulamanın aktif olarak hesaplama yapmadığını, bunun yerine bir şeyi beklediğini (I/O, kilit, harici servis, veritabanı) gösterir. Bu, tipik bir bloklama veya bekleme durumuna işaret eder.

Adım 2: Detaylı Analiz (Kök Neden İzolasyonu):

a. Uygulama Logları ve Dağıtık İzlemeler (Distributed Traces):

  • Uygulama Logları:
    • Yeni dağıtımda log seviyesi ayarlarının değişip değişmediğini kontrol edin (örneğin, debug loglarının açılması performansı düşürebilir).
    • Gecikmeli istekler sırasında loglarda anormal desenler (örneğin, tekrarlanan hata mesajları, uyarılar) olup olmadığını arayın.
    • Loglama altyapısının kendisinde bir sorun olup olmadığını kontrol edin (örneğin, merkezi log sunucusuna erişim sorunları).
  • Dağıtık İzlemeler (Distributed Tracing - Jaeger, Zipkin, OpenTelemetry):
    • Etkilenen API çağrılarının izlerini (trace) inceleyin. Bu, bir isteğin farklı servisler ve bileşenler (veritabanı, önbellek, harici API'ler) arasında ne kadar zaman harcadığını gösterir.
    • Hangi "span"lerin (işlemlerin) ani gecikme artışına neden olduğunu belirleyin. Örneğin, veritabanı çağrıları mı, bir Redis isteği mi, yoksa başka bir mikroservis çağrısı mı yavaşladı?

b. Veritabanı ve Harici API Bağımlılıkları:

  • Veritabanı Sorgu Planları ve Metrikleri:
    • Veritabanı sunucusunun aktif sorgularını ve performans metriklerini (CPU, disk I/O, kilitlenmeler, uzun süren sorgular) kontrol edin.
    • Dağıtımdan sonra yeni veya değiştirilmiş SQL sorgularının "explain plan"larını (sorgu planı) inceleyin. Yeni bir indeks eksikliği veya kötü optimize edilmiş bir sorgu, aniden yavaşlamaya neden olabilir.
    • Bağlantı havuzu metriklerini (aktif bağlantılar, bekleyen bağlantılar, bağlantı alma süresi) inceleyin (bkz. Soru 36). Bir bağlantı havuzu tükenmesi veya yavaşlaması gecikmeye neden olabilir.
  • Harici API Gecikmeleri: Uygulamanın çağırdığı üçüncü taraf API'lerin veya diğer mikroservislerin gecikme metriklerini kontrol edin. Bir downstream (aşağı akış) servisi yavaşlamış olabilir.
  • Önbellek Metrikleri (Redis, Memcached): Önbellek isabet oranlarını (cache hit ratio) ve önbelleğe erişim gecikmelerini kontrol edin. Önbelleğin boşaltılması veya performans düşüşü, veritabanına daha fazla yük bindirerek gecikmeyi artırabilir.

c. JVM ve Uygulama Dahili Durumları:

  • Garbage Collection (GC): GC günlüklerini analiz edin (GCViewer, GCeasy). Uzun süreli GC duraklamaları (STW - Stop-The-World) uygulamanın yanıt vermemesine ve gecikmenin artmasına neden olabilir. Yüksek GC aktivitesi, gereksiz nesne oluşturma veya bellek sızıntısına işaret edebilir (bkz. Soru 31).
  • Thread Çekişmesi ve Senkronizasyon Darboğazları:
    • Uygulamanın thread dump'ını alın (jstack <pid>). Thread dump'ları analiz ederek hangi thread'lerin hangi kilitleri beklediğini (BLOCKED state), hangi metotlarda çok zaman harcadığını veya sonsuz döngüye girip girmediğini görebilirsiniz.
    • synchronized blokları, ReentrantLock veya ConcurrentHashMap gibi eş zamanlılık mekanizmalarının yanlış kullanımı darboğazlara yol açabilir.
  • Heap Dump Analizi: Eğer CPU normalken bellek kullanımı yükseliyorsa, bir bellek sızıntısı veya aşırı nesne oluşturma olasılığına karşı heap dump alıp analiz edebilirsiniz (bkz. Soru 31).

d. Yapılandırma ve Bağımlılık Değişiklikleri:

  • Kod Farkı (Code Diff): Dağıtılan yeni sürüm ile önceki kararlı sürüm arasındaki kod farkını inceleyin. Hangi kod değişikliklerinin performansı etkilemiş olabileceğini tespit edin.
  • Yapılandırma Farkı: Uygulama yapılandırma dosyalarındaki (application.yml, .properties) veya ortam değişkenlerindeki değişiklikleri karşılaştırın. Örneğin, yanlışlıkla artırılmış bir timeout değeri veya yanlış veritabanı bağlantı havuzu ayarı.
  • Bağımlılık Güncellemeleri: Güncellenen kütüphane sürümlerini kontrol edin. Bir bağımlılık güncellemesi, performans regresyonuna veya beklenmedik davranışa neden olabilir.

Geri Alma Gerekip Gerekmediğini Belirleme:

  • Etki Alanı ve Şiddet: Eğer gecikme artışı geniş bir kullanıcı kitlesini etkiliyor ve kritik işlevselliği bozuyorsa, ve/veya sistem genelinde hata oranları artıyorsa, hızlı bir geri alma (rollback) genellikle en iyi ilk yanıttır.
  • Kök Neden İzolasyon Hızı: Kök neden çok hızlı bir şekilde izole edilebiliyorsa ve düzeltme de hızlıca uygulanabiliyorsa, geri alma gerekmeyebilir. Ancak bu çoğu zaman mümkün olmaz.
  • İş Etkisi: İş birimi üzerindeki potansiyel gelir kaybı veya müşteri memnuniyetsizliği, geri alma kararında ana belirleyici faktördür.

Senaryoda: API yanıt süresi 300ms'den 5s'ye çıkıyor ve CPU kullanımı normal kalıyor. Bu genellikle bir I/O bekleme sorununa işaret eder.

  1. Acil Geri Alma: 5 saniyelik yanıt süresi, çoğu web/mobil uygulama için kabul edilemez derecede yüksek bir gecikmedir. Eğer bu gecikme geniş bir kullanıcı tabanını etkiliyorsa, hemen geri alma kararı alınmalıdır.
  2. Teşhis Odaklanması:
    • Dağıtık İzlemeler: Öncelikle dağıtık izleme sistemlerini (Jaeger, Zipkin) kontrol ederdim. Bu, hangi harici bağımlılığın (veritabanı sorgusu, başka bir mikroservis çağrısı, Redis isteği) yanıt süresinin 4.7 saniye civarında arttığını hızlıca gösterecektir.
    • Veritabanı: Eğer izlemeler veritabanını işaret ediyorsa, veritabanı performans metriklerini, aktif sorguları ve sorgu planlarını incelerdim. Yeni dağıtımda eklenen veya değiştirilen bir sorgu, eksik bir indeks nedeniyle yavaşlamış olabilir.
    • Harici Servis: Eğer başka bir mikroservis veya üçüncü taraf API'si yavaşladıysa, o servisin metriklerini ve loglarını incelerdim.
    • Ağ: Nadiren olsa da, ağ gecikmeleri de benzer semptomlara neden olabilir. Ağ metrikleri kontrol edilmelidir.
  3. Kök Neden Düzeltmesi ve Doğrulama: Kök neden (örneğin, eksik indeks, yavaşlayan harici servis, kodda bloklama yapan bir I/O işlemi) bulunduğunda, düzeltme uygulanır ve test ortamında doğrulanır. Ardından, düzeltme ile yeni bir dağıtım yapılır ve üretim ortamında dikkatlice izlenir.

Bu sistematik süreç, üretim sorunlarının hızlı ve etkili bir şekilde çözülmesini sağlar.
