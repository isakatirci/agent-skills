Soru 1 ConcurrentHashMap içinde Thread Safety nasıl sağlanır?

Önce hedefi net anlatalım: Aynı anda birden fazla thread map’e yazarsa değerler bozulmamalı. ConcurrentHashMap bunu lock mantığıyla yapar ama her şeyi tek kilitlemez.

Mantık şudur: Map genelde parçalar halinde çalışır. Her parça için ayrı synchronization vardır. Böylece farklı bucket’lar aynı anda değiştirilebilir.

Java 8+ tarafında bazı işlemler için CAS gibi atomic yöntemler kullanılır. Bu da “kilit bekleme” süresini azaltır.

Ayrıca ConcurrentHashMap, null key ve null value kabul etmez. Çünkü null’lı eşzamanlı davranışları hata üretir ve atomik mantığı karıştırır. 

// Amaç: Aynı map üzerinde farklı thread'ler güvenli şekilde update yapsın.
// ConcurrentHashMap bunun için tasarlanmıştır.
import java.util.concurrent.ConcurrentHashMap;

public class ConcurrentHashMapDemo {

  public static void main(String[] args) {
    ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

    // putIfAbsent: atomik şekilde "yoksa ekle" yapar.
    map.putIfAbsent("count", 0);

    // compute: key mevcutsa hesaplar, değilse yeni değer üretir.
    // Bu işlem tek bir atomic adım gibi düşünülür.
    map.compute("count", (k, v) -> v + 1);

    System.out.println(map.get("count"));
  }
}

Junior ipucu: “Concurrent” kelimesi “her şey kilitlendi” demek değildir. Daha akıllı bölme + atomic operasyon demektir.

Soru 3 wait(), sleep(), join() farkları nelerdir?

Bu üçü “bekleme” gibi görünür ama mekanizması farklıdır. Aradaki farkı bilmek thread bug’larını azaltır.

wait() bir monitor işlemidir. Thread, ilgili lock’u bırakır. Sonra ya notify/notifyAll gelene kadar bekler, ya da timeout biter.

sleep() lock’u bırakmaz. Thread sadece belirli süre “uyur”. Bu süre dolunca tekrar çalışmaya döner.

join() ise başka bir thread bitene kadar bekler. Yani “benim threadim sen bitene kadar dur” der. 

// wait() ve notify() ile doğru kullanım örneği
final Object monitor = new Object();

Thread consumer = new Thread(() -> {
  synchronized (monitor) {
    try {
      // wait: lock'u bırakır
      monitor.wait(1000); // notify gelmezse 1 sn sonra uyanır
      // Buraya notify veya timeout sonrası gelinir
    } catch (InterruptedException e) {
      // interrupt handle
    }
  }
});

Thread producer = new Thread(() -> {
  synchronized (monitor) {
    // Üretim yap (pseudo)
    // ...

    // notify: consumer'ı uyandır
    monitor.notify();
  }
});

consumer.start();
producer.start();
// sleep() örneği: lock'u bırakmaz
Object lock = new Object();

Thread t = new Thread(() -> {
  synchronized (lock) {
    try {
      // sleep: lock halen tutuluyor (diğer thread'ler lock'u alamaz)
      Thread.sleep(500);
    } catch (InterruptedException ignored) {}
  }
});

t.start();

Soru 4 inner class ve static nested class farkı nedir?

Önce şunu düşün: Non-static inner class, dış class’ın instance’ına bağlıdır. Bu yüzden dış sınıf referansını taşır.

Static nested class ise dış instance’a bağlı değildir. Sadece dış class’ın static üyelerini kullanabilir.

Bu fark memory ve erişim yetkisini etkiler. Bu yüzden doğru türü seçmek önemlidir. 

class Outer {
  private int x = 10;

  // Non-static inner class: Outer instance'a bağlıdır
  class Inner {
    int getX() {
      // Outer.x'e ulaşabilir
      return x;
    }
  }

  // Static nested class: Outer instance'a bağlı değil
  static class StaticInner {
    // int getX() { return x; } // Bu derlenmez: x static değil
  }
}

Soru 5 equals() ve == farkı nedir?

Java’da iki farklı “eşitlik” kavramı var: referans eşitliği ve mantıksal eşitlik.

== referans karşılaştırır. Yani iki değişken aynı nesneyi mi gösteriyor?

equals() mantıksal karşılaştırmadır. İki nesnenin içeriği aynı mı?

equals() override ediyorsan, hashCode() de tutarlı olmalıdır. Çünkü HashMap/HashSet equals + hashCode birlikte çalışır. 

import java.util.Objects;

class User {
  private final String email;

  User(String email) {
    this.email = email;
  }

  @Override
  public boolean equals(Object o) {
    // 1) Aynı referans => aynı nesne
    if (this == o) return true;

    // 2) Tür kontrolü
    if (!(o instanceof User other)) return false;

    // 3) Mantıksal eşitlik: email aynı mı?
    return Objects.equals(this.email, other.email);
  }

  @Override
  public int hashCode() {
    // equals'te hangi alanı kullanıyorsan hashCode'ta da aynı alan olmalı.
    return Objects.hash(email);
  }
}

Soru 6 hashCode() neden equals() ile birlikte override edilir?

Hash tabanlı koleksiyonlar önce hashCode hesaplar. Sonra aynı hash’li bucket içinde equals() dener.

Eğer hashCode tutarsızsa, aynı mantıksal eleman başka bucket’a düşer. Sonra HashMap “böyle bir anahtar yok” gibi davranabilir.

Bu yüzden equals() değişince hashCode() da aynı mantıkla güncellenmelidir. Bu kural “contract” gibi düşün.

Soru 7 immutable kavramını açıkla.

Immutable demek: nesnenin durumu değişmez. Yani oluşturduktan sonra field’lar değişmez.

Bu genelde final alanlar ve kopya alma ile yapılır. Eğer mutable bir obje dışarıdan alınıyorsa, onu da kopyalarsın.

Immutable nesneler thread-safety açısından çok kolaydır. Çünkü başka thread “durumu bozamaz”. 

import java.util.List;

final class ImmutableUser {
  private final String name;

  // Eğer roles listesi dışarıdan gelirse,
  // dışarıdan değişebilir. Bu yüzden kopya alırız.
  private final List<String> roles;

  ImmutableUser(String name, List<String> roles) {
    this.name = name;

    // List.copyOf: yeni bir immutable görünüm döndürür
    this.roles = List.copyOf(roles);
  }

  public String getName() { return name; }
  public List<String> getRoles() { return roles; } // artık risksiz
}

Soru 8 Thread pool nedir? Executors neden kullanılır?

Thread pool, thread’leri “hazır bekletme” fikridir. Yeni her iş için yeni thread açmak pahalıdır.

Thread pool ile thread’ler yeniden kullanılır. Bu sayede CPU boşa gitmez.

Executors, thread pool oluşturmayı kolaylaştırır. ayrıca yönetimi (shutdown gibi) düzgün yapmana yardım eder. 

import java.util.concurrent.*;

public class ThreadPoolDemo {

  public static void main(String[] args) throws Exception {
    // 4 worker thread: aynı anda en fazla 4 task çalışır.
    ExecutorService pool = Executors.newFixedThreadPool(4);

    // submit: sonucu istiyorsan Future döndürür.
    Future<Integer> future = pool.submit(() -> {
      // Buraya IO/DB işin gelebilir.
      // Task biterse result dönmeli.
      return 42;
    });

    // Future bitene kadar bekler.
    // Production'da bunu kör şekilde yapmak yerine async akış tercih edilir.
    System.out.println("Result = " + future.get());

    // Düzgün kapatma: yeni task almayı durdur.
    pool.shutdown();
  }
}

Soru 9 CompletableFuture ile async akış nasıl kurulur?

CompletableFuture, “gelecek zamanı” temsil eder. Yani sonucu henüz yoktur ama sonra gelecek.

supplyAsync ile bir değer üretirsin. thenApply ile o değeri dönüştürürsün. thenAccept ile değerle işlem yaparsın ama yeni değer döndürmez.

Async yaparken mutlaka executor kullanabilirsin. Böylece hangi thread havuzunda çalıştığını kontrol edersin. 

import java.util.concurrent.*;

public class CompletableFutureDemo {

  public static void main(String[] args) {
    ExecutorService exec = Executors.newFixedThreadPool(4);

    CompletableFuture<String> f =
        CompletableFuture.supplyAsync(() -> {
          // Örnek: dış servis çağrısı veya DB okuma
          return "hello";
        }, exec)
        .thenApply(s -> {
          // Değeri dönüştür
          return s.toUpperCase();
        });

    // Sonucu kullanan action
    f.thenAccept(result -> System.out.println("Final = " + result));

    // Demo bitmeden program kapanmasın diye basit bekleme:
    // (Gerçek projede doğru lifecycle/shutdown yönetimi yap.)
    exec.shutdown();
  }
}

Junior ipucu: async zinciri kurarken hata akışı için exceptionally/handle da ekleyebilirsin.

Soru 10 Java Garbage Collection nasıl çalışır? Minor/Major farkı nedir?

Java’da bellek yönetimi GC (Garbage Collection) ile yapılır. GC’nin hedefi: kullanılmayan nesneleri temizlemek.

Heap genelde bölgelere ayrılır. Young generation ve Old/Tenured generation gibi.

Minor GC çoğu zaman Young üzerinde çalışır. Çünkü yeni nesneler genelde önce burada yaşar.

Major/Full GC Old generation üzerinde çalışır. Daha ağırdır. Bu yüzden daha uzun duraklama (pause) yaratabilir.

Modern GC’lerde (örn. G1) “regions” mantığı vardır. Ama mülakat için ana fikir: young daha sık, old daha pahalıdır.

Soru 11 Spring Bean lifecycle adımlarını özetler misin?

Spring konteyneri bir Bean oluşturunca bir süreçten geçer. Bu süreç “lifecycle” olarak bilinir.

Genel akış: Bean instantiation olur. Sonra dependency injection yapılır.

Sonra aware callback’ler (isteğe bağlı) çalışır. Daha sonra BeanPostProcessor’lar devreye girer.

init aşaması çalışır. Örneğin @PostConstruct metodun çağrılır. Son olarak uygulama request almaya hazır olur.

Context kapanınca destroy aşaması çalışır. Örneğin @PreDestroy ile cleanup yapılır. 

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.stereotype.Component;

@Component
public class LifecycleBean {

  @PostConstruct
  public void init() {
    // Bean hazır olduğunda bir kez çalışır.
    // Örn: cache warm-up, bağlantı hazırlığı.
    System.out.println("init called");
  }

  @PreDestroy
  public void destroy() {
    // Application kapanırken cleanup olur.
    // Örn: thread pool kapat, resource release.
    System.out.println("destroy called");
  }
}

Soru 12 @Component, @Service, @Repository farkı nedir?

Bunların hepsi Spring tarafından component scan ile bulunabilir. Hepsi Bean oluşturur.

Fark daha çok “semantic intent” tarafındadır. @Service: iş (business logic) için. @Repository: veri erişimi için.

@Repository genelde exception translate gibi ek davranışlar sağlayabilir. Yani persistence layer hatalarını daha Spring-friendly hale getirebilir.

Junior için kısa kural: “Bana ait katmanı anlatmak için doğru annotation’ı seç.”

Soru 13 Dependency Injection (DI) neden önemlidir?

DI, sınıfları birbirine sıkı bağlamamayı sağlar. Yani “new ile bağımlılık yaratma” yerine Spring bunu senin adına inject eder.

Soru 14 Constructor injection vs Field injection farkı nedir?

Constructor injection önerilir. Çünkü bağımlılıklar açıkça görünür.

Constructor injection ile class oluşturulurken dependency zaten garanti gelir. Böylece null hataları daha erken yakalanır.

Field injection’da bağımlılık dışarıdan set edilir. Testte bunu yapmak bazen daha zor olur. Ayrıca final field kullanamazsın.

  }

  // business methods...

Soru 16 Propagation türleri ne işe yarar?

Transaction propagation, “zaten bir transaction var mı?” sorusuna göre davranışı belirler.

Örneğin REQUIRED genelde varsayılandır. Zaten transaction varsa devam eder. Yoksa yeni başlatır.

REQUIRES_NEW her zaman yeni transaction açar. Dıştaki transaction etkilenmez.

NESTED ise nested transaction mantığına dayanabilir ama DB ve platforma göre davranış değişebilir. Mülakatta ana fikir: “iç işlem dış transaction’ı etkiler mi, etkilemez mi?”

Soru 17 Isolation level neden önemli?

Isolation level, transaction’ların birbirlerini ne kadar “izole” ettiğini söyler.

Örneğin dirty read gibi problemler isolation seviyesine göre değişir. Daha yüksek isolation genelde daha tutarlıdır.

Ama daha yüksek isolation genelde daha fazla lock demektir. Bu da daha düşük throughput ve daha yavaş sistem anlamına gelebilir.

Junior için: “Tutarlılık ↔ Performans” trade-off’u var. Proje için doğru seviyeyi seçmek gerekir.

Soru 20 JPA entity lifecycle adımları nelerdir?

JPA entity’lerin yaşam döngüsünde birkaç durum vardır. Bu durumlar “entity persistence context içinde mi?” sorusunu anlatır.

New (transient): Entity henüz DB’ye kaydedilmemiştir. Hibernate bunu takip etmeyebilir.

Managed: Persist eder veya repository save yaparsın. Persistence context entity’yi takip eder.

Managed iken değişiklik yaparsan, transaction commit olunca DB’ye yansır. Yani genelde “dirty checking” çalışır.

Detached: Persistence context entity’yi artık takip etmez. Tekrar merge edilirse managed olur.

Removed: Remove ile entity silinmeye aday olur.

Soru 21 Optimistic Locking vs Pessimistic Locking (JPA)

Optimistic locking “çakışma nadir olur” fikrine dayanır. Yani önce çalışırsın, sonra çakışma var mı kontrol edersin.

JPA’da bu genelde @Version ile olur. İki transaction aynı row’u güncellerse biri commit’te “version değişti” hatası alabilir.

Pessimistic locking “çakışma sık olur” fikrine dayanır. DB lock alırsın. Diğer transaction’lar bekler.

Sonuç: Optimistic genelde daha az lock maliyeti. Pessimistic daha güçlü tutarlılık ama deadlock riski ve throughput düşüş olabilir. 

import jakarta.persistence.*;

@Entity
public class InventoryItem {

  @Id
  private Long id;

  // Optimistic locking counter
  @Version
  private Long version;

  private int quantity;
}

Soru 22 N+1 problem nedir? Nasıl önlenir?

N+1 demek şudur: Bir tane sorgu ile ana listeyi alırsın. Sonra her satır için ekstra sorgu çalışır.

Örnek: 1 sorgu ile 10 order alırsın. Sonra her order için items almak istersen toplam 11 sorgu çıkar.

Bu performansı öldürür. Çünkü round-trip artar.

Çözüm: fetch join ile ilişkileri beraber çekmek. EntityGraph kullanmak. Doğru fetch type (LAZY/EAGER) seçmek. Bazen batch fetching de yardımcı olur. 

// Fetch Join ile N+1'i azaltma
// JPQL: Order + items beraber gelir.
@Query("SELECT o FROM Order o JOIN FETCH o.items WHERE o.customerId = :id")
List<Order> findOrdersWithItems(@Param("id") Long customerId);

Soru 23 Hibernate get() vs load() farkı

get() genelde “hemen sorgula ve sonucu dön” mantığındadır. Entity varsa döner. Yoksa null döner.

load() ise genelde “lazy proxy oluştur” mantığındadır. Sadece proxy döndürebilir. Gerçek data erişilince sorgu olur.

Eğer entity yoksa load çağırınca genelde hemen değil, erişim anında hata fırlatılabilir (ör. EntityNotFoundException).

Soru 24 Cascade türleri (CascadeType) ne işe yarar?

Cascade, parent entity üzerinde bir operation yapılınca child’a da aynı işlemi uygular.

Örnek: Parent persist edilirse child persist de olsun istersin. Ya da parent remove edilirse child da silinsin istersin.

Burada kritik nokta: Cascade yanlış kullanılırsa çok tehlikeli olur. Beklenmedik delete veya update tetiklenebilir. 

// Parent kaydedilince child da kaydedilsin
import jakarta.persistence.*;
import java.util.List;

@Entity
public class Parent {
  @Id
  private Long id;

  @OneToMany(cascade = CascadeType.PERSIST)
  private List<Child> children;
}

Soru 25 E-Commerce Order Tracking System tasarla

Hedef: order durumunu doğru ve tutarlı şekilde göstermek. Kullanıcı “ödeme alındı mı?” “kargoya verildi mi?” görebilmeli.

Event-driven yaklaşım burada çok iyi çalışır. Örn: OrderCreated, PaymentCaptured, Shipped, Delivered.

Her event geldiğinde order’ın state’i değişir. Ayrıca bir “status history” tablosu tutarsın. Böylece geçmişi görmek kolay olur.

Dış servis (shipping provider gibi) için adapter kullanırsın. Event’leri idempotent şekilde işler ve duplicate event’leri güvenle yutarsın. 

// İdeal fikir: Event'i state machine gibi uygula.
// Pseudocode: eventType geldiğinde status değişsin.
enum OrderStatus { CREATED, RESERVED, PAID, SHIPPED, DELIVERED, CANCELED }

class OrderState {
  private OrderStatus status = OrderStatus.CREATED;

  public void apply(String eventType) {
    switch (eventType) {
      case "OrderCreated" -> status = OrderStatus.CREATED;
      case "PaymentCaptured" -> status = OrderStatus.PAID;
      case "Shipped" -> status = OrderStatus.SHIPPED;
      case "Delivered" -> status = OrderStatus.DELIVERED;
      default -> {
        // İlgisiz event'i ignore et
      }
    }
  }
}

Soru 27 Design a URL Shortener

Shortener’ın temel görevi: uzun URL’yi kısa bir kod’a maplemek.

Bileşenler: 1) URL mapping tablosu (short_code -> target_url) 2) Redirect endpoint (short_code al, target_url’ye yönlendir) 3) Cache (çok tekrar eden kodlar) 4) Analytics (tıklama sayısı)

short_code üretimi: random veya counter + base62 kullanılır. Çakışma olursa unique constraint ile yönetirsin. 

// Kısa code üretimi (random)
// Not: Çakışma olasılığı var. DB unique constraint + retry ile yönet.
import java.util.concurrent.ThreadLocalRandom;

public class ShortCodeGenerator {
  private static final String ALPHABET =
      "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";

  public static String generate(int len) {
    StringBuilder sb = new StringBuilder(len);

    for (int i = 0; i < len; i++) {
      int idx = ThreadLocalRandom.current().nextInt(ALPHABET.length());
      sb.append(ALPHABET.charAt(idx));
    }

    return sb.toString();
  }
}

Soru 30 Synchronized vs volatile farkları nedir?

volatile daha çok visibility içindir. Bir thread yazınca, diğer thread o değeri görür.

Ama volatile tek başına atomicity sağlamaz. Örneğin i++ gibi işlemler atomic değildir. Çünkü “read + compute + write” birden fazla adım içerir.

synchronized ise hem visibility hem mutual exclusion sağlar. Yani aynı lock’u aynı anda iki thread alamaz.

Soru 31 Memory leak nasıl yakalanır? Heap dump ne zaman alınır?

Memory leak genelde “uygulama normal çalışırken RAM artmaya devam ediyor” hissiyle anlaşılır. CPU normal olabilir ama heap büyür.

Bu durumda heap dump alırsın. Sonra MAT gibi araçlarla dominator tree incelersin. En çok tutulan referanslar nereden geliyor görürsün.

Yaygın leak sebepleri: limitsiz büyüyen static collection’lar, cache yanlış kullanımı, event listener’ların hiç temizlenmemesi.

Soru 32 Thread dump ile deadlock / contention nasıl anlaşılır?

Thread dump almak için genelde jstack kullanılır. Amaç: thread’ler “hangi lock’u bekliyor” görmek.

Deadlock şüphesinde genelde birden fazla thread birbirinin kilidini bekler. Thread dump’te “waiting for lock” zinciri görülür.

Contention şüphesinde de çok sayıda thread aynı lock için BLOCKED olabilir. Bu da performansı düşürür.

Sonra kodda lock sıralamasını kontrol edersin. Tutarsız lock order deadlock riskini artırır.

Soru 33 Idempotency (idempotency key) neden önemlidir?

Idempotency demek: Aynı isteği iki kez atsan bile sonuç değişmesin.

Distributed sistemlerde retry sık olur. Network hata verdiğinde istemci tekrar gönderir.

Eğer idempotent değilsen, Payment gibi işlemler iki kez “charge” olabilir. Bu ciddi problem.

Idempotency key ile: aynı key tekrar gelirse aynı sonucu dönersin. Yani “duplicate request” güvenle yönetilir. 

// Konsept: idempotency key ile sonucu cachele/record et.
import java.util.concurrent.ConcurrentHashMap;

class IdempotentPaymentStore {
  private final ConcurrentHashMap<String, String> results = new ConcurrentHashMap<>();

  public String pay(String idempotencyKey) {
    // computeIfAbsent: key ilk kez gelirse işlem kaydı oluşturulur.
    // ikinci kez gelirse aynı değer döner.
    return results.computeIfAbsent(idempotencyKey, k -> "PAID_OK");
  }
}

Soru 34 Distributed messaging’te DLQ nedir?

DLQ (Dead-Letter Queue) işlenemeyen mesajlar için ayrılmış bir kuyruğudur.

Normal consumer mesajı işler. Ama mesaj sürekli hata veriyorsa retry sonsuza gidebilir. Bu durum sistemi kilitler.

DLQ, belirli retry limitinden sonra mesajı “kenara alır”. Böylece sistem devam eder.

Sonra DLQ’daki mesajlar manuel incelenir veya recovery worker ile yeniden işlenir.

Soru 35 Bulkhead pattern nedir? Neden kullanılır?

Bulkhead pattern, gemilerdeki bölmeler gibi düşünebilirsin. Bir bölüm hasar görse diğerleri batmaz.

Backend’de bu, kaynakları ayırmaktır. Örneğin thread pool’u her feature için ayırırsın.

Böylece bir endpoint yavaşladığında tüm sistemin thread’i dolmaz. Sistem “kısmen çalışmaya” devam eder.

Bu yaklaşım özellikle production’da çok değerlidir.

Soru 36 Circuit breaker neden gerekir?

Circuit breaker, hatalı/slow bir dış servise sürekli istek atmayı durdurur.

Dış servis down veya çok yavaşsa sistem daha çok yüklenir. Bu da “cascade failure” yapabilir.

Circuit breaker hataları izler. Belirli eşiği geçince “OPEN” olur ve yeni istekleri kısa devre yapar.

Sonra “half-open” durumunda sınırlı deneme yapılır. Servis toparlandıysa “close” edilir. 

// Konsept: Circuit breaker pseudo state machine
class CircuitBreaker {
  enum State { CLOSED, OPEN, HALF_OPEN }
  private State state = State.CLOSED;

  public boolean allowRequest() {
    // OPEN iken istekleri reddet
    return state != State.OPEN;
  }

  public void onSuccess() {
    // Başarı gelirse circuit'i kapat
    state = State.CLOSED;
  }

  public void onFailure() {
    // Failure artarsa circuit'i aç
    state = State.OPEN;
  }
}

Soru 37 Reliable retries ve timeouts mikroservislerde nasıl tasarlanır?

En önemli kural: timeout’suz retry yok. Çünkü bağlantı asla dönmezse retry’ler request biriktirir.

Önce timeout kuralını koyarsın. Connection timeout ve request timeout ayrıdır. Sonra retry davranışı gelir.

Retry’i her hatada yapmazsın. Sadece “retryable” hatalarda yaparsın. Örn: bazı 5xx ve network hataları.

Exponential backoff kullanırsın. Jitter eklersin. Böylece retry storm olmaz. 

// Pseudo: retry politikasI
class RetryPolicy {

  public void runWithRetry(Runnable task) {
    int maxAttempts = 3;

    for (int attempt = 1; attempt <= maxAttempts; attempt++) {
      try {
        task.run();
        return; // başarılıysa çık
      } catch (Exception ex) {

        // Burada ex'in retryable olup olmadığını kontrol edersin.
        boolean retryable = true; // örnek

        if (!retryable || attempt == maxAttempts) {
          throw ex;
        }

        // Exponential backoff: 100ms, 200ms, 400ms gibi
        long baseMs = 100L;
        long backoff = baseMs * (1L << (attempt - 1));

        // Jitter: aynı anda herkesin retry yapmasını engeller
        long jitter = (long) (Math.random() * 50);

        sleep(backoff + jitter);
      }
    }
  }

  private void sleep(long ms) {
    try { Thread.sleep(ms); } catch (InterruptedException ignored) {}
  }
}

Soru 38 Servis geçici kapalıyken sipariş durumunu doğru tutmak nasıl yapılır?

Burada amaç: “tek servis down olunca tüm sistem bozulmasın”.

Ayrıca Saga ile compensating transactions düşünülür. Yani bazı adımlar iptal edilir, state düzeltilir.
